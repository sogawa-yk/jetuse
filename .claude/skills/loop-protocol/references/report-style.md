# 報告書スタイル規約（人間に出す HTML の作り方）

報告書は施主が読む「読み物」であり、実装者の作業記録ではない。読んで分からなければ、
その報告書は失敗である（実例: 2026-07-28、ADR-0018 の承認判断をタスクパケット様式で出して
「わかりにくすぎて読む気が起きない」と差し戻し）。以下は全報告書に共通の規約。

## 1. どのテンプレートを使うか

| 報告の目的 | テンプレート | 骨格 |
| --- | --- | --- |
| **実装タスクの完了報告**（受け入れ条件を満たした・承認してコミットしたい） | `task-packet-template.html` | 何を・なぜ / 例外 / 判定 / 差分 / 動作確認 |
| **方式・設計の判断を仰ぐ**（ADR、やり方を変えたい、選択肢を選んでほしい） | `decision-packet-template.html` | 前提 → なぜ → どのように（図）→ 承認してほしいこと |

判断を仰ぐ報告に実装報告の様式を使わない。実装報告の様式は**文脈が共有済み**の前提で
判定・差分・証跡を並べる形式で、方式の是非を決める材料にはならない。

## 2. 構成

- **前提から書く。** 読み手が持っている前提を2〜3行で確認してから本題に入る。
  施主は毎日この作業を見ているわけではない。
- **なぜ → どのように の順。** 実装の詳細から始めない。
- **専門語は展開する。** 内部識別子・パス・HTTP コード・`§`参照をそのまま置かない。
  どうしても必要なら `<details>` の中へ。
- **詳細は畳む。** `<details>` を開かなくても承認可否が決まる状態にする。
  findings 全件・パス・設定キー・ファイル数は畳む側。
- **承認してほしいことを最後に箇条書き。** 何を答えれば前に進むかを、選択肢の形で示す。

## 3. 図（必須。文章だけで構造を説明しない）

- **HTML + CSS で描く。**`div` の枠線・背景・グリッドと、矢印は文字（`→` `↓`）。
  文字量が増えれば箱が伸びるので、**重なりが原理的に起きない**。
- **SVG で座標を手置きしない。** 固定 viewBox の SVG は、テキストが想定より長いと隣の図形に
  重なり、幅が狭いと文字が縮んで読めなくなる（2026-07-28 の実害）。
  SVG を使ってよいのは**大きさが変わらない装飾アイコン**だけ。
- **幅で縦積みに切り替える。** Obsidian の埋め込み iframe は横幅が狭い。
  `@media (max-width:780px)` で多カラムを1カラムにし、矢印は `rotate(90deg)` で下向きにする。
  横並び前提の文言（「右側の」「左の図」）を本文に書かない。

## 4. 技術制約（Obsidian のサンドボックス iframe で開かれる）

- 単一ファイル完結。**外部依存ゼロ**（CDN・外部フォント・fetch・`<script>` は動かない）。
- 先頭に `<meta charset="utf-8">`（無いと単体ファイルとして開いたとき日本語が化ける）。
- ダーク / ライト両対応（`prefers-color-scheme`）。

## 5. 提示前に必ずレンダリングを見る（省略不可）

書きっぱなしで提示しない。**自分の目で見てから出す。**

```bash
.claude/skills/loop-protocol/scripts/check_report_render.sh <報告書.html>
```

出力された PNG を **Read ツールで実際に開いて**、次を確認する:

- [ ] 図の要素が**重なっていない**（箱と文字、箱と箱）
- [ ] 見切れ・はみ出しがない
- [ ] 不自然な折り返し（1文字だけ次行に落ちる等）がない
- [ ] 文字が小さすぎない
- [ ] 畳んだ部分を開かずに、承認可否が判断できる

Chrome が無い環境では検証をスキップしてよいが、**その旨を報告に明記する**（無言で省略しない）。
