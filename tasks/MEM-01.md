# タスク: MEM-01 Oracle AI Database を Agent Memory のバックエンドとして選択可能にする

## 目的
会話の長期記憶（Agent Memory）の格納先として **Oracle AI Database を選べる**ようにする。
RAG の高機能バックエンド（`adb`）と同じ土台・同じ権限体系に載せ、
「記憶も業務データと同じ場所で、同じ SQL・同じアクセス制御で扱える」を成立させる。

## 仕様参照
- `docs/decisions/ADR-0020-rag-metadata-backend.md` §2（Accepted。2026-07-29 のユーザー方針が根拠）
- `docs/decisions/ADR-0006-long-term-memory.md`（**Accepted。棄却しない**。OCI ネイティブ長期メモリ）

## 対象 area
api

## 前提（依存タスク / 人間の事前作業）
- RAGM-02（`adb` バックエンド）で表・埋め込み・索引の土台ができていること。
- ADR-0006 の OCI ネイティブ長期メモリ（プロジェクト LTM + `memory_subject_id`）は**併存**させる。
  置き換えではなく選択式にする。

## 調査してから決めること（着手前）
ADR-0006 の教訓「プロジェクト作成時オプションは作成前に全て棚卸しする」を踏まえ、
実装前に次を実機で確定する（推測で設計しない）:
- [ ] Oracle 側が「Agent Memory」として提供している機能の実体は何か
      （専用 API / パッケージがあるのか、`VECTOR` 表 + 自前設計なのか）。
      ADB 26ai の実機で確認し、無い機能を前提にしない。
- [ ] 記憶の抽出（どの発話を覚えるか）を誰がやるのか。
      OCI ネイティブ LTM は抽出まで込みだが、自前バックエンドでは自分でやることになる。
      その差分コストを見積もる。
- [ ] 忘れられる権利（削除）の経路。ADR-0006 は「会話削除で派生記憶も消える」ことを実機確認済み。
      ADB バックエンドでも同等の保証を設計する。

## 作業内容
- 上記の調査結果を `docs/verification/MEM-01.md` に実行結果付きで残す。
- 記憶の格納先を選択式にする（既定は現行の OCI ネイティブ LTM のまま＝既存挙動を変えない）。
- ADB バックエンドを選んだ場合の書き込み・想起・削除を実装する。
- 能力差を `GET /api/capabilities` に載せる（RAGM-03 と同じ枠組み）。

## 完了条件（検証可能な述語で）
- [ ] 調査結果（Oracle の Agent Memory の実体・抽出の責務・削除経路）が実行結果付きで残っている。
- [ ] 記憶バックエンドを切り替えられ、**既定では現行の挙動が一切変わらない**。
- [ ] ADB バックエンドで、会話をまたいだ想起と subject 分離が実環境で動く。
- [ ] 会話削除で派生記憶も消えることを実環境で示す（ADR-0006 と同等の保証）。
- [ ] `.venv/bin/pytest packages/api/tests` 全緑・`.venv/bin/ruff check packages/api` クリーン。

## E2E シナリオ（実環境 / jetuse-dev）
- [ ] シナリオ1: ADB バックエンドで会話 A の情報が会話 B で想起される。
- [ ] シナリオ2: 別 subject では想起されない（分離の確認）。
- [ ] シナリオ3: 会話削除後に該当記憶が想起されない。
- [ ] 実施不能な範囲は `runs/<run-id>/e2e/SKIPPED.md` に理由を明記。

## 非ゴール / 禁止事項

- 「Oracle が Agent Memory を売っている」から機能があるはず、という前提での実装
  （実機で確認できたものだけを使う。SPIKE-10 の教訓）。
- 顧客データの持ち込み。認証情報・OCID のコミット。
