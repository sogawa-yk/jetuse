# タスク: VID-07 大きな映像を登録できるようにする（Object Storage への直接アップロード）

## 目的
**要求1（映像を登録できること）が実機で成立していない。** API Gateway の本体サイズ上限に阻まれ、
実用的な素材（4K・長尺）が登録できない。映像をゲートウェイに通さない経路へ変える。

## 実測（2026-08-20・jetuse-pubdemo のゲートウェイ）

| 送ったサイズ | 結果 |
|---|---|
| 1 / 5 / 8 / 9 / 10 / 12 / 14 / 15 / 16 / 17 MB | HTTP 200 |
| 20 MB | **HTTP 413** `{"code":413,"message":"Payload Too Large"}` |

**この 413 は API Gateway が返している**（アプリの応答形式は `{"detail": ...}`。アプリ側の上限は
500MB で、そこには届いていない）。利用者の報告は 3840x2160 25fps の mp4。

**なぜ各タスクの E2E で見えなかったか**: VID-01〜06 の E2E は Object Storage を SDK で直接
叩いており、**ゲートウェイを経由する経路を通していなかった**。配備して初めて出た経路差。

## 仕様参照: specs/20-video-search.md §2

## 前提
- VID-01〜06（統合済み）

## 作業内容
- `POST /api/video/assets/upload-url` — 登録の入口。asset を `uploading` で作り、
  **書き込み専用・短命・オブジェクト名を固定した PAR** と asset id を返す
- `POST /api/video/assets/{id}/complete` — ブラウザが PUT を終えたら呼ぶ。
  **実物を検証してから登録を確定する**（存在・サイズ・Content-Type）。検証に落ちたら
  オブジェクトごと片付けて 4xx を返す。**「入れたと言われたから入った」ことにしない**
- ブラウザ側（`/videos`）: 上記2段 + Object Storage への直接 PUT。進捗表示。
  複数ファイルは順に処理する
- 既存の `POST /api/video/assets`（multipart）は**小さい映像用に残す**か、
  廃止するなら理由を書く。残すなら**上限を実測値に合わせて下げ、413 の理由を利用者に見せる**
  （いまは「file too large (max 500MB)」と出るが実際は 20MB 未満で落ちる＝**嘘の案内**）
- `uploading` のまま放置された asset の回収（既存の `reap_orphan_assets` に寄せる）

## 完了条件（検証可能な形で）
- **実機（配備済みゲートウェイ経由）で 100MB 超の映像を登録できる**こと。証跡に実サイズを記す
- 途中で中断した場合に `uploading` が残り、回収されること
- 検証に落ちる細工（サイズ 0・別 Content-Type・PAR の使い回し）を弾くこと
- 単体テスト: PAR の期限・スコープ、complete の検証、中断時の扱い
- make lint 緑・make test 緑・codex-review PASS

## 成果物
コード / `docs/verification/VID-01.md` に追記（ゲートウェイ上限の実測を含む）

## 禁止事項
- **PAR を読み書き両用・長命にすること**（アップロード用は書き込み専用・短命・オブジェクト単位）
- 上限の案内を実態と違う値のままにすること
- 実 ADB で通常フロー外の DROP を打つこと
