# タスク: TOOL-03 外部HTTPツールの引数に入れ子・繰り返しを持たせる

## 目的
**外部HTTPツールの引数が平坦なスカラーに限られており、入れ子・配列を持つ業務 API を登録できない。**

TOOL-01 の `validate_parameters` は `ALLOWED_PARAM_TYPES = ("string","number","integer","boolean")`
のみを受理する。企業の業務 API は**入れ子のオブジェクトと配列が普通**であり、
実案件のデモでは **8 本中 6 本が登録すらできない**。

このデモの趣旨は「**SoR の API 仕様が複雑すぎるので、AI に仕様書を読ませて正しく呼べるかを確かめる**」
ことである。JetUse が複雑なボディを表現できないと、**複雑な API ほど渡せない**という逆転が起きる。

## 実環境で確認した事実（推測ではない）
```
入れ子オブジェクト → 400 「引数 <名> の type は string/number/integer/boolean のいずれかです」
配列              → 400 同上
平坦なスカラーのみ → 200 登録できる
```

| 相手の API | 必要な形 | 現状 |
|---|---|---|
| 受付可否 | スカラー 1 個 | 登録できる |
| 注文コンテキスト初期化 | スカラー 2 個 | 登録できる |
| 契約者情報設定 | オブジェクト 1 段 | **不可** |
| お届け予定日取得 | オブジェクトの配列 + スカラー | **不可** |
| 受取方法設定 | オブジェクト 1 段 + スカラー | **不可** |
| 商品設定 | オブジェクトの配列 | **不可** |
| サービス情報設定 | **配列の中に配列**（2 段） | **不可** |
| 分割払い情報設定 | オブジェクトの配列 + スカラー | **不可** |

## 決まっていること（2026-08-02 人間ゲートで承認済み。作り直さない）

**入れ子オブジェクトと配列を宣言できるようにする。ただし「検証しきれる形しか通さない」方針は変えない。**

現状の設計意図は正しい — 未対応の JSON Schema キーワードを素通しすると
「**モデルには制約に見えるが、実行前検証は何もしていない**」状態になり、その方が危険である。
したがって **入れ子・配列も、実行時に同じ強さで検証できる形でだけ**受理する。

## 作業内容
- `validate_parameters` を再帰にする。受理する型を `object` / `array` へ拡張する。
  - `object` は `properties` を持つこと（自由形式の object は受理しない＝検証できないため）。
  - `array` は `items` を持つこと。`items` は単一スキーマのみ（tuple 形式は受理しない）。
  - 各階層で**検証できるキーだけを残す**現状の方針を維持する（未対応キーワードは落とす）。
- `_validate_args`（`tools.py`）を再帰にする。**宣言と実際の入力の強さを一致させる**。
  - 未知キーの拒否・型検査を各階層で行う。`required` も各階層で効かせる。
  - 配列は要素ごとに `items` で検査する。
- **上限を設ける**（`MAX_TOOLS_PER_AGENT` と同じ流儀で定数化。際限なく複雑なものは断る）:
  - 入れ子の**深さ**の上限
  - スキーマ全体の**ノード数**の上限
  - 配列の**要素数**の上限（実行時。宣言時ではない）
  - 既存の `MAX_PROPERTIES` は各階層に効かせる
- 上限超過は**宣言時に 400**、実行時の要素数超過は**ツール実行の失敗**として返す（切り詰めない）。

## 判断を上げること（実装せず ADR に書いて止める）
- 上限値そのもの（深さ・ノード数・配列要素数）を**いくつにするか**は、
  実際の業務 API の形（2 段の入れ子が実在する）を根拠に提案し、判断を上げること。
  「足りないから上げる」を繰り返さないよう、**根拠のある値**にする。

## 非ゴール / 禁止事項
- JSON Schema の全機能に対応しない（`oneOf` / `allOf` / `$ref` / `pattern` / `enum` 等は**対象外**）。
  **検証できないものを受理しない**という現行方針を維持する。
- 自由形式の（`properties` を持たない）オブジェクトを受理しない。
- 既存の SSRF 防御・秘密の扱い・TOOL-02 のヘッダ検証を**緩めない**。
- **顧客名・案件名を書かない**（公開リポジトリ）。認証情報・OCID をコミットしない。
- IAM を変更しない。未承認のコミット / PR / push を行わない（人間ゲート）。
