# タスク: PREP-04 1セルが上限を超える xlsx を取り込めるようにする（セル内分割）

## 目的
**1つのセルに上限（2,000 文字）を超えるテキストが入っている xlsx が、丸ごと取り込めない。**
実案件の仕様書で発生し、**8 冊中 2 冊が取り込み不能**になった。

PREP-01 は「上限を超えたら**行境界で分割**する（分割は切り詰めではない）」と設計したが、
**1 行そのものが上限を超える**場合は分ける場所が無く、`422 limit=chunk_chars` で
**ファイル全体を拒否**する。影響が「一部が欠ける」ではなく「**そのファイルが入らない**」なので重い。

## 実データで確認した事実（推測ではない）
| 事実 | 値 |
|---|---|
| 失敗したファイル | 2 冊（いずれも「サンプル」シート） |
| 超過していた行 | 13,728 文字 / 13,288 文字 |
| その行の非空セル数 | **1 個**（`A53` に 13,728 文字。API のリクエスト例が丸ごと 1 セルに入っている） |

→ **セル境界では割れない。**「行で分ける」「セルで分ける」のどちらでも解決しない。

## 決まっていること（2026-08-02 人間ゲートで承認済み。作り直さない）
**セルの中で分割する。** 上限の引き上げも、長いセルの読み飛ばしも**採らない**。

- 引き上げ: もっと長いセルが出れば同じ問題。検索単位も粗くなり根拠の絞り込みが効かなくなる
- 読み飛ばし: **黙って中身が欠ける**。「取り込めている」と思っているのに入っていない状態を作る

元の設計意図は「黙って切り捨てない」であり、**分割は切り捨てではない**（中身は全部残る）。
**分ける場所が無いなら作る**、が本タスク。

## 作業内容
- `extract_xlsx` で、1 セルの値が上限を超える場合に**そのセルの中で分割**する。
  - 切る位置は**意味の切れ目を優先**する（改行 → 区切り文字 → 最後の手段として文字数）。
    JSON / XML のサンプルが 1 セルに入っている実例があるので、改行での分割が効くはず。
    **ただし「きれいに構造を解析する」ことは目指さない**（レイアウト解析は非ゴール）。
  - 分割した各断片には、**元のセルと同じ出典**（`sheet` / `cells`）を付ける。
    どの断片も「そのセルが根拠」であることは正しいので、**出典の精度は落ちない**。
  - `chunk_id` は断片ごとに一意にする（既存の採番規則に従う）。
- **上限の意味を変えない**: 総チャンク数・ブック全体のバイト数の上限は据え置き。
  それらを超えたときは従来どおり **422 で拒否**する（切り詰めない）。
- 分割が発生したことを、**利用者が気づける形にする**か決めて実装する
  （例: 応答に分割件数を出す）。**黙って分割して終わりにしない**方が望ましいが、
  API 契約を変えるなら判断を上げること。

## 非ゴール / 禁止事項

- **顧客の実ファイルを使わない・持ち込まない。** 同じ形（1 セルに巨大テキスト）の**架空ファイル**で検証する。
