# タスク: PREP-02 Select AI バックエンドと xlsx の実機確認（推測で「使えない」と書かない）

## 目的
PREP-01 で `.xlsx` を許可した結果、**Select AI バックエンドだけ挙動が異なる**。
現状は `jetuse_core/rag.py:510` が **拡張子だけを根拠に恒久 `error`** としており、
**実機・一次資料の裏付けが無い**（review-7 PREP01-004・`SKIPPED.md` §2）。

推測でユーザーに「使えない」と表示している状態を解消する。
実機で確かめ、**確かめた結果を根拠に**判定と表示を確定させる。

## 前提（依存タスク / 人間の事前作業）
- PREP-01 がマージ済み（済）。

  `ops/setup-select-ai.py`（RP-01 でリソースプリンシパルへ統一済み）。

## 背景（なぜ挙動が違うか）
他のバックエンドは**アプリ側が抽出したテキスト**を取り込む。
Select AI は `DBMS_CLOUD_AI.CREATE_VECTOR_INDEX` が**バケットの原本を DB 側パイプラインで直接読む**ため、
アプリ側の抽出（`extract_xlsx`）を通らない。したがって xlsx の扱いは
**OCI 側パイプラインが xlsx をどう扱うか**に依存し、アプリからは決められない。

## 作業内容
### 1. 実機で確かめる（推測を排する）
- 架空の xlsx を Select AI の索引対象バケットに置き、索引を作って**実際にどうなるか**を観測する。
  最低限、次を実行結果として記録する:
  - 索引作成が成功するか／エラーになるか（**エラーコードと本文をそのまま**）
  - 索引に取り込まれた場合、`$VECTAB` に**何が入るか**（本文がテキストとして読めているか、
    バイナリのゴミが入っているか、そもそも行が作られないか）
  - 検索したときに何が返るか
- 一次資料（`docs.oracle.com`）に xlsx の対応可否の記載があるかを確認し、**あれば URL を引く**。
  無ければ「一次資料に記載なし・実測のみ」と明記する。

### 2. 結果に応じて判定と表示を確定させる
観測結果は 3 通りありうる。**どれになるかは実機が決める**ので、事前に決め打ちしない。

| 観測結果 | 実装 |
|---|---|
| 索引作成が失敗する | 恒久 `error` の判定は正しい。**根拠（実行結果）を添えて**理由文言を実測に合わせる |
| 索引はできるが本文が壊れる | `error` ではなく「取り込めるが内容が壊れる」旨の**正確な表示**にする。誤解を招く文言にしない |
| 正常に扱える | **恒久 `error` を撤回する**。他バックエンドと同様に扱えるようにする |

- どの結果でも、**表示文言は実測に基づくものだけ**にする。「対応していません」と断定するなら、
  その根拠が `docs/verification/PREP-02.md` から辿れること。

### 3. 抽出テキストを供給する案の検討（実装は結果次第）
Select AI にも抽出テキストを供給する道（原本と併せて `.xlsx.txt` をバケットへ置く等）が
考えられるが、**索引の対象範囲・重複取り込み・削除時の整合**に影響する。
実装するかどうかは §1 の結果を見てから判断し、**やらない場合も理由を記録**する。
判断が割れる場合は実装せず、選択肢と影響を書いて人間ゲートへ上げる。
