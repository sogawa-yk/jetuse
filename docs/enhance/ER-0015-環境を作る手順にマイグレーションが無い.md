## ひとことで

配備しても DB のテーブルが作られず、機能が動かない。手順のどこにも書かれていない。

## 何が起きたか

2026-08-04、Internal リリース点を配備して E2E を取ろうとしたところ、
`GET /api/demos` が **503 `database unavailable`** を返した。デモ基盤（SP1〜SP3）が動かない。

原因は**内部固有 migration（`017_demos_v2` 以降）が個人スキーマに未適用**だったこと。

- **`make deploy DEV=<名>` は migration を流さない。** `ops/dev-env-up.sh` にも
  `ops/deploy-dev-app.sh` にも該当処理が無い
- `docs/guides/dev-environments.md` は `ops/setup-dev-schema.py` に触れているが、
  **既存スキーマに対して後から migration を流す手順が無い**

## さらに踏んだ落とし穴

`python -m jetuse_core.migrate` は **実行している checkout の `migrations/` ディレクトリ**を見る。

```
main の checkout から実行     → 適用 0 件（内部固有の 017 以降がそもそも存在しない）
internal-dev の checkout から → 適用 11 件
```

**`main` から流すと黙って 0 件で終わる。**エラーも警告も出ないので、
「流したのに動かない」という状態になる。これで時間を溶かした。

## 根拠（実測 2026-08-04）

```
接続先 DB=..._JETUSEDEV  USER=JETUSE_SOGAWA
適用: 11 件
  + 017_demos_v2  018_demos_idx_owner  019_demos_idx_visibility
  + 020_conversations_demo_id  021_conversations_idx_demo  022_demo_backend_targets
  + 023_dbt_idx  024_rag_files_filename_char
  + 025_builder_sessions  026_builder_sessions_idx  027_builder_sessions_sufficient
```

適用前 `/api/demos` = 503 → 適用後 = 200。**適用が状態を変えたことが、必要だった証拠。**

証跡: `runs/2026-08-04T1832_FINISH-4/e2e/demo-platform/README.md`

## どう直すか

**(a) 手順に書く（最小）**
`docs/guides/dev-environments.md` に「Internal 機能を使う環境では internal 系の checkout から
migration を流す」を明記する。checkout 依存であることも書く。

**(b) 流し忘れを検知する（推奨）**

素朴に「`migrations/` にある版 と `schema_migrations` の差分」を見るだけでは**今回の原因を
検出できない**。`main` の checkout には内部固有 migration が**そもそも存在しない**ので、
DB も `main` も 016 までなら差分 0 で正常終了してしまう。

検出するには「**いま居るブランチが、そのDBを使う版として正しいか**」を見る必要がある。

- **案1: DB 側に「どの系統か」を記録する。** `schema_migrations` とは別に、
  適用時のブランチ系統（public / internal）を残す。`main` から internal 用の DB へ流そうと
  したら「このDBは internal 系。いま public 系の checkout に居る」と警告する
- **案2: 期待する migration 一覧を DB に持たせる。** 最後に適用した checkout の
  migration ファイル名一覧を保存し、次回それより少ない一覧で流そうとしたら警告する
  （`main` から流すと「前回は 027 まであったのに今回は 016 までしか無い」と分かる）
- **案3（最小）: 適用0件のときに、DB の最新版と checkout の最新版を並べて出す。**
  自動判定はしないが、`DB=027 / checkout=016` と表示されれば人が気づける

**案3 が最小で効果的**。案1・2 は状態を増やすので、まず案3 で足りるか見る。

**(c) 配備に組み込む**
`ops/dev-env-up.sh` / `ops/deploy-dev-app.sh` に migration の実行を足す。
ただし ADB への接続情報が必要で、配備スクリプトの前提が増える。**(a)+(b) を先にやるのが妥当。**

## やらない場合の代償

新しい開発環境を作るたび、あるいは Internal 機能を触るたびに同じところで詰まる。
症状（503）から原因（migration 未適用・checkout 依存）に辿り着くのに時間がかかる。
