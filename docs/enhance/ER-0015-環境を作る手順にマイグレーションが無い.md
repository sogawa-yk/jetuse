## ひとことで

配備しても DB のテーブルが作られず、機能が動かない。手順のどこにも書かれていない。

## 何が起きたか

2026-08-04、Internal リリース点を配備して E2E を取ろうとしたところ、
`GET /api/demos` が **503 `database unavailable`** を返した。デモ基盤（SP1〜SP3）が動かない。

原因は**内部固有 migration（`017_demos_v2` 以降）が個人スキーマに未適用**だったこと。

- **`make deploy DEV=<名>` は migration を流さない。** `ops/dev-env-up.sh` にも
  `ops/deploy-dev-app.sh` にも該当処理が無い

- `docs/guides/dev-environments.md` は `ops/setup-dev-schema.py` に触れているが、
  **既存スキーマに対して後から migration を流す手順が無い**

**追記（2026-08-06 の調査）**: 「どこにも無い」のではなく、**経路によって在ったり無かったりする**。
これが「配備すれば流れるはず」という思い込みの正体だった。

| 経路 | migration | 仕掛け |
|---|---|---|
| ORM ワンクリック配備（一般利用者） | **流れる** | `infra/orm/locals.tf` が `RUN_DB_BOOTSTRAP=true` を渡し、`entrypoint.sh` が `jetuse_core.bootstrap` を起動する |
| `ops/setup-dev-schema.py`（開発者の**初回**） | **流れる** | 末尾で `python -m jetuse_core.migrate` を実行する |
| `ops/dev-env-up.sh` / `ops/deploy-dev-app.sh` | **流れない** | `environments/app` が `RUN_DB_BOOTSTRAP` を設定しない |

`RUN_DB_BOOTSTRAP` の設定箇所はリポジトリ全体で `infra/orm/locals.tf` の1か所だけ。
**一般利用者の環境は自動で migrate され、開発者の環境だけ初回しか migrate されない**という
非対称になっていた。

## さらに踏んだ落とし穴

`python -m jetuse_core.migrate` は **実行している checkout の `migrations/` ディレクトリ**を見る。

```
main の checkout から実行     → 適用 0 件（内部固有の 017 以降がそもそも存在しない）
internal-dev の checkout から → 適用 11 件
```

**`main` から流すと黙って 0 件で終わる。**エラーも警告も出ないので、
「流したのに動かない」という状態になる。これで時間を溶かした。

## 根拠（実測 2026-08-04）

```
接続先 DB=..._JETUSEDEV  USER=JETUSE_SOGAWA
適用: 11 件
  + 017_demos_v2  018_demos_idx_owner  019_demos_idx_visibility
  + 020_conversations_demo_id  021_conversations_idx_demo  022_demo_backend_targets
  + 023_dbt_idx  024_rag_files_filename_char
  + 025_builder_sessions  026_builder_sessions_idx  027_builder_sessions_sufficient
```

適用前 `/api/demos` = 503 → 適用後 = 200。**適用が状態を変えたことが、必要だった証拠。**

証跡: `runs/2026-08-04T1832_FINISH-4/e2e/demo-platform/README.md`

## どう直したか

### 最初の実装は的を外していた（記録として残す）

`schema_migrations` は version をファイル名で記録しているので、**DB − checkout** を取れば
「この DB は、いまの checkout に無い migration を持っている」と分かる。新しい状態を足さずに
済むので、これで塞いだつもりでいた。

**塞がっていない。** Codex レビューが blocker で指摘した。実害時の状態は

```
DB       = Public 集合（017_demos_v2 以降は未適用）
checkout = Public 集合（main）
```

で、**DB − checkout も checkout − DB も 0**。この2つを見比べる限り、何をどう引いても
差は出ない。**どちらの側にも「この環境は Internal を要求している」と書かれていない**からだ。

起票時の3案（系統を DB に記録 / 期待する一覧を DB に持たせる / 版を並べて出す）も、
同じ理由でどれも実害を検出できない。3案とも「DB と checkout」の2者しか見ていない。

### 三人目がいた — 動いているイメージ

要求を知っているのは**配備されたコンテナイメージ**だった。Internal 版のイメージは
Internal 固有 migration を同梱している。だから

```
pending = イメージが持つ migration − DB に適用済みの migration
```

が空でなければ、そのアプリは**必要な表の無い DB に向いている**と確定する。実害時はこれが 11 件。

置き場所は `/api/health`。ランナー（`migrate`）に置いても意味が無い —— ランナーにとって
pending はこれから適用するものだからだ。**見るべきなのは「流す人」ではなく「流されないまま
動いているアプリ」の側。**

| | |
|---|---|
| 判定 | `pending_versions(db, image) = sorted(set(image) - set(db))` |
| 出す場所 | `GET /api/health` の `schema`（`ok` / `behind` / `foreign` / `unknown`） |
| `ok` への影響 | `behind` なら全体の `ok` を **false** にする。未適用があるのに ok=true と言うのが、まさに人を迷わせた嘘 |
| 副作用 | 無し。`applied_versions()` は読むだけで、`schema_migrations` を作りもしない |

### ランナー側にも別の取り違えがあった

**DB − checkout**（最初に作ったほう）は無駄ではない。Internal で育てた DB を Public 系の
checkout から流そうとした場合を捉える。実害とは**逆向き**の取り違えなので、両方残した。

- `migrate()` は適用の**前**に警告する（適用 0 件で終わる経路こそ読ませたい）
- CLI は `logging.basicConfig` で素の1行にして stderr へ。JSON ログでは人が読まない
- CLI の「up to date」という断定をやめた。**その断定こそが本件の誤解を再生産する**

### 手順

(a) `docs/guides/dev-environments.md` に「マイグレーションを後から流す」節を追加。
経路ごとに流れる/流れないを表にし、`/api/health` での確認、後から流すコマンド、checkout 依存、
503 の切り分け順を書いた。E2E 検証の「503ならDB/スキーマ未整備」も、ADB 停止（[[ER-0018]]）と
紛れるので書き直した。

回帰テストは `packages/api/tests/test_health_schema.py`（12件）と
`test_migrate_foreign_schema.py`（23件）。**集合を実行中の checkout から推定しない**ので、
public / internal どちらの checkout でも同じ結論を出す（sync 後に CI が壊れない）。

## やらなかったこと

**(c) 配備に組み込む**（`ops/dev-env-up.sh` に migration 実行を足す）は入れていない。
ADB の接続情報が配備スクリプトの前提に加わるため。起票時の判断（(a)+(b) を先に）を踏襲した。
検出できるようになったので、**次に踏んだら別 ER として起票する**。

## 検証

**実 OCI で検証済み。** 当初は「配備しても新しく動く経路が無い」として実機を省いたが、これは誤り
（Codex review-4 の blocker）。`/api/health` は毎リクエスト実 DB の `user_tables` と
`schema_migrations` を読む。対象 ADB は `jetuse-loop-adb`（ap-osaka-1・`.env` の指す先。
この検証のため STOPPED から起動）。

| | 内容 | 結果 |
|---|---|---|
| シナリオ7 | 実 Oracle を読む / **非 DDL** / `call_timeout` | 21 件を 2.7s。診断を3回まわしても `user_tables` 21→21・`schema_migrations` 21→21。`call_timeout=10000` |
| シナリオ8 | `ok` / `behind` / `foreign` を実 DB のまま出す | 3状態とも再現。**DB は前後で不変** |
| シナリオ9 | HTTP ルート込みで `GET /api/health` | **200 / 3.58s**・`schema={"status":"ok","applied":21,"expected":21}` |

**共有スキーマを壊さずに `behind` を出せた。** ER-0015 は「DB は据え置きでイメージだけ先に進んだ」
状態なので、動かすべきは DB ではなくイメージ側だった。`migrations/` に1本足せば `behind`、
1本外せば `foreign` が実 DB を読んだまま再現する。`jetuse-spike-` スキーマを作る必要も無い。

ローカル側:

| | 内容 |
|---|---|
| シナリオ1 | 単体 35 件（health 12 / ランナー・判定 23） |
| シナリオ2 | **変異検査 5 種**。`pending` を殺す→5件 FAIL / `ok` に効かせない→1件 / ランナー警告を消す→4件 / 差の向きを反転→12件 / `call_timeout` を張らない→1件 |
| シナリオ3 | CLI を**別プロセスで起動**して stderr を確認 |
| シナリオ4 | 実ブランチの migration 集合を照合（`internal-dev` ⊃ `public-dev`・差分 11 本・public 専用 0 本） |
| シナリオ5 | `RUN_DB_BOOTSTRAP` の設定箇所を全リポジトリで数え、非対称を確認 |
| シナリオ6 | **internal-dev 相当の checkout を実際に作って**（`checkout_versions()` が 21→32）テストが通ることを確認 |

記録は `runs/2026-08-06T_ER-0015-MIGRATE/e2e/`（`SKIPPED.md` にレビュー4巡で潰した点も含む）。

**副産物**: 検証にあたり **ADB が3つとも STOPPED** だった。[[ER-0018]] が現在進行形であることの追加証拠。

## 学び

**「何が足りないか」を知っているのは誰か、を先に決める。** 最初の実装は DB と checkout の
2者だけを見比べ、差の向きを変えれば解けると思い込んでいた。実際にはその2者のどちらも
要求を知らず、知っていたのは**三人目（配備されたイメージ）**だった。差の取り方をいくら
工夫しても、要求を持たない者どうしを比べている限り答えは出ない。

同じ形が [[ER-0021]] にもある（worktree を見る道具が、worktree に現れない残作業に盲目だった）。
どちらも**判定ロジックではなく、見ている対象の選び方**が誤りだった。
