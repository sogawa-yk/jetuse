## ひとことで

「やりかけを取りこぼさない」ための一覧が、**安定枝へ出していない分**を1行も出していなかった。
一番大きな残作業が、それを見つけるための道具から漏れていた。

## 何が起きたか

2026-08-06 時点で `public-dev` は `main` より **16 commit** 先行し、`internal-dev` は
`internal-stable` より **10 commit** 先行していた。どちらも release PR は出ていない。
つまり **4ブランチ体制への移行・OCID 漏洩検査・Containerfile のレイヤ分割（再ビルド 42分→82秒）
まで、誰にも届いていない**状態だった。

にもかかわらず `ops/stalled.py` の出力は `API-01`（意図的に止めているもの）1行だけで、
Obsidian の ER 一覧の「止まっている作業」も「放っておくと問題になるものはありません。」と
表示していた。

## なぜ漏れたか

`stalled.py` は **worktree を走査する**道具で、取り込み済みかどうかを
「4長期ブランチ（`main` / `public-dev` / `internal-dev` / `internal-stable`）のどれかに
入っているか」で判定していた。

```python
merged = f"origin/{branch}" in merged_long   # どれか1つに入っていれば「取り込み済み」
```

この判定自体は正しい。`main` だけを基準にすると、開発枝へ入れただけの作業が
「未出荷」に見え続けてしまうからだ（そう直した経緯がコメントに残っている）。

問題は**その先**にある。開発枝へ merge した瞬間にその作業は一覧から消えるが、
**安定枝へ出す作業は誰の worktree にも現れない**。長期ブランチ間の遅れは、
worktree を何度走査しても構造的に見つからない。

## どう直したか

`_release_lag()` を足し、`origin/<stable>..origin/<dev>` を直接数えるようにした。

| | |
|---|---|
| 対象 | `public-dev`→`main` と `internal-dev`→`internal-stable` の2組 |
| 状態 | release PR が無ければ `unreleased`（**要注意**側）。出ていれば `pr` に落とす |
| 日数 | **一番古い未リリース commit からの経過**。直近 commit を見ると、溜め続けるほど「昨日動いた」に見えて遅れが隠れる |
| `main` の場合 | 「merge すると公開配信物が差し替わる」を文面に含める |

worktree ディレクトリが無い環境でも返るよう、`LOOPS` の早期 return より前に積んでいる。

回帰テストは `packages/api/tests/test_stalled_release_lag.py`（42件）と `test_er_stalled_rows.py`（11件）。使い捨ての git
リポジトリを作って検査するので、実リポジトリの状態に依存しない。

初版は Codex レビューで blocker 1 / major 2 / minor 1 を受けて直した。

| 指摘 | 直した内容 |
|---|---|
| `origin/*` が古いと嘘をつく | 判定前に `git fetch` し、失敗したら**文面に「古い可能性がある」を出す**（黙って古い判定を見せない） |
| head だけで release PR を判定 | `base` も一致を見る。**実在した #155**（`head=public-dev` / `base=internal-dev` の同期 PR）で `main` への未リリースが消えていた |
| `gh` の失敗を「PR 無し」と同一視 | 取得失敗は `None` として `unknown` に落とす。`--limit 200` も指定（既定 30 件で取りこぼす） |

その修正版も major 2 / minor 1 を受け、さらに直した。

| 指摘 | 直した内容 |
|---|---|
| `subprocess` の例外が伝播する | `TimeoutExpired` / `OSError` を捕まえる。**オフラインや `gh` 未導入で `ops/er.py report` ごと落ちていた**（[[ER-0020]] と同じ「無音で使えなくなる」形） |
| `--limit 200` に達したら誤表示 | 上限に達したら `None`＝**取りこぼした可能性がある以上「PR は無い」と言えない** |

テスト側にも欠陥があった。`mod.subprocess.run = ...` は**本物の `subprocess` モジュールを
書き換える**ので、テストファイル自身の `_git()` まで壊れ、後続5件が
`FileNotFoundError` で落ちた。`monkeypatch.setattr` へ直して復元されるようにした。

さらに2巡し、**「確認できない状態を『問題なし』として黙る」経路**を潰し切った。

| 指摘 | 直した内容 |
|---|---|
| ref が1本でも欠ければ黙ってスキップ | `unknown` として**行を残す**。single-branch clone では `fetch` しても ref が増えず、恒久的に消えていた |
| shallow clone を完全な履歴として数える | `--is-shallow-repository` を見て `unknown` に落とす |
| fetch 失敗＋古い ref で差ゼロだと**行ごと消える** | 「差は無いが、取得できておらず無いとは言えない」と出す |
| `git fetch origin` は refspec 外のブランチを**更新せず成功**する | `+refs/heads/<b>:refs/remotes/origin/<b>` を4本明示して発行する |
| `_git()` が失敗を `""` に潰し、`rev-list` の失敗が 0 件になる | 失敗を `None` で返す `_git_out()` を分け、数える系はこちらを使う |
| git 自体を起動できないと「ref が手元に無い」と**誤った理由**を出す | 先に検出して「`git` を実行できず」と正しく言う |
| fork の同名ブランチからの PR を release PR と誤認 | `isCrossRepository` で弾く |
| `gh` が想定外の JSON を返すと例外が外へ飛ぶ | 形（list of dict）まで確かめて `None` に落とす |
| 鍵の欠けたレコードで `scan()` が `KeyError` | 要る鍵まで検証し、呼び出し側も欠落を飛ばす |
| `gh` の値の**型**が想定外だと誤判定・例外 | `headRefName: []` や `isCrossRepository: "false"` を型で弾く |
| 検出を直してもレポート表示側にテストが無い | `test_er_stalled_rows.py` を追加。`unreleased` が**要注意側**に出ることと日本語表示を固定。`stalled.RANK` を定数化し、状態を足したとき生の英単語が表に出ないことを照合する（`clean` の表示欠落が実際に見つかった） |

## 学び

**取りこぼしを見つけるための道具は、「何を見ていないか」を定期的に疑う必要がある。**
この道具は「worktree を見る」と決めた時点で、worktree に現れない残作業に対して盲目だった。
判定ロジックはどれも正しく、レビューも通っていた。**個々の判定が正しくても、
入口が狭ければ全体は嘘になる。**
