## ひとことで

コンテナのビルド設定を決める場所が2つあり、片方だけ直した状態になっている。

## 何が起きているか

2026-08-04 に配備が2回壊れ、その対策を `ops/dev-env-up.sh` と `ops/deploy-hosted-agent.sh` に
入れた（PR #139 / #144）。しかし **`ops/deploy-dev-app.sh`（Internal 共有プレビューの配備）には
入っていない**。

| 対策 | `dev-env-up.sh` | `deploy-hosted-agent.sh` | `deploy-dev-app.sh` |
|---|---|---|---|
| エンジン解決を `ops/_container.sh` に統一 | ✅ | ✅ | ❌ 独自の `CONTAINER_TOOL`（23行目） |
| `--platform linux/amd64` の固定 | ✅ | ✅ | ❌ 無し（72行目） |

`deploy-dev-app.sh` はヘッダで「**ローカル検証とワークフローが同一手順**」と謳っており、
ローカル実行を想定している。CI（ubuntu / x86）では素の build でも amd64 になるため露見しないが、
**Apple Silicon から実行すると arm64 イメージができ、Container Instance が弾く**。

## 根拠

実測（2026-08-04・PR #144 の証跡）:

```
Error Message: work request did not succeed ... entity: containerinstance, action: CREATED.
Message: A container image provided is not compatible with the processor architecture
         of the shape selected for the container instance.
```

しかも `image_url` の変更は Container Instance の**置換**になり、terraform は旧インスタンスを
先に削除する。作成に失敗すると**環境が落ちたまま復旧できない**（実際に踏んだ）。

`deploy-dev-app.sh` の該当箇所（`origin/internal-dev`）:

```
23: CONTAINER_TOOL="${CONTAINER_TOOL:-$(command -v podman >/dev/null 2>&1 && echo podman || echo docker)}"
72: "${CONTAINER_TOOL}" build -f packages/api/Containerfile -t "${image}" .
```

## どう直すか

1. `. "$(dirname "$0")/_container.sh"` を読み込み、`CONTAINER_TOOL` を `jetuse_container_engine` に置き換える
   （どちらも無ければ落とす挙動を揃える）
2. `build` に `--platform "${JETUSE_BUILD_PLATFORM:-linux/amd64}"` を渡す
3. 既存の回帰テスト `packages/api/tests/test_build_platform.py` の `SCRIPTS` に
   `ops/deploy-dev-app.sh` を足す（4つの検査がそのまま効く）

## 起点の判断が要る

`deploy-dev-app.sh` は **`internal-dev` にしか無い**が、`ops/internal-only-paths.txt` には
載っていない。そのため起点検査（`ops/check-branch-base.sh`）は共有物として扱う。

- **一覧に足す**なら `internal-dev` 起点で直せる
- **足さない**なら、このファイルを `public-dev` にも置く必要がある

「Public 版に出しても差し支えないか」で決める（ADR-0028）。**Internal 共有プレビュー専用の
配備スクリプトなので、一覧に足すのが筋**だと考えるが、判断が要る。

## やらない場合の代償

Apple Silicon から `ops/deploy-dev-app.sh` を実行すると、共有プレビュー環境（`jetuse-dev-app`）を
落としたまま復旧できなくなる。**個人スタックと違い共有なので影響が大きい。**
