## ひとことで

CI のコンテナビルドが、毎回ゼロから依存をインストールしている。

## 何が起きているか

PR #151 で `Containerfile` のレイヤを分割し、**ローカルの再ビルドは 42分 → 82秒**になった。
依存層がキャッシュされるようになったため。

**CI にはこの恩恵が届いていない。** GitHub Actions は既定でレイヤキャッシュを保持しないので、
`release.yml` も `deploy-dev.yml` も毎回ゼロから依存を入れている。

| ワークフロー | 現状の所要 | 内訳（推定） |
|---|---|---|
| `release.yml`（Public 配布） | 13〜14分 | 大半が依存インストール |
| `deploy-dev.yml`（Internal） | 7〜11分 | 同上 |

## 根拠

実測（2026-08-05・amd64）:

```
依存のインストール      2519秒
自パッケージのインストール  83秒
```

依存が全体の **97%** を占める。CI はネイティブ x86 なので絶対値は小さいが、比率は同じはず。
**この比率は推定**（CI 内で層ごとの時間を計っていない）。

`release.yml` は **`docker/build-push-action` を5回**実行する（`jetuse-api` / `jetuse-fn-router` /
`jetuse-agent-{openai,langgraph,adk}`）。**リージョンごとの再ビルドではなく、1回のビルド結果に
複数リージョンのタグを付けて push する**構造。push 先は API / fn-router が4リージョン
（kix / nrt / iad / ord）、agent 3種が2リージョン（kix / ord）。

したがって**削減対象はビルド5回分**であり、リージョン数は効かない。

## どう直すか

`docker/build-push-action` に GitHub Actions cache を渡す。

```yaml
cache-from: type=gha,scope=<イメージごとに変える>
cache-to: type=gha,mode=max,scope=<イメージごとに変える>
```

**`scope` をイメージごとに分けることが必須。** 既定では全 build が同じ `scope=buildkit` を
使うため、5回の build が互いのキャッシュを上書きし、最後の1つ以外は効かなくなる
（[Docker の公式ドキュメント](https://docs.docker.com/build/cache/backends/gha/)も
複数イメージでは scope を分けるよう指示している）。

**確認すべき点**:
- GHA cache の容量制限（リポジトリあたり10GB）。**scope を5つに分けるので、
  1つあたり2GB に収まるか**。依存層は 780MB のイメージのうち大半を占めるため、
  超える可能性がある。溢れると古いものから追い出され、ヒット率が落ちる
- 依存層が変わらない限りヒットするか（`pyproject.toml` / `jetuse_shared/` の変更頻度は
  直近90日で4回なので、ヒット率は高いはず）
- **キャッシュ汚染で古い依存が使われないか**。`mode=max` は中間層も保存するため、
  誤ったキャッシュヒットが起きないことを確認する
- `jetuse-agent-*` は `packages/agent-containers/Containerfile.*` を使う。こちらは
  **元から正しい順序**（`requirements.txt` → 依存 → ソース）なので、キャッシュを渡せば
  そのまま効くはず

## やらない場合の代償

Public リリースのたびに13〜14分待つ。頻度が上がると効いてくる。
**急ぎではない**（現状で困っていない）。
