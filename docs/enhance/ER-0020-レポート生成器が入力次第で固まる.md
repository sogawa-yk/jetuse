## ひとことで

`ops/er.py report` が10分以上応答しなくなった。原因は Markdown 変換の無限ループで、
**引き金は ER ファイルの書き方**だった。書き手が踏める地雷が生成器側に残っていた。

## 何が起きたか

2026-08-04 に ER-0014〜0019 を追加したあと、Obsidian 側の一覧（`_renders/ER/index.md`）が
更新できなくなった。詳細 HTML は生成されるのに index が古いまま（全13件で止まる）で、
プロセスは終了せず居座り続けた。書き込み先が OneDrive なので同期待ちを疑ったが、
1ファイル書き込みは0秒、`_stalled_rows()`（`gh pr list` を叩く）も2.1秒で、どちらも無罪だった。

`faulthandler.dump_traceback_later()` でスタックを取って確定した:

```
File "ops/er.py", line 151 in _md
File "ops/er.py", line 217 in _detail_html
```

`_md()` の段落分岐は**継続条件だけ**でループを回していた。

```python
buf = []
while i < len(lines) and lines[i].strip() and not lines[i].startswith(("#", "|", ">")) ...:
    buf.append(lines[i].strip()); i += 1
```

`|` で始まる行に来ると、まず表の分岐が「次の行が `|---|` 区切りか」を見る。区切りでなければ
表として扱われず段落分岐へ落ちるが、段落の継続条件は `not lines[i].startswith("|")` なので
**即 false**。`buf` は空、`i` は進まない。外側の `while i < len(lines)` が同じ行を延々と回す。

引き金は自分が書いた `docs/enhance/ER-0012-*.md` の表で、1行に収めるべきセルを
**3行に折り返して**書いていた。Markdown としては壊れているが、書き手が普通にやる間違いである。

## なぜ気づきにくかったか

- **失敗ではなく無音**。例外も終了コードも出ず、ただ返ってこない。
- **部分的に成功する**。詳細 HTML 19件は先に書き終えているので、出力先を見ると
  「新しい ER の HTML はある」＝生成は動いたように見える。壊れているのは index だけ。
- **疑う先が外にある**。書き込み先が OneDrive、`_stalled_rows()` が `gh` を叩くので、
  「同期待ち」「ネットワーク待ち」を先に疑って時間を使った。実際はどちらも無関係。

## どう直したか

| 直したもの | 内容 |
|---|---|
| 生成器 | 段落分岐で**1行目を無条件に取り込んで `i` を進める**。継続条件だけに依存しない |
| データ | ER-0012 の折り返した表の行を1行にまとめた |
| 回帰テスト | `packages/api/tests/test_er_md.py`。`signal.setitimer` で時間制限を掛け、**再発時はハングせず落ちる** |

テストは折り返した表・区切りの無い表・`|` だけの行・末尾が `|` の4形を持つ。
修正前のコードに当てると6件が「5秒で終わらなかった」で落ち、修正後は10件通る。
`ops/er.py report` の所要は10分以上（未完）から**1秒**になった。

## 学び

**入力データの書き方の間違いが、道具のハングとして現れてはいけない。** 表が壊れているなら
崩れて表示されればよく、返ってこないのは道具側の欠陥である。ループは「継続条件が真なら進む」
ではなく「**必ず1つ進む**」で書く。

もうひとつ、**無音の失敗は時間を溶かす**。同じ形の道具（`ops/` の生成器）を書くときは、
終わらない可能性のあるループにテストで時間制限を掛けておく。
