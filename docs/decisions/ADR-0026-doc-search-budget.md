# ADR-0026: 文書検索をツール往復（ホップ）の予算から外し、検索に別枠の上限を置く（上限値と「同じ検索の繰り返し」の扱いは人間の判断を仰ぐ）

日付: 2026-08-02 / 状態: **Accepted（2026-08-02 人間ゲートで承認。§2 は既定 40 / 天井 80、§4 は案 B で確定）** /
関連: ADR-0025（ホップ上限を設定可能にし adb バックエンドを足した。§1 の副作用評価を本 ADR で訂正）,
ADR-0020（RAG バックエンドごとの能力差）, AGT-01d（ツール上限の安全弁）,
仕様: `specs/11-agents.md` §ツール往復の上限 / §文書検索の予算,
検証: `docs/verification/AGT-05-doc-search-budget.md`
（`AGT-05.md` は別タスク「長期メモリ統合」が使用済みのため接尾辞付き。
`AGT-04-agent-tool-hops.md` / `agt-04.md` と同じ先例）

## 背景 — 予算の 8 割が文書検索に消えていた

チャンク単位の出典（`agent_rag_backend=adb`）を選ぶと、`rag_search` は built-in ではなく
**function tool** になる。function tool の実行は「モデル 1 往復」＝ **1 ホップ**を消費するので、
検索するほど業務 API に使える往復が減る。実案件のデモ（API 8 本の受付フロー・仕様書 8 冊・
`agent_rag_backend=adb`・ホップ上限は既定 24）を 3 回実行した実測:

| 実行 | 文書検索 / 全ツール呼び出し | 業務 API 成功 | 自己修正 | 打ち切り |
|---|---|---|---|---|
| 1 | **20 / 24** | 0 | 0 | `max_tool_hops` |
| 2 | **22 / 24** | 1 | 0 | `max_tool_hops` |
| 3 | **19 / 24** | 2 | 1 | `max_tool_hops` |

**3 回とも上限で打ち切り。予算 24 のうち 19〜22（約 8 割）が検索**で、業務 API に回せたのは
4〜5 回分だけだった。エージェント自体の振る舞いは正しい（先頭 2 本を正しい順序で呼び、
422 から自己修正し、409 の順序違反から前段へ戻っている）。**足りないのは予算の配分**である。

従来の `vector_store` 経路（`file_search` built-in）は OCI 側が 1 応答の中で検索を実行するので
**ホップを消費しない**。同じ「文書を調べる」という操作が、出典を細かくした途端に予算を食う。
これは能力の対価ではなく、実装形態（built-in か function tool か）が予算に漏れているだけの
**不整合**である。

### ADR-0025 §1 の前提が実測と合っていなかった（訂正）

ADR-0025 は既定値 24 を「1 ステップ = 検索 1 + API 1」（8 本 × 2 = 16 に自己修正とまとめ分
+50%）という前提で置いた。**実測は 1 API あたり検索 3〜5 回**で、前提の 3〜5 倍だった。
ADR-0025 §2 は「function tool はホップを消費する」を副作用として認識してはいたが、
**影響の大きさを見誤っていた**（`docs/verification/AGT-04-agent-tool-hops.md` の E2E は
API 6 本・仕様書 1 冊 8 チャンクの縮小版で、検索は 1 問あたり 1〜2 回にとどまっていた。
実案件は仕様書 8 冊で、1 本の API を呼ぶ前に順序・コード値・制約を別々に引き直す）。

ADR-0025 §1 の数値（24 / 48）自体はこの ADR では変えない。**変えるのは「何を数えるか」**である。

## 決定

### 1. ホップは「業務の操作」の往復だけを数える

- ホップを消費するのは、その往復に**業務の操作**（外部 HTTP ツール・MCP・組込ツール）が
  1 つでも含まれる場合。検索と業務の操作が同じ往復に混ざったときは **1 ホップ**。
- `adb` 経路の `rag_search` **だけの往復はホップを消費しない**。別枠（§2）で数える。
- `vector_store` 経路（built-in）は**元々消費していない**ので挙動不変。揃えたのは adb 側である。
- 承認往復をまたぐ累計上限（`max(16, ホップ上限)`・AGT-01d）**からも検索を除く**。
  ホップ側だけ直すと、承認モードでは検索を挟むほど先に打ち切られる不整合が残る。

**上限を上げる案は採らない**（タスクの決定事項）。対症療法であり、検索が増えればまた足りなくなる。
コストは往復数に対して概ね二次で効く（ADR-0025 のコスト表）ので、上げ幅がそのまま効く。

### 2. 文書検索の上限 `AGENT_MAX_DOC_SEARCHES`（**提案値 40。人間の判断を仰ぐ**）

> **決定（2026-08-02 人間ゲート）: 既定 40 / 天井 80 で確定。** 実装もこの値になっている
> （`settings.AGENT_MAX_DOC_SEARCHES_DEFAULT` / `_CEILING`）。
>
> 承認前は「新しい policy の数値を勝手に決めない」ため、既に承認済みのホップ上限の数値
> （24 / 48）を暫定として流用していた。承認に伴いこの 2 行を差し替えた。
> 要求ボディの `tool_results` の件数上限も `ホップ天井 + 検索天井` = 48 + 80 = **128**。
> **これは予算の上界ではなく安全弁**である（1 往復から複数の `function_call` が返りうる）。
無制限にはしない。同じ検索を繰り返して止まらなくなるのを防ぐため、検索にも上限を置く。

| 定数 | 提案値 | 根拠 |
|---|---|---|
| `AGENT_MAX_DOC_SEARCHES_DEFAULT` | **40** | 実測「1 API あたり 3〜5 回 × API 8 本」＝ **24〜40**。その**上端**を採る。上端にした理由は、上限に達しても手続きは死なない（§3）ため、余らせるより届かせる側に倒すほうが外したときの代償が小さいこと。env `AGENT_MAX_DOC_SEARCHES` で変更できる。 |

**天井 `AGENT_MAX_DOC_SEARCHES_CEILING` = 80（既定の 2 倍。2026-08-02 承認）を置く。**
当初は
「要求から指定する口が無い＝縛る相手がいない」として置かない設計にしていたが、
**承認往復で送り返せる `tool_results` の件数上限を静的に決めるのに要る**（review-2 の指摘）。
検索をホップの予算から外した以上、1 ターンに積める結果は「ホップ天井 + 検索天井」まで
在りうるので、要求ボディの上限を `ホップ天井 + 検索天井`（`48 + 80 = 128`）にした。
**これは予算の上界ではなく安全弁**である —— 1 往復から複数の `function_call` が返りうるので、
`tool_results` の件数はホップ数からは決まらない（従来の 48 も上界ではなかった。実際の歯止めは
`stream_agent` 側の 2 つの予算が持つ）。ここが小さいままだと、
**検索を挟む承認往復が予算判定に届く前に 422 で詰まる**（ADR-0025 §1 で
「上限を上げたら承認モードの受け口も連動させる」と決めたのと同じ失敗の形）。
天井を超える設定値はクランプせず**拒否**する（ホップ上限と同じ）。

**代替（採否の影響）**

- **24（実測の下端）**: コストは下がるが、仕様書が厚い実案件では手続きの後半で検索できなくなる。
  §3 のとおり手続き自体は続くので「止まる」ことはないが、後半の API の引数を仕様書から
  引けず、モデルが記憶で埋める（＝ 422 / 409 が増える）恐れがある。
- **40（提案）**: 実測の上端を満たす。1 ターンの往復数の上界は
  `ホップ上限 24 + 検索 40 + 最終回答 1 = 65`。
- **上限を置かない**: 却下（タスクの決定事項。同じ検索を繰り返して止まらなくなる）。

**コスト（この判断の代償。実測ではなく外挿）**: エージェントはステートレス（全履歴再送）なので
入力トークンは往復数に対して概ね二次で伸びる。ADR-0025 の実測は **11 往復で入力 55,233**。
同じ伸び方を延ばすと **65 往復では入力 100 万〜200 万トークン規模**になりうる。
これは「上限まで回りきった最悪ケース」であって常用の想定ではない（実測の検索回数は 19〜22）が、
**検索を別枠にすると 1 ターンの往復数の上界そのものが上がる**ことは、上限値を決める前提として
承知しておく必要がある。安く抑えるなら env で 24 に下げる運用が取れる。

### 3. 検索の上限に達しても**手続きは打ち切らない**（検索ツールだけ外す）

- 上限に達したら `rag_search` を**そのターンのツール一覧から外し**、業務の操作は続けさせる。
- 併せて **`{"notice": …, "limit_reached": {"reason": "max_doc_searches", "limit": n}}`** を流し、
  同じ文面を `delta` にも出す（現行 UI は `notice` を描かない — ADR-0025 §3 と同じ扱い）。
  `reason` が `max_tool_hops` と分かれているので、**どちらの予算で止まったか**が応答から追える
  ＝ 直すべき設定がどちらかも追える。
- 手続きごと打ち切る案は却下した。「検索が業務の予算を潰す」という直したはずの不整合を、
  別の入口で作り直すことになる。
- **上限を跨いだ回のバッチは切り詰めない**。モデルが 1 往復で複数の検索を出したとき、
  超過分を捨てると `function_call` に結果が返らない（Responses の入力契約が壊れる）うえ、
  「調べたのに結果が来ない」状態を作る。**その回は全部実行してから**ツールを外す。
  したがって実際の検索回数は上限をわずかに超えうる（超えた分も結果は返す）。

### 4. 「同じ検索の繰り返し」の扱い — **判断を仰ぐ（実装していない）**

実測では同一クエリの反復がある（実行 1 は 24 呼び出し中 20 が検索で、業務 API に 1 本も到達
していない＝同じ材料を引き直している）。扱いは 3 通りあり、**今回は A（何もしない）のまま**
実装を止めてある。

| 案 | 中身 | 影響 |
|---|---|---|
| **A. 何もしない**（現状） | 反復もそのまま実行し、§2 の上限だけで抑える | 実装ゼロ。無駄な往復は残るが、モデルは常に「引いた結果」を得られる |
| **B. 検知して知らせる** | 同一クエリ（正規化して比較）の 2 回目以降に `notice` を出す。**結果はそのまま返す** | 反復が起きていることが応答と証跡に残り、上限値の見直しや instructions 改善の材料になる。実装は小（直近クエリ集合の保持） |
| **C. 抑止する**（重複を実行しない / 結果を空にする） | — | **却下を推す**。エージェントは「調べた」と思ったまま結果を得られず、記憶で埋めるか同じ検索を繰り返す。握り潰しは失敗を見えなくする |

**推す案は B**（知らせるが握り潰さない）。ただし「通知が増えて画面がうるさくなる」ことと
天秤なので、採否は人間の判断とする。A のままでも §2 の上限で暴走は止まる。

**決定（2026-08-02 人間ゲート）: 案 B を採る。** 実装済み（`_normalized_query` /
`_repeated_search_event`）。表記ゆれ（前後の空白・大小・連続空白）だけの違いは同じ検索とみなし、
**解析できない引数は反復判定の対象にしない**（判定できないものを「同じ」と決めつけない）。
**結果は必ずそのまま返す。**

## 却下した案

- **ホップ上限の既定値・天井を上げる**: 対症療法。検索が増えればまた足りなくなり、
  コストは往復数に対して二次で効く（タスクの決定事項でもある）。
- **検索結果を切り詰める**（件数や本文を減らして往復を稼ぐ）: 根拠が欠ける。
  ADR-0025 §2 の「本文は切り詰めない」と衝突する。
- **`vector_store` 経路（built-in）にも同じ上限を掛ける**: built-in の検索は
  function_call として往復せず、回数を正しく数える手立てが無い。挙動不変が回帰の観点でも安全。
- **検索の上限で 1 ターンを打ち切る**: §3 のとおり、直した不整合を別の入口で作り直す。
- **要求ごとに検索上限を指定できるようにする**（`max_doc_searches` フィールド）: 今回は要らない。
  外から来る値を受けると天井の議論も要る（§2）。必要になったら別タスクで足す（YAGNI）。

## 既知の限界

- 1 ターンの往復数の上界が `ホップ上限 + 検索上限 + 1` に上がる（§2 のコスト）。
- 承認モード（`auto_tools=false`）では要求ごとに予算が 0 から数え直される既存の性質
  （ADR-0025 §1 の「既知の限界」）は変わらない。検索の予算も同じくターン内の予算である。
- 検索の上限に達したあとにモデルが `rag_search` を呼び続けた場合（ツール一覧から外しても
  名前を出すことはありうる）、**その呼び出しは実行せず理由を返す**
  （「文書検索の回数が上限（n 回）に達したため実行できません」）。実行してしまうと
  上限がホップ上限のぶんだけ空振りする。またその往復は**業務の操作と同じ扱い**で
  ホップを消費する ——終了性を担保するための扱いであって、検索を罰する意図ではない。
- **承認往復では検索の予算を送り返された `tool_results` から復元する**。承認のたびに
  0 から数え直すと、累計上限からも外した検索に歯止めが無くなる。復元できるのは
  クライアントが送り返した分だけなので、サーバー側で自動実行した検索（承認不要）は
  次の要求には引き継がれない（ADR-0025 §1 の「既知の限界」と同じ性質）。
