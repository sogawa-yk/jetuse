# ADR-0027: JetUse をシカゴへ移し、モデル差を吸収する層を置く

- 状態: **Accepted**(2026-08-03 人間ゲートで承認。§5-A = `xai.grok-4.3` / §5-B = **B-1 完全撤去**)
- 日付: 2026-08-03
- 関連: ADR-0001(大阪の制約) / ADR-0011・ADR-0017(イメージとリージョン) /
  ADR-0016 §E(シカゴ提供の方針) / `docs/verification/AGT-06.md` /
  `docs/comparison/agent-capable-models.md`

## 文脈

エージェントで使えるモデルが `gpt-oss-120b` の 1 つしかなかった。登録簿が
「他は Responses API 非対応」としていたが、**実機で当たると誤りだった**
(gemini 系・`gpt-oss-20b` は Responses で動く)。

比較できるモデルが無いことの実害が案件デモで出た。`order_context_initialize` が
`requested_product_code` を返しているのにモデルがそれを使わず、同じ検索を 12 回繰り返し、
最後に架空の品番を作って**実行せず手順書を返した**。**モデルの限界なのかプロンプトの
問題なのか切り分けられない**。

あわせて、シカゴは大阪より品揃えが厚い(CHAT/ACTIVE で 47 対 29。大阪に無い Grok 系がある)。

## 決定

### 1. JetUse 本体を `us-chicago-1` へ移す

配備先の既定をシカゴにする(Terraform 変数・`.env.example`・`settings.py`・ops スクリプト)。
大阪も値を渡せば動く(リージョンを固定するのではなく、既定を移す)。

**根拠**: エージェントで使えるモデルが 5 → 8 に増え、**比較できる系統(Grok)が入る**。
モデル差かプロンプト差かを切り分けられるようになることが移設の主目的。

### 2. リージョン依存の直書きを 1 か所へ集約する

`ops/deploy-agent-containers.sh` / `redeploy-agent-env.sh` / `deploy-hosted-agent.sh` は
リージョン(`ap-osaka-1`)と OCIR ホスト(`kix.ocir.io`)を**別々に直書き**していた。
リージョンだけ変えても**イメージは大阪の OCIR を指したまま**になる。

`ops/_region.sh` に集約し、リージョン → OCIR ホスト(`ord`/`kix`/`nrt`/`iad`)を 1 か所で解決する。
**未対応リージョンは推測せず停止する**(`OCIR_HOST` の明示指定を促す)。

### 3. 登録簿は実機の測定結果だけを載せる

`jetuse_core/models.py` を測り直した結果に合わせた。**測っていないモデル・
測っていないフラグは載せない。** 追加手順は `docs/verification/AGT-06.md` §9。

- 追加: `gpt-oss-20b` / `grok-4.3` / `grok-4.20-reasoning` / `grok-4.20-non-reasoning` /
  `gemini-2.5-flash-lite`
- 訂正: `gemini-2.5-pro` / `gemini-2.5-flash` を `chat` → **`responses`**
- 追加(不可として): `grok-4.20-multi-agent`
- **載せなかったもの**: 非推奨日を過ぎた Grok(`grok-4` 等)・Responses が 404 の
  Llama 4 系 / Cohere 系

**`reasoning` フラグは名前から推測しない**。`grok-4.20-reasoning` は名前に反して
`reasoning effort` を 400 で拒否する(実測)。

### 4. モデル差は「吸収する」か「断る」の二択にする

新設 `jetuse_core/model_compat.py`。**実測で確認した 2 つの差だけ**を吸収する
(推測で先回りしない)。

| 差 | 対象 | 吸収 |
|---|---|---|
| `role=system` の入力アイテムを拒否 | Gemini 全て | 役割だけ `user` へ移す(**本文は変えない**) |
| `function_call` を `id` 付きで積み直せない(stream 時) | Gemini 全て | `id` を落とす(`call_id` は残す) |
| client-side tools 自体が使えない | `grok-4.20-multi-agent` | **吸収せず断る** |

**吸収できない差は登録簿の `agent_blocked_reason` に持たせ、要求時に理由つきで断る。**
黙って動かないより断るほうがよい。断りは 2 段(ルートで 400 / `stream_agent` でも
エラーイベント)で、`/api/chat/models` にも `agent` 可否を出して UI が選ばせる前に弾ける。

**なぜ「差を吸収する層」を新しく置いたか**: 差はこれからも増える(モデルは足される)。
呼び出し側(`chat.py`)に `if model == gemini` を散らすと、次のモデルで同じ判断が別の場所に
生える。登録簿がフラグを持ち、吸収層がそれを読む形にすれば、**追加は登録簿の 1 行**で済む。

## 実装しなかったこと(意図的)

- **`terraform apply` / 大阪の削除を行っていない**(人間ゲート)。plan と手順書まで。
- **既定モデルは 2026-08-03 の人間ゲートで `xai.grok-4.3` に変更した**(§5-A)。
  ループの実装時点では `gpt-oss-120b` のままにして判断を上げ、承認後に 1 行を差し替えた。
- **TTS のコードを変えていない**。シカゴで TTS は 500 で失敗するが、既存の自動
  フォールバック(FIX-58)が Phoenix へ回すため実害が無い(実測で確認)。
  `TTS_REGION` をシカゴに固定してはいけない、という制約が増えただけ。

## 5. 判断を上げる(実装せず止めた 2 点)

### A. エージェントの既定モデルをどれにするか

現行は `gpt-oss-120b`。多段の手続き比較(8 モデル × 3 試行)では
**`gpt-oss-120b` / `grok-4.3` / `grok-4.20-reasoning` / `gemini-2.5-{pro,flash,flash-lite}`
が揃って 3/3 完了**で、**この難度では差がつかなかった**。

| 選択肢 | 得られるもの | 失うもの・リスク |
|---|---|---|
| **A-1. `gpt-oss-120b` のまま**(現状維持) | 挙動の連続性。回帰リスクゼロ。`reasoning effort` 可 | 画像入力不可。移設の成果が既定に現れない |
| **A-2. `grok-4.3` にする** | 画像入力可 + `reasoning effort` 可 + 3/3 完了(5.0 秒)。**シカゴ移設の意義が既定に出る** | **大阪では使えない**(大阪を残す判断=B と衝突)。単価は未調査 |
| **A-3. `gemini-2.5-flash` にする** | 3/3 完了・画像可・5.4 秒 | **吸収層に依存する**(system 折り畳み + id 除去)。吸収層に穴があると既定が壊れる。`reasoning effort` 不可 |

**測定から言えること**: 精度では選べない(差が出ない)。**選定の軸は
「大阪を残すか(B)」「画像を既定で扱うか」「単価」**になる。
**単価は未調査**(このタスクでは測っていない)。コストが軸なら先に調べる必要がある。

**推奨**(判断前): **B の結論が出るまで A-1(現状維持)。** B で「大阪を完全撤去」なら A-2 を推す
(移設の成果が既定に出て、画像も扱える)。B で「大阪を残す」なら、既定が
リージョンで使えたり使えなかったりするのは避けたいので A-1 を維持すべき。

### B. 大阪を完全に撤去するか、一部を残すか

| 選択肢 | 得られるもの | 失うもの・リスク |
|---|---|---|
| **B-1. 完全撤去** | 課金と運用対象が 1 リージョンに閉じる。二重管理が消える | **大阪限定のモデルが使えなくなる**(`gemini-3.1-flash-lite` / `gemini-3.5-flash` / `cohere.command-a-*` はシカゴに無い)。日本国内リージョン要件のデモができない |
| **B-2. GenAI 推論だけ大阪に残す** | 上記モデルのデモが続けられる | project・Vector Store をリージョンごとに持つ運用が残る |
| **B-3. 当面まるごと残す(並行運用)** | 切り戻せる。案件デモの `mnpdemo-*` に一切触れない | 課金が二重。どちらが正かが曖昧になる |

**事実として押さえておくこと**:
- 案件デモのモック・ゲートウェイ(`mnpdemo-*`)は**大阪にあり、移設対象ではない**。
  JetUse 本体を撤去しても、これらは残す前提。
- 大阪にしか無いモデルが実際にある(上表)。「シカゴが上位互換」ではない。
- **日本国内にデータを置く要件**があるデモでは大阪が要る。この要件の有無は
  技術判断では決められない。

**推奨**: **B-2**(推論だけ残す)。

**決定(2026-08-03 人間ゲート): B-1(完全撤去)を採る。** 推奨とは異なる判断だが、
「どちらが正か曖昧なまま二重に持たない」を優先する。上表の代償(大阪にしか無いモデルの
デモができない・国内限定要件に応えられない)は**承知の上**で受け入れる。
必要になったら大阪へ配備し直す(Terraform で作り直せる。state は別)。

**ただし撤去の範囲は「JetUse 本体の配備物」に限る。** `docs/guides/osaka-teardown.md` §1 の
「消してはいけないもの」——案件デモの `mnpdemo-*`、ループ共有の `jetuseloop2` / `jetuse-loop-project`、
別コンパートメントの既存資産——は **B-1 でも対象外**。撤去の実務は同手順書に従い、**実行は人間**。

## 影響

- 既存の大阪配備は**何も壊れない**(シカゴの plan は `0 to destroy`。別 state・別リージョン)。
- 既定リージョンが変わるので、`.env` を持たないローカル実行はシカゴを向く。
- `gemini` 系が `chat` → `responses` に変わるため、可用性フォールバック
  (`routes/chat.py` の chat-family 探索)の候補が Llama 系 2 つに減る。動作は維持。
