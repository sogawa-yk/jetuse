# ADR-0020: RAG チャンクのメタデータ（出典粒度・フィルタ検索）をどの方式で実現するか

日付: 2026-07-28 / 承認: 2026-07-29
状態: **Accepted**（2026-07-29 ユーザー承認。承認時に「単一方式の段階採用」から
**「選べる2バックエンド＋能力差の可視化」**へ決定内容を拡張した — 下記「決定」参照）

## 背景

`jetuse_core/chat.py:_extract_citations()` が返す引用は `{file_id, filename, score}` だけで、
**ファイル単位までしか遡れず、検索時にメタデータで絞る口も無い**。
一方で顧客案件では「仕様書 v2.0 の『制約』シート C5:E5 が根拠」まで示したい、
「旧版の記述を回答に混ぜたくない」という要求が出る。

この不足をどの方式で埋めるかを、推測ではなく実機で決めるために SPIKE-M1 を実施した
（検証レポート `docs/verification/SPIKE-M1.md`・比較 `docs/comparison/rag-metadata-backends.md`）。

検証前の想定は「① 外部ベクタストアでは属性もフィルタも持てないので ③ ADB 自前索引が要る」だったが、
**実機でこの前提は覆った**。① は属性もフィルタも動く。以下はその結果を踏まえた提案である。

## 実機で確定した事実（要点のみ。根拠は検証レポート）

| | ① Vector Store + file_search | ② Select AI 索引 | ③ ADB 自前索引 |
|---|---|---|---|
| 任意メタデータ | 可（16キー/512文字/入れ子不可） | **不可**（`ORA-20048`） | 可（列・JSON 自由） |
| フィルタ検索 | 可（eq/and/or/gte。`in` は不可） | 標準経路に無い | 可（SQL の WHERE 全部） |
| 出典の粒度 | **ファイル単位**（1ファイル=5チャンクでも属性は 1 種類） | ファイル単位 + オフセット | **チャンク単位** |
| 業務表との JOIN | 不可 | 実質不可 | 可 |
| 検索レイテンシ中央値 | 121.5 ms | 69.3 ms | 16.7 ms（+埋め込み 84.5 ms）／192.7 ms（DB内埋め込み込み） |

> レイテンシは**方式選択の決め手にならない**。同じ土俵（テキスト入力→結果）では
> ① 121.5 ms に対し ③ 約 101〜192.7 ms とほぼ同じで、しかも 10 行規模・実行ごとに揺れる数字。
> 判断は表現力と出典粒度で行う（3 方式が同じ 10 チャンクを見ていることは chunk_id 一致で確認済み）。

## 決定

**どちらか一方を選ぶのではなく、性格の違う 2 バックエンドを「選べる」ようにする。
そして能力差をアプリから見えるようにする。**

「手軽さ」と「高機能」はトレードオフであって優劣ではない。デモ用途では前者が、
業務データと絡む提案では後者が要る。JetUse は既に RAG バックエンドを選択式で持っている
（`packages/web/src/pages/rag.tsx` の `rag_backend`）ので、その延長で扱う。

### 1. `vector_store`（Enterprise AI マネージド Vector Store）— 手軽さ側・既定

- 取り込み時に `vector_stores.files.create(attributes={file, version, sheet, cells, sha256, kind,
  current_version, chunk_id})` を付ける。
- `_extract_citations()` を拡張し、`file_search_call.results[].attributes` と `.text` を
  構造化引用として返す（`{file_id, filename, score}` は後方互換のため残す）。
- 検索時に `tools[].filters` で `current_version='Y'` を掛けられるようにする。
- チャンク単位の出典が要る文書は **1 チャンク = 1 ファイル**で取り込む
  （① の属性はファイル単位のため。これが手軽さ側の代償）。

### 2. `adb`（Oracle AI Database 自前索引）— 高機能側

- チャンク単位の出典（セル範囲・行番号）、SQL の全表現力での絞り込み、業務表との JOIN、
  検索とメタ更新の同一トランザクション、VPD / Data Redaction による行レベル制御。
- **Agent Memory のバックエンドとしても同じ土台を使う**（2026-07-29 ユーザー方針）。
  Oracle AI Database は会話記憶の格納先としても打ち出されており、RAG のメタデータ基盤と
  同じ表・同じ権限体系に載せられる。ADR-0006 の OCI ネイティブ長期メモリは**併存**させ、
  置き換えない（選択式にする）。
- 本文の保管と検索は ADB 内で完結する。ただし DB 内埋め込み（`UTL_TO_EMBEDDING`）は
  本文を OCI Generative AI の `embedText` へ送るため、「テナント外へ一切出ない」ではない（実測）。

### 3. 能力差をアプリケーションから見えるようにする（2026-07-29 追加要件）

高機能側を選んだときに**何が増えるのかが利用者に伝わらなければ、選べる意味がない**。
API だけでなくフロントからも分かる形にする。

- `GET /api/capabilities` の `rag.search` ディスクリプタに、**バックエンドごとの能力**
  （出典粒度 / 絞り込みの表現力 / 業務データ結合 / 行レベル制御 / メタ更新の整合性）を
  機械可読で載せる。ビルダーと外部連携はこれを読んで判断できる。
- 引用（citations）は選択バックエンドに応じて粒度が変わる。**API 契約は後方互換**
  （既存 `{file_id, filename, score}` を残し、`source` 等の拡張フィールドを足す）。
- **フロント**（`rag.tsx` の既存バックエンド選択 UI）で、選択中のバックエンドで
  「使える機能／使えない機能」を明示する。`adb` を選ぶと版フィルタとセル範囲出典が
  有効になることが画面上で分かること。取り込み状況バッジ（indexed/pending）とは別に、
  **能力の差**を出す。

### 4. `select_ai` はメタデータ管理の基盤としては採用しない

既存の RAG バックエンドとしては現状維持（削除しない）。任意メタデータの置き場としては使わない。

## 却下した案とその理由

- **単一バックエンドに固定する（どちらか一方だけ提供）**: 却下（2026-07-29 の決定）。
  手軽さと高機能はトレードオフで、デモ用途と業務データ提案で要るものが違う。
  片方に寄せると、もう片方の場面で JetUse が使えなくなる。
- **③ へ全面移行（今すぐ・① を廃止）**: 却下。① が属性もフィルタも満たす以上、
  すべての利用者に自前の取り込みパイプライン（抽出・チャンク化・埋め込み・索引・再取り込み）を
  強制する理由がない。高機能が要る人が選べればよい。
- **② を採用**: 却下。任意キーが `ORA-20048` で拒否され、`$VECTAB` に列を足す回避は
  索引リフレッシュのたびに新規行が NULL になる（実測）。取り込みのたびに補完ジョブを
  回し続ける前提の設計になり、メタデータの正しさを構造で保証できない。
- **① のフィルタだけで版管理を担保**: 部分的に却下。フィルタ自体は動くが、
  **存在しないキーを指定してもエラーにならず 0 件**になる（実測）。
  キー名の担保はアプリ側の責任として明示的にテストで守る必要がある。

## 影響

- `rag.py`（取り込み時 attributes）・`chat.py`（引用の構造化）・`capabilities.py`（能力差の記述）・
  API 契約（citations の拡張・後方互換）・`packages/web/src/pages/rag.tsx`（能力差の表示）に変更が入る。
  SPIKE-M1 自体は JetUse 本体を変更していない（検証のみ）。
- `adb` バックエンドは新規モジュールで足す（既存 RAG 経路は据え置き）。ADB 23ai 以上が前提。
- Agent Memory の ADB バックエンドは ADR-0006（OCI ネイティブ長期メモリ）と併存。
  ADR-0006 は棄却しない。

## 未解決 / 後続で決めること

- 大規模データでの `adb` の索引利用と再現率は未計測（10 行ではオプティマイザが索引を使わない）。
  本番規模で使う前にスケール検証が要る（RAGM-02 の前提）。
- VPD / Data Redaction がベクタ検索にも効くことは未実証（SPIKE-M1 の非ゴール）。
  「行レベル制御ができる」と顧客に言う前に実機確認が要る。
- Chicago リージョンでの可否は未確認（SPIKE-M1 は大阪のみ）。
- `ops/setup-select-ai.py` / `ops/setup-dev-schema.py` の `~/.oci/config` パーサが
  複数プロファイル環境で壊れる（本スパイクで発覚）。別タスクで修正が要る。
