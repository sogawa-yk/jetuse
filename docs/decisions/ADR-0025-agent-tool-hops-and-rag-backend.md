# ADR-0025: エージェントのホップ上限を設定可能にし、文書検索に adb バックエンドを足す（既定値と天井は人間の判断を仰ぐ）

日付: 2026-08-02 / 状態: **Accepted（2026-08-02 人間ゲートで承認。§1 の既定 24 / 天井 48 で確定）** /
関連: ADR-0020（RAG バックエンドごとの能力差）, ADR-0024（外部 HTTP ツールの入れ子引数）,
AGT-01（エージェントループ）, AGT-01c（`rag_search`）,
仕様: `specs/11-agents.md` §エージェントモードのツール往復,
検証: `docs/verification/AGT-04-agent-tool-hops.md`

## 背景

実案件のデモ（業務 API 8 本を順に呼ぶ受付フロー）を実環境で走らせ、2 つの実測を得た。

| 事実 | 値 |
|---|---|
| 業務 API の呼び出し | 6 回（うち成功 4・自己修正 1） |
| 文書検索（`rag_search`）の呼び出し | 約 40 回 |
| 到達点 | 8 本中 4 本。**ホップ上限に当たって停止**（診断のため一時的に 30 へ上げた状態で） |

原因は 2 つあり、どちらも「エージェントに業務 API を渡す」という看板機能に直結する。

1. `MAX_TOOL_HOPS = 5` が固定。API 8 本の手続きに文書検索が挟まるので、5 往復では入口にも届かない。
2. エージェント経路の文書検索は Vector Store の `file_search` built-in だけで、出典が
   **ファイル単位**（「どの仕様書か」）にとどまる。「どのシートのどのセルか」が返らない。
   ADR-0020 が「Oracle AI Database ならチャンク単位で出せる」と決めた能力が、
   エージェント経路では活きていない。

   > 起票時は「出典が粗いからエージェントが同じ文書を何度も引き直す（上の約 40 回）」と
   > 見立てていた。**この見立ては E2E の実測では支持されなかった**（§5）。
   > チャンク単位の出典を足す価値は「根拠がセルまで辿れること」であって、
   > 「検索回数が減ること」ではない。

## 決定

### 1. ホップ上限を設定可能にする。**既定値と天井（この節が人間の判断を仰ぐ点）**

> **なぜ未承認の数値がコードに入っているか**（レビューで論点になった）:
> tasks/AGT-04.md の「決まっていること（2026-08-02 人間ゲートで承認済み。作り直さない）」が
> 「ホップ上限を設定可能にし、**既定を業務フローに耐える値へ上げる**」と定めており、
> 完了条件（「上限が設定で変えられる」「上限に当たったことが分かる」）と E2E シナリオ1
> （「従来の上限では届かない長さの手続きが最後まで到達する」）は、動く既定値なしには
> 検証できない。よって**機構と提案値を実装した上で、数値そのものを本 ADR で上げる**。
> 承認前に固定してよいという意味ではない —— 定数は `settings.py` の 1 か所にあり、
> 値の変更は 2 行の編集で済む（ADR-0024 §3 と同じ運び方）。



1 ホップ = **モデル 1 往復**（ツール結果を積んで再送 → 次の tool_call か最終回答）。
1 ホップに複数の tool_call が載ることもある。**上限はツールを渡した往復の数**で、
上限に達したときの「ツールなしの最終回答」はその外側の 1 往復になる
（＝ 1 要求の最大往復数は **上限 + 1**。この最終往復の usage も出す）。

| 定数 | 提案値 | 効く場所 | 根拠 |
|---|---|---|---|
| `AGENT_MAX_TOOL_HOPS_DEFAULT` | **24** | 既定値（env `AGENT_MAX_TOOL_HOPS` で変更） | 実案件の手続きは API **8 本**。adb バックエンドでは `rag_search` が built-in ではなく **function tool** になる＝**検索も 1 ホップを消費する**（後述 §2 の副作用）。仕様を読んでから呼ぶので「1 ステップ = 検索 1 + API 1」を基準にすると 8×2 = **16**。ここに自己修正（実案件の実測で 6 回中 1 回）とまとめ回答の分で **+50%** を見て 24。**E2E 実測（API 6 本の手続き・adb 検索つき）は、同じ要求を 8 回流して 8〜13 ホップ**（`docs/verification/AGT-04-agent-tool-hops.md`）。API 8 本へ線形に伸ばすと 11〜17 ホップ相当で、24 はその 1.4〜2.2 倍の余裕にあたる。 |
| `AGENT_MAX_TOOL_HOPS_CEILING` | **48** | 要求・設定の**上限**（超えたら拒否） | 既定の 2 倍。1 ホップの実測レイテンシは数秒規模なので、48 ホップでも 1 ターンが数分に収まり、SSE の実用的な待ち時間と API Gateway の `readTimeout`（最大 300 秒／ADR-0003 の keepalive 前提）から外れにくい。**「足りないから上げる」を無限に許さない**ための硬い天井であって、推奨値ではない。 |
| 累計ツール結果の上限 | `max(16, ホップ上限)` | 承認モードの往復（AGT-01d の安全弁） | 従来は固定 16。ホップ上限だけ上げると**承認モードでは 16 件で先に打ち切られる**ので連動させる。要求ボディの `tool_results` の件数上限も従来の 24 件から**天井に合わせる**（小さいままだと、上限を上げても承認モードだけ 422 で継続できない）。 |

**決定（2026-08-02 人間ゲート）: 既定 24 / 天井 48 で確定する。** 実測（API 6 本で 8〜13 ホップ）に
対して十分な余裕があり、天井が暴走を止める。低すぎると業務フローが完走しない（それが本タスクの
不具合そのもの）。入力トークンがホップ数に対して概ね二次で伸びること、上限まで回れば 1 要求で
20〜30 万トークン規模になりうること（外挿）を承知の上で、**上限は「止まらないための保険」**として置く。

**クランプしない**。天井を超える値は要求なら 422、設定値なら 400 で**拒否**する。黙って下げると
「上げたのに効かない」が起き、上限に当たった理由を設定値から追えなくなる。
なお設定値の検証は **`Settings` のレンジ検証にはしない**——`get_settings()` はほぼ全 API が
呼ぶので、エージェント専用の設定ミスがチャットも RAG も 500 にしてしまう。壊すのは当該機能だけに閉じる。

**コスト（1 ホップ = モデル 1 往復）**: エージェントはステートレス（全履歴再送）なので、
入力トークンはホップごとに「それまでの tool_call + ツール結果」の分だけ増える。
ツール仕様（外部 HTTP ツール 6〜8 本の入れ子スキーマ・ADR-0024）も毎回載る。
つまりホップ数に対して**出力は線形・入力は概ね二次**で効く。E2E の実測（同じ要求・
ツール 6 本・gpt-oss-120b）:

| 条件 | モデル往復（最終回答の 1 往復を含む） | 入力トークン計 | 出力トークン計 |
|---|---|---|---|
| 上限 5（旧固定値。2〜3/6 で打ち切り） | 6 | 20,467 | 1,995 |
| 既定（6/6 完走・10 ホップ） | 11 | 55,233 | 1,954 |

往復が 1.8 倍で入力は **2.7 倍**（履歴とツール仕様を毎回送り直すため）。この伸び方を延ばすと
24 ホップ・ツール 8 本では**入力 20 万〜30 万トークン規模**になりうる（**外挿であって実測ではない**）。
天井 48 まで回れば更にその数倍になる。上限を上げるのは「止まらないための保険」であって、
常用でここまで回る想定ではない —— という前提で 24 / 48 を提案している。
実測の内訳は `docs/verification/AGT-04-agent-tool-hops.md`。

**既知の限界（この判断に関わるので明記する）**: ホップ上限は**1 要求のうち**の往復数である。
承認モード（`auto_tools=false`）では、承認のたびに新しい要求になるのでホップは 0 から数え直す。
累計の安全弁（`max(16, ホップ上限)`）が数えるのは**クライアントが送り返してくる `tool_results`**
だけなので、承認不要のツール（`get_current_time` / `query_database` / adb の `rag_search`）を
サーバー側で自動実行した分は数に入らない。つまり「承認を繰り返すクライアント」に対する
1 会話あたりの総往復数には上限が無い（AGT-01d からの既存の性質で、上限を 5 → 24 にしたことで
1 往復あたりの最大値が増える）。会話単位の上限が要るなら別タスク。

**判断を仰ぎたいこと（採否の影響）**

- **24 / 48 で確定してよいか**。低すぎれば実案件のデモがまた途中で止まり、
  高すぎれば「モデルが同じツールを呼び続ける」ときの浪費（トークンと待ち時間）が増える。
- 既定を上げず **要求ごとの `max_tool_hops` だけで運用する**選択もありうる（既定 5 のまま据え置き）。
  その場合デモ側が毎回指定する必要があり、指定漏れが「途中で止まる」として再発する。
- 実案件（API 8 本・大きい仕様書）で 24 に収まるかは**まだ測っていない**。E2E は API 6 本の
  縮小版である。収まらなければ天井 48 の範囲で `max_tool_hops` を指定して凌げるが、
  既定値そのものの見直しは改めて判断が要る。

### 2. エージェントの `rag_search` に adb バックエンドを足す（**増やすだけ**）

- `rag_search` を **function tool** として実装し、`rag_adb.search`（現行版のみ）を呼ぶ。
  結果 1 件に `source = {file, sheet, cells, version, chunk_id, ...}` を載せる＝
  「制約シート C5:E5」まで答えの根拠にできる。**本文は切り詰めない**（根拠が欠ける）。
- どちらを使うかは要求で選ぶ（`agent_rag_backend`。既定 `vector_store` ＝**挙動不変**）。
  Vector Store の `file_search` built-in は**置き換えない**。
- この tool は読み取り専用なので `requires_approval=False`。承認を要ると、承認モードでは
  文書検索のたびにストリームが止まり、多段の手続きが進まなくなる。
- adb が使えない（表が無い / DB につながらない）ときは**要求を 400 で断る**。素通しすると
  検索が毎回失敗したまま、もっともらしい回答だけが返る。
- 検索結果は `citations` イベントとしても流す。function tool の結果は
  `response.completed` に現れないので、出さないとチャンク単位の出典が UI の出典欄に出ない。

**副作用（意図的）**: built-in の `file_search` は OCI 側が 1 応答の中で実行するのでホップを
消費しないが、function tool はホップを消費する。§1 の既定値はこれを織り込んだ値である。

### 3. 上限に当たったことを応答に出す

従来は「ツールなしで最終回答を強制」するだけで、**途中で力尽きたのか答え切ったのかが外から
区別できなかった**。デモで「なぜ途中で止まったか」を説明できないのは、失敗そのものより悪い。

- 構造化イベント `{"notice": <文面>, "limit_reached": {"reason": "max_tool_hops"|"max_tool_results", "limit": n}}`
- 加えて同じ文面を `delta` としても流す。現行のチャット UI は `delta` / `tool_call` / `error` しか
  描かないため、イベントだけだと**画面には何も出ない**。本文に出れば会話履歴にも残り、
  後から「これは打ち切りだった」と分かる。UI が専用表示を持ったら `notice` に一本化してよい。

### 4. `agent` と `rag` の併用禁止は維持する

併用時に何が起きるかが不明瞭なままなので、今回はエージェント側の口を増やすだけにする。
禁止を外すなら別タスク。

### 5. 実測で否定された前提を記録する（検索回数は減らなかった）

E2E シナリオ3（`runs/2026-08-02T1501_AGT-04/e2e/scenario-3.md`）で、同じ文書・同じモデルに
2 種類の問いを投げ、バックエンドだけを変えて `rag_search` の回数を数えた。

| 問い | vector_store | adb |
|---|---|---|
| 複数の事実をまとめて聞く | 1 回 | 1〜2 回（実行により変動） |
| 1 つの値と出典を聞く | 1 回 | 1 回 |

**減らなかった**（むしろ 1 回だけ adb が 1 回多かった）。各条件 1 回ずつの実測なので
「増える／減る」を統計的に言える強さは無いが、
少なくとも**「チャンク単位にすれば引き直しが減る」を根拠として採ってはいけない**。
起票時の約 40 回という観測は、この検証用の小さな仕様書（8 チャンク）では再現していない
（実案件は API 8 本・仕様書も大きい）。**adb バックエンドを採る理由は §2 の出典の粒度だけで足りる**ので、
決定そのものは変えない。ホップ上限の既定値も「検索が 1 ホップを食う」前提で置いてあり、
この結果で見直す必要はない。

## 却下した案

- **ホップ上限の撤廃**: モデルが同じツールを呼び続けたときに止まらない。天井は必要。
- **超過値のクランプ**: 黙って下げると設定が効かない理由が追えない（§1）。
- **`rag_backend` フィールドの再利用**: `rag=true` 用のフィールドで、既定 `vector_store` を
  そのまま流用するとエージェント経路で `select_ai` / `opensearch` を指定できてしまい、
  意味が定義されていない組み合わせが増える。専用の `agent_rag_backend` にした。
- **`file_search` built-in を adb に置き換える**: 既存デモの回帰リスクを負う理由がない。選べれば足りる。
