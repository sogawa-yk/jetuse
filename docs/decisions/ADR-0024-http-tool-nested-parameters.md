# ADR-0024: 外部 HTTP ツールの引数に入れ子・配列を受理する（上限値は人間の判断を仰ぐ）

日付: 2026-08-02 / 状態: **Accepted（2026-08-02 人間ゲートで承認。§3 の上限値は提案値で確定）** /
関連: ADR-0023（TOOL-02 の固定ヘッダ）, TOOL-01（外部 HTTP ツールの導入）,
仕様: `specs/17-demo-platform-redesign.md` §「`agents` の外部ツール」,
検証: `docs/verification/TOOL-03.md`

## 背景

TOOL-01 の `validate_parameters` は `ALLOWED_PARAM_TYPES = ("string","number","integer","boolean")`
だけを受理していた。実案件のデモで登録しようとした業務 API **8 本のうち 6 本**が、入れ子の
オブジェクトか配列を必要とするため**登録すらできなかった**（実測: 400
「引数 `<名>` の type は string/number/integer/boolean のいずれかです」）。

このデモの趣旨は「**SoR の API 仕様が複雑すぎるので、AI に仕様書を読ませて正しく呼べるかを
確かめる**」ことである。JetUse が複雑なボディを表現できないと、**複雑な API ほど渡せない**という
逆転が起きる。測定したい能力の手前で、機構の都合が上限を作ってしまっていた（ADR-0023 の
「仕掛けの制約で失敗すると測定値が意味を失う」と同じ構図）。

## 決定

### 1. 入れ子・配列を受理する。ただし「検証しきれる形しか通さない」方針は変えない

TOOL-01 の設計意図（未対応の JSON Schema キーワードを素通しさせない）は正しい。素通しすると
「**モデルには制約に見えるが、実行前検証は何もしていない**」状態になり、そちらの方が危険である。
したがって受理するのは、**実行時に同じ強さで検証できる形**に限る。

- `object`: **`properties` を持つこと**。自由形式（`properties` なし）は受理しない＝何が来ても
  検証できないため。root だけは従来どおり省略可（`{"type":"object"}` = 引数なし）。
- `array`: **`items`（単一スキーマ）を持つこと**。タプル形式（`items` が配列）は受理しない。
- 各階層で**検証できるキーだけを残す**（`enum` / `pattern` / `oneOf` / `$ref` 等は落とす）。
- 実行前検証（`tools._validate_args`）も再帰にし、**未知キーの拒否・型検査・`required` を
  各階層で**効かせる。配列は要素ごとに `items` で検査する。

宣言側（`validate_parameters`）と実行側（`_validate_args`）の強さが一致していることが本 ADR の
核である。片方だけ緩いと、上の「制約に見えて素通し」が階層の内側で再発する。

### 2. GET ツールには入れ子・配列を宣言できない（登録時に 400）

GET にはボディが無く、入れ子・配列をクエリ文字列へ載せる**標準の書き方が無い**
（`a[0].b=` / `a=<JSON>` / `a=1&a=2` はいずれも相手の実装次第）。JetUse が勝手な符号化を決めると
「送ったつもりの形と、相手が読む形が違う」という、検証をすり抜ける壊れ方になる。
入れ子が要る API は POST（JSON ボディ）で登録する。実行時にも `str(dict)` を送らない
（DB を直接書き換えられた場合の fail-closed）。

### 3. 上限値（**この節が人間の判断を仰ぐ点**）

際限なく複雑なスキーマを受けると、モデルへ渡す仕様が肥大し、実行前検証のコストも青天井になる。
`MAX_TOOLS_PER_AGENT` と同じ流儀で定数化する。**「足りないから上げる」を繰り返さないよう、
根拠のある値**を提案する。

| 定数 | 提案値 | 効く場所 | 根拠 |
|---|---|---|---|
| `MAX_SCHEMA_DEPTH` | **6** | 宣言時（400） | 実在する業務 API の最深構成「配列の中に配列（2 段）」＝ root(1) → 配列(2) → 要素オブジェクト(3) → 配列(4) → 要素オブジェクト(5)。**実測の最深が 5 段**なので、1 段だけ余裕を持たせた。スカラの葉は段数に数えない。 |
| `MAX_SCHEMA_NODES` | **100** | 宣言時（400） | 深さだけでは `MAX_PROPERTIES`(20) の掛け算で 20^6 まで広がるので、実際の広がりはノード数で抑える。**8 本の API のうち最大のものが 30 ノード程度**（要素オブジェクトの項目数が 10〜15）。その 3 倍強。100 ノードの JSON Schema は 3〜5KB で、8 ツール分をモデルへ渡しても仕様提示のコストに収まる。 |
| `MAX_ARRAY_ITEMS` | **100** | 実行時（ツール実行の失敗） | 業務 API の配列（明細行・サービス項目・分割払い回数）はデモの操作で数件〜十数件。その約 10 倍を天井にする。宣言時ではなく**呼び出しごと**に効く（何件来るかは実行時にしか分からないため）。**切り詰めない**——切り詰めると相手には成功に見えて中身だけ欠ける。 |
| `MAX_PROPERTIES` | 20（既存） | 宣言時（400） | TOOL-01 から据え置き。**各階層に**効かせる（従来は root だけだった）。 |

**判断を仰ぎたいこと（採否の影響）**

| 論点 | 提案どおりにする | 変える場合の影響 |
|---|---|---|
| 深さ 6 | 実測 5 段 + 1 段の余裕。3 段の入れ子が出てきても入る | **下げる（5）**と実測の最深がちょうど天井になり、余裕がゼロ。**上げる（8 以上）**と、モデルが仕様を読み違えたときの被害（間違った形の巨大なボディを相手へ送る）が深くなる |
| ノード数 100 | 実測最大の 3 倍強 | **下げる（50）**と、20 項目の要素オブジェクトを持つ配列が 2 本あるだけで届かない。**上げる（300 以上）**と、8 ツール分の仕様がモデルの入力を圧迫する（1 ツールで 1 万字級） |
| 配列 100 件 | 明細 100 行までの発注が通る | **下げる（20）**と現実的な発注（明細 30 行）が拒否される。**上げる（1000）**と、入れ子配列で 1000×1000 = 10^6 要素の検証が実行前に走る |
| 超過時の扱い | **宣言時 400 / 実行時は失敗**（切り詰めない） | 切り詰めると「相手には 200 で届いたが中身が欠けている」になり、デモの測定対象（エージェントが正しく呼べたか）が汚れる |

**決定（2026-08-02 人間ゲート）: 上表の提案値で確定する。** 実測（最深 5 段 / 最大 30 ノード /
配列は数件〜十数件）に対して余裕を持ち、かつモデルへ渡す仕様が肥大しない範囲に収まっているため。

**実装は上表の提案値で置いてある。値だけを変える場合、変更点は定数 3 行（`http_tools.MAX_SCHEMA_DEPTH` /
`MAX_SCHEMA_NODES` と `tools.MAX_ARRAY_ITEMS`）で、他に波及しない。**

## 非ゴール

- JSON Schema の全機能に対応しない（`oneOf` / `allOf` / `anyOf` / `$ref` / `pattern` / `enum` /
  `minimum` / `additionalProperties` 等は**対象外**）。再帰的な `$ref` を受けると深さ制限も
  ノード数制限も意味を失うため、そもそも受理しない。
- 既存の SSRF 防御・秘密の扱い・TOOL-02 のヘッダ検証は一切緩めない。

## 影響

- DB スキーマの変更なし（`parameters` は既に CLOB）。マイグレーションなし。
- **既存の平坦なツールは挙動不変**（`validate_parameters(平坦)` の戻り値がバイト等価であることを
  回帰テストで固定）。
- GET ツールで入れ子を宣言しようとすると新たに 400 になるが、**従来は型の時点で 400 だった**ので
  「通っていたものが通らなくなる」変化ではない。
