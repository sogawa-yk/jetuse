# ADR-0023: 外部 HTTP ツールの固定ヘッダと、冪等キーは JetUse が発行する

日付: 2026-08-02 / 状態: **Accepted（2026-08-02 人間ゲートで承認。§4 は案 A で確定）** /
関連: TOOL-01（外部 HTTP ツールの導入・`specs/17-demo-platform-redesign.md` §「`agents` の外部ツール」）,
検証: `docs/verification/TOOL-02.md`

## 背景

TOOL-01 は認証を `auth_header` + `auth_secret_ocid`（Vault 参照）の **1 組だけ**送る設計にした。
実案件のデモで、**認証キー / 追跡 ID / 冪等キーの 3 つを必須とする API** に当たり、
JetUse 経由では**登録しても必ず 400 になる**（`MISSING_CORRELATION_ID` / `MISSING_IDEMPOTENCY_KEY`）
ことが判明した。3 つ揃えて手で叩けば 200 になるので、相手の API は正しく動いている。

「ゲートウェイ側で固定値を注入する」回避策は採らない。**冪等キーは呼び出しごとに変わる前提の
仕組み**であり、固定すると同一パスへ異なるボディで 2 回目を呼んだ時点で
`409 IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_INPUT` になる。このデモの測定対象は
「エージェントがエラーから自己修正して呼び直せるか」であり、そこが機構の都合で機械的に
拒否されると**エージェントの能力ではなく仕掛けの制約で失敗する**＝測定値が意味を失う。

## 決定

### 1. 固定ヘッダ（`headers`）を数個添えられるようにする（一般機能として）

認証以外に必須ヘッダを持つ API は一般的にあるので、案件専用の抜け道ではなく登録項目にする。
上限は `MAX_EXTRA_HEADERS = 5` / 値は `MAX_HEADER_VALUE_LENGTH = 200` 文字
（`MAX_TOOLS_PER_AGENT` と同じ流儀で定数化）。

### 2. 冪等キーは **JetUse が呼び出しごとに発行する**（モデルに作らせない）

登録するのは**ヘッダ名だけ**（`idempotency_header`）で、値は登録しない。実行のたびに
`uuid4` を新しく生成して送る。

**なぜモデルに作らせないか。** 番号を作るのは「呼ぶ側」の責任であり、実際に HTTP を出しているのは
JetUse である。モデルに任せると、リトライや会話の再開で**同じ値を使い回す**——これは二重実行防止が
効かなくなる（同じ入力なら握り潰され、違う入力なら 409 になる）ということで、しかも
**モデルの気まぐれで壊れ方が変わる**。ここは決定論に倒す。

これは「引数のテンプレート機構」ではない。`{{...}}` のような一般の置換は**作らない**
（非ゴール）。動的な値は**冪等キーだけを特別扱い**する。

### 3. ヘッダの組み立て順は 固定 → 冪等 → 認証 → Host（後から入るものが勝つ）

固定ヘッダで認証ヘッダや宛先（Host）を上書きできないことを、検証だけでなく**順序でも**担保する。
検証は**登録時と実行時の両方**で行う（登録時だけだと、後から DB を直接触られた場合に素通りする。
秘密の認可を実行時に取り直しているのと同じ理由）。禁止ヘッダ（大小無視）は
`host` / `authorization` / `proxy-*` / `cookie` / `set-cookie` / `content-length` / `content-type` /
`transfer-encoding` / `accept-encoding` / `connection` / `upgrade` / `expect` / `te`
＋ `trailer` / `keep-alive`、および**そのツール自身の `auth_header`**。
値は CR/LF を含まない印字可能 ASCII のみ（ヘッダインジェクション対策）。ヘッダ名は RFC 9110 の
token（区切り文字・制御文字が入らないので、名前側のインジェクションもこれで塞がる。
相手が `X_Trace` や `api.version` を要求することがあるため、認証ヘッダ名より広く取る）。

DB の値が壊れている場合（CLOB を直接書き換えられた・過大）は、読み出しで例外を投げず
**dict でない印**に変え、実行時検証で必ず弾く。壊れた 1 行で一覧 API 全体が 500 になると
「拒否したいもの」が「障害」に化けるため。一覧は `headers_invalid: true` で状態を隠さない。

## 4. 人間の判断を仰ぐ点（固定ヘッダは DB に平文で載る）

固定ヘッダの値は `http_tools.extra_headers`（CLOB）に**平文で保存される**。ここに秘密を書かれると
「秘密は Vault だけ」という TOOL-01 の建前が崩れる。TOOL-01 で受容した「URL 自体が資格情報に
なりうる」（PAR・署名付き URL）と**同じ形の穴**であり、今回は入口が 1 つ増える。

**契約案（本 ADR で提案し、承認を求めるもの）**

- **秘密はヘッダ値に書かない。認証は従来どおり `auth_secret_ocid`（Vault 参照）に限る。**
  固定ヘッダは「追跡 ID・テナント識別子・API バージョン」のような**秘密でない定数**のための口とする。
  これはドキュメント上の契約であり、機構では強制しない（値が秘密か否かは JetUse には判定できない）。
- **一覧 API は値を返さず名前だけ返す**（`header_names`）。

**採否の影響**

| 案 | 影響 |
|---|---|
| A: 名前だけ返す（**実装済みの既定**） | 値が一覧・画面・スクリーンショット・会話履歴に出ない。反面、**登録した値を後から確認できない**（間違ったヘッダ値を入れたときの切り分けは「消して登録し直す」になる）。TOOL-01 で URL を見せる判断をしたこととは非対称。 |
| B: 値も返す（TOOL-01 の URL と同じ扱い） | 切り分けは楽。登録者本人しか見られない点も URL と同じ。ただし**平文の秘密を入れられたとき、それが画面と証跡へそのまま広がる**。TOOL-01 の residual を 1 段悪化させる。 |
| C: 機構で強制（Vault 参照のみ許す・値を暗号化） | 建前と実装が一致するが、本タスクの目的（3 ヘッダ必須の API を呼ぶ）に対して過剰。秘密でない定数まで Vault 登録を強いる。 |

**実装は A（fail-safe な側）で置いてある。B に倒すなら `_public()` の `header_names` を値つきに
戻すだけで、他に波及しない。**

**決定（2026-08-02 人間ゲート）: 案 A を採る。** 利用者がこれから増える段階であり、
**間違いの被害が小さい側**に倒す。切り分けのやりにくさは「消して登録し直す」で回復できるが、
平文の秘密が画面・証跡へ広がるのは回復できない。TOOL-01 の URL 表示との非対称は受容する
（URL は宛先として本質的に必要な情報だが、ヘッダ値はそうではない）。
B へ倒す場合は `_public()` の 1 箇所を戻すだけでよく、本 ADR の改訂で足りる。

## 影響

- マイグレーション `021_http_tool_headers.sql` で `extra_headers CLOB` / `idempotency_header VARCHAR2(64)`
  を追加。**既存行は両方 NULL** で、送るヘッダは 1 つも増えない（挙動不変）。
- 既存の SSRF 防御（https 限定・私設アドレス禁止・IP ピン留め・リダイレクト拒否）は変更しない。
