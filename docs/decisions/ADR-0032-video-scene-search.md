# ADR-0032: 映像を場面単位で分析・検索する（VID-01）

- 状態: 提案（人間レビュー待ち）
- 日付: 2026-08-19
- 関連: [ADR-0028](ADR-0028-four-branch-layout-and-base-check.md)（4ブランチ体制）/
  `specs/13-multimodal.md`（MM-01 映像分析）/
  `docs/comparison/video-scene-analysis-on-oci.md`（比較の正本）

## 背景

映像を登録すると AI が内容を理解して検索用メタデータを付与し、利用者が自然言語や条件指定で
**複数の映像から目的の場面を探せる**ようにしたい、という要求を受けた（2026-08-19）。

要求の核は「映像ファイル単位の検索ではなく、**映像内の特定の場面**を検索し、その時点から
確認できること」。用途は放送素材に限定せず、設備映像・記録映像・過去事例の検索にも使える
汎用機能として定義する。

既存の `/video`（MM-01）は**ステートレス**で、ブラウザで抽出したフレームを視覚モデルに
1回投げて説明させるだけ。保存も検索も無く、今回の要求は満たさない。

## 決定

### 決定1: 分析を2層に分ける（構造化と記述を混ぜない）

| 層 | 使うもの | 取るもの |
|---|---|---|
| 構造化 | OCI AI Vision `video-job` | ラベル・物体・物体追跡・顔・**画面内文字**（**区間つき**） |
| 記述 | 視覚 LLM（gemini-2.5-pro / flash） | 場面説明・行動・天候・時間帯・屋内外・出来事 |

**時刻は必ず構造側から出す。** LLM に「何秒の場面か」を答えさせない。渡していない情報を
作文するため。LLM には「この区間に何が映っているか」だけを聞く。

**AI Vision 層は無くても成立させる。** video-job が大阪／シカゴで受理されるかは未検証
（エンドポイントの応答は確認済み）。使えなければ物体・文字が空になるだけで、場面説明と
ベクトル検索は機能する。**「あるはず」を前提に他を組まない。**

### 決定2: フレーム抽出はサーバ側で行う（`imageio-ffmpeg`）

ブラウザ側抽出（既存 `/video` の方式）は採らない。**要求8 の「再分析の依頼」が成立しない**ため
（元の端末で同じ映像を開き直す必要がある）。複数件の一括登録も現実的でない。

導入は `apt-get install ffmpeg` ではなく **pip の `imageio-ffmpeg`**（静的 ffmpeg 同梱・
manylinux x86_64 wheel 28MB・実測）。`Containerfile` の「変わりにくい層（依存）→ 変わりやすい層
（アプリ）」というレイヤ設計を崩さないため。apt 層を足すと、レイヤ分割で 42分→82秒にした成果
（2026-08-04）を目減りさせる。

### 決定3: 場面の境界は実測から作る

`ffmpeg` の場面転換検出（`select='gt(scene,X)'`）で一次分割し、短すぎる区間を併合、
長すぎる区間を分割する。AI Vision のラベル区間で補正する（同じ画のまま内容が変わる場面に効く）。
**LLM に区切らせない。**

### 決定4: 検索は ADB 23ai のベクトル + 条件を1クエリで

OpenSearch は増やさない（この機能のためだけに常設クラスタを持たない）。Select AI も使わない
（自然言語→SQL であって意味の近さの検索ではない）。

既存 `rag_adb.py` と同じ 23ai のベクトル検索を使い、**ベクトル距離とメタデータ条件を同一の
SQL で扱う**。要求4（自然言語）と要求5（条件絞り込み）を別々の検索系にまたがらせずに済む。
埋め込みは既存の `cohere.embed-multilingual-v3.0`（`embeddings.py` で使用中）。

要求10（類似場面）＝その場面のベクトルで再検索、要求11（根拠表示）＝一致したタグ・距離・
効いた項目を返す。この構成なら追加費用がほぼ無い。

### 決定5: メタデータの出所を必ず区別する

すべてのメタデータに **`source`（`ai` / `human` / `ai_confirmed`）** を持たせる。要求8 の
「AI が自動生成した情報 / 人が入力した情報 / 人が確認・修正した情報」を区別するため。

**AI の結果を確定情報として扱わない。** 認識できなかった項目は埋めず `unknown` として持つ
（要求2 の末尾）。空文字やもっともらしい既定値で埋めると、後から「AI が言ったのか、値が無いのか」
が判別できなくなる。

### 決定6: Public 版に実装する

共有機能であり内部固有ではない。**`public-dev` 起点**で実装し、マージ後に internal へ同期する
（ADR-0028）。DB migration は Public 帯（`0xx_`）。

要求のうち「最初に実現すべき機能」の9項目。

| # | 要求 | v1 |
|---|---|---|
| 1 | 映像登録・管理（複数件） | ○ |
| 2 | AI による内容分析 | ○ |
| 3 | 場面ごとのメタデータ | ○ |
| 4 | 自然言語検索 | ○ |
| 5 | 条件絞り込み | ○ |
| 6 | 該当場面の表示と時刻移動 | ○ |
| 7 | タイムライン表示 | ○ |
| 8 | 人による確認・修正・再分析 | ○ |
| 9 | 映像全体の要約 | ○ |
| 11 | 根拠表示 | ○ |
| 10 | 類似場面検索 | ○（ベクトルが在るため追加費用が小さい） |
| 13 | 画面内文字の検索 | △ AI Vision が使えれば入る。使えなければ視覚 LLM が読んだ文字のみ |

### v1 の外

| # | 要求 | 理由 |
|---|---|---|
| 12 | 音声の文字起こしと発話検索 | 要求側で「最初の必須機能ではない」と整理済み。OCI Speech（`specs/12`）で後続 |
| 14 | メタデータの外部出力（CSV/JSON）・他システム連携 | 一覧表示と JSON 取得までは v1。CSV 出力・外部連携は後続 |
| — | 長時間映像・大量映像の一括処理 | まず短い映像で成立させ、規模は測ってから |

## 影響

- API コンテナに 28MB の依存が増える（依存層のため、アプリ変更時のビルド時間には影響しない）
- Object Storage に映像本体・サムネイルを置くバケットが増える
- ADB に表が増える（Public 帯 `022_`〜）
- AI Vision を使う場合、動的グループとポリシーに `ai-service-vision-family` の権限追加が要る
  （**IAM 変更は人間の承認ゲート**）

## 未解決

- AI Vision `video-job` の可用性・課金・所要時間（未検証。使えない場合の縮退は設計済み）
- 画面内文字（テロップ）の日本語精度は AI Vision と視覚 LLM のどちらが実用に足るか（実測して決める）
- 映像の同時実行数と Container Instance 4GB での上限
