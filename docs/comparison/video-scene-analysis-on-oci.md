# 映像を場面単位で分析・検索する — OCI 上の選択肢の比較

映像を登録すると AI が内容を理解して検索用メタデータを付与し、利用者が自然言語や条件で
**複数映像を横断して目的の場面を探せる**機能（VID-01）を作るにあたり、OCI 上でどう実装するかを比較する。

> **用途を放送素材に限定しない。** 設備映像・記録映像・過去事例の検索にも使える汎用機能として設計する。
> 「場面（時間区間）が第一級の検索対象である」ことがこの機能の核で、映像ファイル単位の検索とは別物。

## 1. 「映像から何が映っているかを取り出す」層

| 方式 | 取れるもの | 時刻情報 | 状況 |
|---|---|---|---|
| ~~OCI AI Vision `video-job`~~ | — | — | **使えない（2026-08-20 実測）**。大阪・シカゴとも `create_video_job` が 404 `NotAuthorizedOrNotFound`。同じ資格情報で `analyze-image` は成功するので**権限ではなく機能が無い**（下記「video-job の実測」） |
| **OCI AI Vision `analyze-image`**（フレーム単位） | ラベル / 物体 / 顔 / 画面内文字 | こちらが持つフレーム時刻を使う | 使える（実測）。ただし**日本語の文字は読めない**（下記「画面内文字の実測」） |
| **視覚 LLM（gemini-2.5-pro / flash）にフレームを渡す** | 自然言語の場面説明・行動・天候・屋内外・出来事 | **なし**（渡したフレームの時刻はこちらで持つ） | 大阪で画像入力・複数画像とも動作確認済み（MM-01・実測） |
| OCI Document Understanding | 文書画像の文字・表 | なし | 静止画・文書向け。映像用ではない |
| OCI Media Services (Media Flow) | トランスコード・パッケージング | — | 変換・配信が目的。内容理解はしない |

### なぜ片方では足りないのか

**AI Vision だけでは「雨の中でリポーターが話している場面」を検索できない。** ラベルは
`person` `umbrella` `road` のような語彙に閉じており、要求4 の例（豪雨 → 強い雨・傘を差した人物・
濡れた路面）のような**意味の近さ**を扱えない。

**視覚 LLM だけでは時刻が出ない。** LLM に「何秒の場面か」を答えさせると、渡していない情報を
作文する。要求3・6 の中核は「何分何秒付近か」なので、時刻は**こちらが管理する構造**から出す必要がある。

→ **両方使う。** 構造化された事実（物体・文字・時刻）は AI Vision、意味の記述は LLM。
これは「どちらが優れているか」ではなく**役割が違う**という判断。

## 2. 「フレームをどこで切り出すか」

場面説明を LLM に書かせるには、その場面の**代表フレーム**が要る。

| 方式 | 長所 | 短所 | 判定 |
|---|---|---|---|
| **A. サーバ側 ffmpeg**（`imageio-ffmpeg`） | 再分析できる／まとめて登録できる／場面転換で切れる／音声も取り出せる（将来の文字起こし） | 依存が 28MB 増える（実測: manylinux x86_64 wheel） | **採用** |
| B. ブラウザ側 canvas（既存 `/video` の方式） | サーバに依存が要らない | **要求8 の「再分析の依頼」が成立しない**（元のクライアントが要る）／複数件の一括登録が現実的でない／等間隔にしか切れない | 不採用 |
| C. OCI Media Flow でサムネイル生成 | マネージド | ワークフロー定義・ジョブ管理が増える。フレーム抽出だけのために導入するには重い（未検証） | 不採用 |

**B を採らない決め手は要求8。** AI の結果を人が確認・修正し、**再分析を依頼できる**ことが要件に
入っている。ブラウザ側抽出だと、再分析のたびに元の端末で同じ映像を開き直す必要があり、
「登録済みの映像を後から別モデルで解析し直す」ができない。

**apt ではなく pip で入れる。** `imageio-ffmpeg` は静的ビルドの ffmpeg を同梱した wheel なので、
`Containerfile` の「変わりにくい層（依存）→ 変わりやすい層（アプリ）」というレイヤ設計を崩さない。
`apt-get install ffmpeg` を足すと依存層が別系統になり、レイヤ分割で 42 分 → 82 秒にした成果
（2026-08-04）を目減りさせる。

## 3. 「場面をどう区切るか」

| 方式 | 内容 | 判定 |
|---|---|---|
| **等間隔** | N 秒ごとに機械的に切る | 単独では不採用（場面転換をまたぐ） |
| **ffmpeg の場面転換検出** | `select='gt(scene,X)'` で画の変化点を取る | **採用（一次分割）** |
| **AI Vision の区間** | ラベル・物体の出現区間 | **採用（補正）**。転換検出が拾えない「同じ画のまま内容が変わる」場面に効く |
| LLM に区切らせる | フレーム列を見て境界を答えさせる | 不採用。時刻の作文を招く |

**転換検出で切り、短すぎる区間を併合し、長すぎる区間を分割する**。境界は必ず実測の時刻から作り、
LLM には「この区間に何が映っているか」だけを答えさせる。

## 4. 「検索をどう実現するか」

| 方式 | 意味の近さ | 条件絞り込み | 根拠の提示 | 判定 |
|---|---|---|---|---|
| **ADB 23ai ベクトル検索＋SQL 条件** | ○（埋め込み） | ○（同一の表を WHERE で絞る） | ○（一致したタグ・距離を返せる） | **採用** |
| OpenSearch | ○ | ○ | ○ | 不採用（この機能のためだけに常設クラスタを増やさない） |
| Select AI | △ | ○ | △ | 不採用（自然言語 → SQL であり、意味の近さの検索ではない） |

既に RAG で `rag_adb.py` が 23ai のベクトル検索を使っており、**同じ DB の中でベクトル距離と
メタデータ条件を1つの SQL で扱える**。要求5（条件絞り込み）と要求4（自然言語）を
**別々の検索系にまたがらせずに済む**のが決め手。埋め込みは既存の
`cohere.embed-multilingual-v3.0`（日本語対応・`embeddings.py` で使用中）をそのまま使う。

要求10（類似場面）と要求11（根拠表示）は、この構成なら追加費用がほぼ無い。
類似は「その場面のベクトルで再検索」、根拠は「一致したタグ・距離・どの項目が効いたか」を返すだけ。

## 5. 採用する構成

```
登録  ─→ Object Storage（映像本体）
          │
          ├─→ ffmpeg: 場面転換検出 → 区間 → 代表フレーム / サムネイル
          │              │
          │              └─→ 視覚 LLM（gemini-2.5-pro）
          │                    → 場面説明・行動・天候・屋内外・出来事（不明は不明のまま）
          │
          └─→ OCI AI Vision video-job
                 → ラベル / 物体 / 画面内文字（区間つき）
                            │
                     ┌──────┴──────┐
                     ▼             ▼
              場面メタデータ    埋め込み（cohere multilingual v3）
                     └──────┬──────┘
                            ▼
                   ADB 23ai（ベクトル + 条件を1クエリで）
                            ▼
        検索 → 場面（開始/終了・サムネイル・説明・一致理由）→ その時刻から再生
```

## 5.5. 実測（2026-08-20・本テナンシ）

### video-job の実測 — **使えない**

```
oci ai-vision video-job create ... --region us-chicago-1
  → 404 NotAuthorizedOrNotFound (POST .../20220125/videoJobs)
oci ai-vision video-job create ... --region ap-osaka-1
  → 404 NotAuthorizedOrNotFound
```

**404 だけでは「機能が無い」のか「権限が無い」のか判らない**（OCI は存在を漏らさないため
403 を 404 で返す）。切り分けのため**同じ資格情報で `analyze-image` を叩いたところ成功した**。
したがって ai-vision へのアクセス自体は通っており、**video-job という機能が無い**と判断できる。

→ 構造化層は `video-job` ではなく、**こちらが抽出したフレームに対する `analyze-image`** で行う。
時刻はフレーム抽出側が持っているので、「時刻は必ず構造側から出す」という原則（ADR-0032 決定1）は
そのまま満たせる。

### 画面内文字の実測 — **日本語は視覚 LLM が必要**

`大阪 OSAKA 12:34` を焼き込んだテロップ相当のフレーム（800x450）で比較した。

| 方式 | 読み取り結果 | 判定 |
|---|---|---|
| AI Vision `TEXT_DETECTION` | `XRR OSAKA 12:34` | **日本語が壊れる**。英字・数字は正確 |
| `gemini-2.5-pro` | `大阪 OSAKA 12:34` | 正確 |
| `gemini-2.5-flash` | `大阪 OSAKA 12:34` | 正確 |

要求13 の例は「**大阪**と書かれたテロップ」「地名」「人名」であり、**日本語が主対象**。
AI Vision の TEXT_DETECTION では要求を満たせない。**画面内文字は視覚 LLM に読ませる。**

英字・数字（機器のエラーコード・時刻表示・型番）は AI Vision も正確なので、
設備映像・記録映像の用途では併用に意味がある。

### 埋め込みの実測 — 意味の近さは成立する

`cohere.embed-multilingual-v3.0`（1024 次元）で、要求4 の例（「豪雨」で検索したときに
「強い雨」「傘を差した人物」「濡れた路面」が候補に出るか）を実測した。

| 「豪雨」との cos 類似度 | 場面説明 |
|---|---|
| **0.501** | 傘を差した人物が濡れた路面の前で話している。屋外・雨天・夜 |
| 0.408 | 赤い乗用車が交差点を通過する。屋外・昼 |
| 0.345 | スタジオで複数人が着席して会話している。屋内・照明あり |

**語が一致しなくても意味で引ける**ことは確認できた。ただし**差は 0.09 程度しかない**。
絶対値のしきい値で足切りすると、無関係な場面を通すか、正解を落とすかのどちらかになる。
**順位で見て、しきい値で切らない**（切るなら実データで決める）。

## 6. 未検証として残すもの

- **`analyze-image` の物体検出が実写でどれだけ効くか。** 単色・テロップだけのフレームでは
  物体が 0 件だった（当然）。実写での有用性は実映像で測る。視覚 LLM の記述と重複するなら、
  AI Vision 層を残す意味そのものを問い直す。
- 長時間映像・大量映像での所要時間とコスト。初回は短い映像で成立させ、規模は後続で測る。
- フレーム1枚ごとに `analyze-image` を呼ぶ場合の課金と所要時間（場面数×呼び出し回数）。
- **ADB 23ai の `VECTOR_DISTANCE` と `WHERE` を1クエリで評価する経路（決定4）は未実測。**
  `VECTOR(1024, FLOAT32)` 列が実 ADB に作られることは VID-01 の E2E で確認済みだが、
  距離＋条件の同時評価そのものは VID-04 の E2E で確かめる。
