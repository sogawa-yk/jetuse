# 比較: OCI Generative AI のどのモデルがエージェントを動かせるか

**問い**: 「複雑な業務 API を、モデルに順番どおり呼ばせて手続きを完了させたい。
OCI ではどのモデルを選べばよいか。」

- 測定日: **2026-08-03** / リージョン **`us-chicago-1`**(比較のため `ap-osaka-1` も同条件)
- 測定した実体: OCI Enterprise AI の **OpenAI 互換 Responses API**(agentic API)
- 生データと手順: `docs/verification/AGT-06.md` / `spikes/agt06/`

> **すべて実機の測定値。** カタログや資料からの引き写しは含めていない。
> 提供状況はテナンシ・コンパートメント・時期で変わるため、**採用前に測り直すこと**
> (手順は `docs/verification/AGT-06.md` §9)。

---

## 1. 結論(先に)

1. **エージェント(client-side tools を使う自律的なツール呼び出し)が成立するのは
   Responses API に対応したモデルだけ。** OCI の同一エンドポイントに載っていても、
   Chat Completions しか通らないモデルが多い(Llama 系・Cohere 系は当コンパートメントで
   Responses が 404)。
2. **シカゴでは 8 モデルがエージェントとして動く**(gpt-oss ×2 / Grok ×3 / Gemini ×3)。
   大阪では Grok 系が無いため 5 モデル。**モデルを比べたいならシカゴ。**
3. **「Responses が通る」と「エージェントとして使える」は別。** 同じ Responses API でも
   **受け付ける入力アイテムの形が違う**(§3)。差を吸収する層を挟まないと、
   最初の 1 往復は通っても**ツール結果を返した次の往復で 400 になる**。
4. **モデルの大小は多段の手続きの成否に直結する。** 軽量モデル(`gpt-oss-20b`)は
   3 試行中 2 回**ツールを 1 度も呼ばず**、利用者に聞き返して終わった(§4)。
5. **名前から能力を推測しない。** `xai.grok-4.20-reasoning` は名前に反して
   `reasoning effort` パラメータを 400 で拒否する。

## 3. 同じ API でも入力の形が違う(実装で吸収が要る)

エージェントを回すには、毎ターン「これまでの履歴 + 出したツール呼び出し + その結果」を
積み直して送る。**この積み直しの受け付け方がモデルで違う。**

| 差 | 影響を受けるモデル | 症状 | 吸収の仕方 |
|---|---|---|---|
| `role=system` の入力アイテム | **Gemini 全て** | `400 Content with system role is not supported` | 役割だけ `user` へ移す(本文は変えない) |
| 返した `function_call` を `id` 付きで積み直す | **Gemini 全て**(`stream=True` のときだけ) | `400 did not match any variant of untagged enum ResponseInput` | `id` を落とす(`call_id` は残す) |
| client-side tools 自体 | `grok-4.20-multi-agent` | `400 Client-side tools ... require beta access` | **吸収不能 → 要求時に断る** |

**`id` の差はストリーミング限定**。非ストリーミングで検証すると通ってしまい、
本番(SSE で流す)で初めて落ちる。**検証は本番と同じ stream で行うこと。**

**吸収できない差は「そのモデルではエージェント不可」として登録簿に持たせ、
選択された時点で理由つきで断る**設計にした。黙って動かないより断るほうがよい。

### 3.1 非 OpenAI モデルには project ヘッダが要る

Gemini / Grok は `OpenAi-Project` ヘッダが**必須**
(無いと `400 Non-OpenAI models require 'OpenAI-Project'`)。
**project OCID はリージョン別**で、大阪の project をシカゴへ送ると `400 Invalid OpenAI project`。
= **使うリージョンごとに GenerativeAiProject を用意する。**

## 4. 定量比較 — 多段の業務手続きを完了できるか

「1 本のツールを呼べるか」ではモデル差は出ない。**戻り値を次の呼び出しに使わないと
完了できない手続き**を用意して測った(`spikes/agt06/compare.py`)。

- `order_context_initialize` が正しい品番 `PX-9001` を返す
- **`product_search` にはその品番が出てこない**(デコイだけが出る)
- `set_product` は正しい品番でしか成功しない → `confirm_order` で完了
- 満点 = ツール 3 呼び出しで完了

**8 モデル × 3 試行(計 24 回)**:

| モデル | 完了 | 順序平均(3.0満点) | 平均呼出 | 検索 | 架空の品番 | 拒否 | 平均秒 |
|---|---|---|---|---|---|---|---|
| `gpt-oss-120b` | **3/3** | 3.0 | 3.0 | 0 | 0 | 0 | 4.0 |
| **`gpt-oss-20b`** | **1/3** | **1.0** | **1.0** | 0 | 0 | 0 | 3.5 |
| `grok-4.3` | **3/3** | 3.0 | 3.0 | 0 | 0 | 0 | 5.0 |
| `grok-4.20-reasoning` | **3/3** | 3.0 | 3.0 | 0 | 0 | 0 | 7.6 |
| `grok-4.20-non-reasoning` | **3/3** | 3.0 | **4.3** | 1 | 0 | **3** | 4.8 |
| `gemini-2.5-pro` | **3/3** | 3.0 | 3.0 | 0 | 0 | 0 | **11.8** |
| `gemini-2.5-flash` | **3/3** | 3.0 | 3.0 | 0 | 0 | 0 | 5.4 |
| `gemini-2.5-flash-lite` | **3/3** | 3.0 | 3.0 | 0 | 0 | 0 | **4.1** |

**読み取り**

- **軽量モデルは多段に耐えない。** `gpt-oss-20b` は 3 回中 2 回、**ツールを一度も呼ばず**
  「どの品番を設定しますか？キーワードを教えてください」と聞き返して終了した。
  デモで観測した「実行せず手順書を返す」壊れ方と同じで、**これはモデル差**である。
  一覧には出しても**既定にはしない**。
- **この難度では上位 7 モデルに差がつかない。** 最短経路をそのまま踏む。
  つまり**「業務 API を捌けるか」は、この程度の手続きならモデル選定の争点にならない。**
  争点になるのは**速度・コスト・画像対応・可用性**のほう。
- `grok-4.20-non-reasoning` だけ手数が多い(平均 4.3 呼出・拒否 3 回)。ただし
  **拒否されたあと自力で正しい品番へ戻れている**(自己修正あり・全試行完了)。
  「間違えるが直せる」個体で、承認モードでは往復が増える分だけ利用者の手数も増える。
- `gemini-2.5-pro` は正しいが**最速の約 3 倍遅い**。品質差が出ない手続きでは選ぶ理由が薄い。
- **架空の品番を作ったモデルは 24 試行中 0。** デモで起きた捏造はこの難度では再現しない
  → **より長い手続き・より多い候補で再測が要る**(この比較の限界)。

> **限界**: n=3。順位を断定できる数ではない。**傾向として読むこと。**
> また「完了できるか」は測ったが、**業務的な正しさの質**(報告文の妥当性など)は測っていない。

## 5. 用途別の選び方(この測定から言えること)

| 用途 | 候補 | 理由 |
|---|---|---|
| 多段の業務手続き(既定用途) | `gpt-oss-120b` / `grok-4.3` | 3/3 完了・最短経路・4〜5 秒 |
| 速度優先(短い対話) | `gemini-2.5-flash-lite` / `gpt-oss-20b` | 3.5〜4.1 秒。ただし 20b は**多段不可** |
| 画像を伴う手続き | `grok-4.3` / `gemini-2.5-*` | エージェント可 **かつ** 画像可はこの 4 つだけ |
| reasoning effort を出し分けたい | `gpt-oss-120b` / `gpt-oss-20b` / `grok-4.3` | 他は 400 |
| **選んではいけない** | `gpt-oss-20b`(多段) / `grok-4.20-multi-agent` / Llama・Cohere 系 | §2・§4 |

**既定モデルは `xai.grok-4.3` に決定**(2026-08-03 人間ゲート・ADR-0027 §5-A)。
完了率では上位 7 モデルに差が無く、争点は速度・画像対応・可用性だった。
`grok-4.3` は完了 3/3・平均 5.0 秒・**画像対応**・`reasoning effort` 対応で、
大阪を完全撤去(§5-B)する判断と整合する。**この比較はその材料である。**
`gpt-oss-120b` は一覧に残り、要求で選べる。

## 6. 他クラウドから来た人への読み替え

| よくある前提 | OCI での実際 |
|---|---|
| 「同じ OpenAI 互換エンドポイントなら、どのモデルでも同じ形で呼べる」 | **違う**。system ロール・ツール結果の積み直しの受け付け方がモデルで異なる(§3) |
| 「モデル一覧に出ている = 使える」 | **違う**。一覧にあって Responses が 404、非推奨日を過ぎている、がある(§2.1) |
| 「リージョンは近い方を選べばよい」 | **モデルの品揃えがリージョンで大きく違う**。Grok 系はシカゴのみ(§2.1) |
| 「project は 1 つ作れば全リージョンで使える」 | **リージョン別**。他リージョンの project を送ると 400(§3.1) |
| 「TTS/OCR も同じリージョンで揃う」 | **揃わない**。TTS はシカゴ・大阪とも不可で Phoenix のみ可(`docs/verification/AGT-06.md` §6) |
