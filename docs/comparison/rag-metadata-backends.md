# RAG メタデータ管理の実現方式比較 — 外部ベクタストア vs Select AI 索引 vs AI Database 自前索引

日付: 2026-07-28（ap-osaka-1 実機計測。プリセールス転用可）
計測条件: Oracle AI Database 26ai（23.26.3.1.0）/ 架空の日本語チャンク 10 件（うち旧版 3 件）/
埋め込み `cohere.embed-multilingual-v3.0`（1024次元）/ 同一クエリ「在庫照会APIのレート制限と
1回の最大取得件数を教えて」/ 各 5 回・中央値。生データは `docs/verification/SPIKE-M1.md`。

> 想定読者: 「RAG の出典をどこまで細かく出せるか」「古い版を検索から外せるか」を
> 顧客に説明する場面。**外部ベクタストアでも属性フィルタはできる**（ここは誤解されやすい）。
> 差が出るのは粒度と、業務データ・トランザクション・権限との統合である。

## 一覧

| 観点 | ① OCI Vector Store + file_search | ② Select AI 索引（DBMS_CLOUD_AI） | ③ AI Database 自前索引（DBMS_VECTOR_CHAIN） |
|---|---|---|---|
| **絞り込みの表現力** | `eq` / `and` / `or` / `gte`（`in` は 422 で不可）。キーは最大 16・値 512 文字・文字列/数値/真偽のみ。存在しないキーはエラーにならず 0 件 | 標準経路に絞り込みの口が**無い**。`$VECTAB` へ列を足して自分で SQL を書けば可 | **SQL の WHERE すべて**。JOIN・サブクエリ・範囲・LIKE・日付関数・業務表との結合が全部使える |
| **出典の粒度** | **ファイル単位**。1 ファイルが 5 チャンクに割れると 5 チャンクとも同じ属性。チャンク本文・スコア・chunk_id は返る | ファイル単位（object_name + start/end offset）。応答末尾に `Sources:` の**文字列**として付き、スコアは無い | **チャンク単位**。列に持てば何でも返せる（file/version/sheet/cells/sha256/kind/…） |
| **メタデータの持たせ方** | `attributes`（登録時・更新時に API で付与） | 固定 6 キーのみ（object_name / object_size / last_modified / location_uri / start_offset / end_offset）。任意キーは `ORA-20048` で拒否 → **オブジェクト名に埋め込む**しかない | 列 + `JSON` 列。スキーマありもスキーマレスも同居 |
| **メタデータの更新** | `files.update(attributes=)` で可（再取り込み不要） | 索引リフレッシュで**入った新規行は自前列が NULL**。取り込みのたびに補完処理が要る | `UPDATE` 1 文。検索と**同一トランザクション** |
| **レイテンシ（検索のみ）** | 121.5 ms | 69.3 ms（`$VECTAB` 直接） | 16.7 ms（埋め込み済みベクタ。別途 埋め込み API 84.5 ms が要る）／192.7 ms（DB 内埋め込み込みの 1 本 SQL） |
| **レイテンシ（生成込み）** | 4324 ms | 3276 ms | 該当なし（③ は検索のみ担当） |
| **実装コスト** | **最小**。JetUse は既に稼働（`rag.py`）。属性を付けて `results[].attributes` を拾うだけ | 中。索引作成は 1 コールだが、任意メタデータのために命名規約 + 列追加 + 補完ジョブを自作する | 中〜大。表設計・チャンク化・埋め込み・索引・取り込みを自前で組む（`DBMS_VECTOR_CHAIN` が部品を提供） |
| **運用の重さ** | 軽い（マネージド。取り込みは非同期・10 ファイルで約 60 秒） | 中（refresh_rate のバケット同期。既定 60 分＝反映が遅い） | 中（自分で入れるので即時。索引メンテは DB 任せ） |
| **DB 要件** | なし | ADB 23ai 以上 | ADB 23ai 以上（`VECTOR` 型・`DBMS_VECTOR_CHAIN`） |
| **本文をどこに置くか** | OCI 側（Files API） | Object Storage + ADB 内ベクタ表 | **保管は ADB 内のみ**。ただし DB 内埋め込み(`UTL_TO_EMBEDDING`)は本文を OCI GenAI の `embedText` へ送る＝**テナント外に出ないわけではない**。アプリ層を経由しない、が正確な利点 |
| **業務データとの結合** | 不可（別サービス） | 実質不可（$VECTAB は DB 内だが用途が索引） | **可**（在庫表・契約表と JOIN したベクタ検索が 1 SQL） |
| **アクセス制御** | ストア分離 / IAM | DB 権限 | DB 権限。VPD / Data Redaction は同じ表に対する DB 機能なので原理的には併用できるが、**本スパイクでは未実証**（SKIPPED.md 3 参照） |

## どこで差がつくか（提案の軸）

1. **チャンク単位の出典が要るか**。「この回答は仕様書 v2.0 の『制約』シート C5:E5 が根拠」まで
   出すなら、① は 1 チャンク = 1 ファイルに割る運用が必要になる（ファイル数がチャンク数になる）。
   ③ は列に持つだけ。Excel の行・セル単位まで遡る要件があるほど ③ が効く。
2. **「今の版だけ」を保証したいか**。① でも `eq` フィルタで実現できる。ただし
   タイポしたキーは **エラーにならず 0 件**になるので、ガードはアプリ側の責任になる。
   ③ は `NOT NULL` 制約や CHECK でスキーマ側に寄せられる。
3. **業務データと混ぜるか**。「在庫が 10 個未満の商品の仕様だけを検索」のような、
   ベクタ検索と業務表を結合する要求は ③ でしか 1 クエリにならない。ここが
   Oracle AI Database の本来の主張点であり、外部ベクタストアでは原理的にできない。
4. **メタ更新と検索の一貫性**。③ は同一トランザクション。① は API 更新で結果整合。
5. **本文の経路を短くしたいか**。③ + DB 内埋め込みなら、本文の保管も検索も ADB 内で完結し、
   アプリ層に本文を持ち出さずに済む。ただし埋め込み時に本文は OCI Generative AI の
   `embedText` エンドポイントへ送られる（実装で確認済み）。「一切外に出ない」ではない。
   完全に閉じたい要件なら DB 内で完結する埋め込み手段が別途必要になる。

## 数字の読み方（誠実な但し書き）

- **3 方式とも同一の 10 チャンクを見ている状態で計測している**（計測前に各方式から chunk_id を
  取り出して一致を実測確認。揃わなければ計測しない）。
- 10 チャンクという極小データでの計測である。③ の 16.7 ms は 10 行の全件走査であり、
  実行計画上もベクタ索引は使われていない（オプティマイザが厳密検索を選択）。
  **件数が増えたときの傾きは未計測**で、この表を「大規模でも ③ が速い」とは読めない。
- **③ の 16.7 ms と ① の 121.5 ms を直接比べない。** ③ の 16.7 ms はクエリの埋め込みを含まず、
  埋め込み API 単体が 84.5 ms かかる。同じ土俵（テキストを渡して結果が返るまで）では
  ③ 約 101 ms（クライアント埋め込み）／192.7 ms（DB 内埋め込み）に対し ① 121.5 ms でほぼ同じ。
  実行ごとの揺れも大きいため、**この規模では速度差を方式選択の根拠にしない**
- ローカル macOS → ap-osaka-1 の往復を含む。配備済み Container Instance からの数字ではない。
- ① の生成込み 約 4.3 秒（実行により 3.4〜5.0 秒）はモデル（gpt-oss-120b）の推論時間が支配的で、検索方式の差ではない。

## 制約・前提（実機で確認したもの）

| 方式 | 制約 |
|---|---|
| ① | 属性はファイル単位／キー 16・値 512 文字・入れ子不可／`in` フィルタ不可／Vector Store は CP 作成後 DP へ伝播するまで files 系が 404 |
| ② | `CREATE_VECTOR_INDEX` の `attributes` は索引設定であってチャンクのメタではない（任意キーは `ORA-20048`）／`$VECTAB` 列追加はリフレッシュで欠損／走行中パイプラインは前景実行不可（`ORA-20044`） |
| ③ | 資格証明は `DBMS_VECTOR_CHAIN.CREATE_CREDENTIAL` で作る必要あり（`DBMS_CLOUD` のものは引けず `ORA-20003`）／取り込みパイプライン（抽出・チャンク化・投入）は自前 |

## 一言でいうと

- **① で足りるケースは実際にある**（ファイル単位の出典 + 版フィルタで十分なら追加開発ほぼゼロ）。
- **チャンク単位の出典・業務データとの結合・トランザクション整合・VPD** のどれかが要件に入った
  瞬間に ③ 以外の選択肢が消える。ここが「メタデータ管理は AI Database が強い」の実体である。
- ② は「バケットに置くだけで RAG」が価値であり、メタデータ管理の基盤としては選ばない。

## JetUse としての採用（ADR-0020 / 2026-07-29 承認）

**どちらか一方を選ばず、性格の違う 2 つを「選べる」形で提供する。**

| | 手軽さ側 | 高機能側 |
|---|---|---|
| 実体 | ① Enterprise AI マネージド Vector Store（既定） | ③ Oracle AI Database 自前索引 |
| 向く場面 | すぐ見せたいデモ、文書 Q&A | 業務データと絡む提案、監査が要る用途 |
| 出典 | ファイル単位（1チャンク=1ファイルにすればチャンク相当） | チャンク単位（セル範囲・行番号） |
| 絞り込み | `eq`/`and`/`or`/`gte` | SQL の WHERE 全部・JOIN |
| 兼用 | — | **Agent Memory の格納先としても同じ土台を使う** |

提案の場では「**Oracle AI Database を選ぶと何が増えるか**」を示せることが肝になる。
そのため JetUse 側でも、選択中のバックエンドで使える機能・使えない機能を
API（`GET /api/capabilities`）と画面の双方で明示する（ADR-0020 §3）。
