## 1. 実案件で見つかった経緯

実案件のデモ（業務 API 8 本を順に呼ぶ受付フロー）を実環境で走らせたところ、
**手続きが最後まで通らなかった**。エージェントに 8 本の HTTP ツールと文書検索を渡し、
手順を書かずに依頼した結果の実測は次のとおり:

| 事実 | 値 |
|---|---|
| 業務 API の呼び出し | 6 回（うち成功 4・自己修正 1） |
| 文書検索（`rag_search`）の呼び出し | 約 40 回 |
| 到達点 | 8 本中 4 本。**ホップ上限に当たって停止**（診断のため一時的に 30 へ上げた状態で） |

見つかったのは 2 つで、**どちらも「エージェントに業務 API を渡す」という看板機能に直結する**。

1. `MAX_TOOL_HOPS = 5` が固定で、API 8 本の手続きには足りない（入口にも届かない）。
2. エージェント経路の文書検索が Vector Store の `file_search` built-in だけで、出典が
   **ファイル単位**にとどまる。ADR-0020 が「Oracle AI Database ならチャンク単位で出せる」と
   決めた能力が、エージェント経路では使えなかった。

さらに、上限に当たったときの挙動が「ツールなしで最終回答を強制する」だけで、
**途中で力尽きたのか答え切ったのかが応答から区別できなかった**。
デモの画面で「なぜ途中で止まったか」を出せないと、失敗の説明ができない。

## 3. ホップ数の実測（既定値の根拠）

同じ要求（API 6 本の受付フロー。手順は書かず、順序とコード値は仕様書から引かせる）:

| 条件 | 到達した業務 API | モデル往復（最終回答含む） | 入力トークン計 | 出力トークン計 | 打ち切り通知 |
|---|---|---|---|---|---|
| `max_tool_hops=5`（旧固定値と同じ） | **2〜3 / 6** | 6（= 5 + 最終回答 1） | 20,467 | 1,995 | `{"reason": "max_tool_hops", "limit": 5}` が応答に出る |
| 既定（設定値） | **6 / 6**（`confirm_reception` まで・毎回） | 9〜14（ホップ 8〜13） | 55,233（10 ホップの回） | 1,954（同） | **なし**（自力で完了） |

- **旧固定値では入口で止まる**ことが、実案件だけでなく縮小版の手続きでも再現した。
- 同じ要求を 8 回流して **8 / 10 / 13 / 10 / 11 / 9 / 11 / 10 ホップ**。モデルの出方には揺れがあるので、
  既定値は平均ではなく**観測した最大値に対する余裕**で決める必要がある。
  なお `runs/.../e2e/` に残るのは**最後の 1 回（10 ホップ）**の証跡である
  （同じスクリプトを再実行すると証跡ファイルが上書きされるため）。
- API 8 本へ線形に伸ばすと 11〜17 ホップ相当。既定 **24** はその 1.4〜2.2 倍。
- **上限はツールを渡した往復の数**で、上限到達時の「ツールなしの最終回答」はその外側の
  1 往復（1 要求の最大往復数は上限 + 1）。この往復の `usage` も出す
  —— 出さないと**打ち切ったターンだけコストが記録から漏れる**。
- **コスト**: 上表のとおり、往復が 1.8 倍（6 → 11）で入力は **2.7 倍**（20,467 → 55,233）。
  エージェントはステートレス（全履歴再送）で、ツール仕様も毎回載るため、
  **出力は線形・入力は概ね二次**で効く。この伸び方を延ばすと 24 ホップ・ツール 8 本では
  入力 20 万〜30 万トークン規模になりうる（**外挿であって実測ではない**）。
  上限を上げるのは「止まらないための保険」であって、常用でここまで回る想定ではない。

**上限に当たったことは応答から分かる**（`scenario-1.md`）。構造化イベント
`{"notice": …, "limit_reached": {"reason", "limit"}}` と、同じ文面の `delta` の両方が出る
（現行 UI は `notice` を描かないため。ADR-0025 §3）。

## 4. 検索回数の実測 —— **見立ては誤りだった**

起票時の見立ては「出典がファイル単位だからエージェントが同じ文書を何度も引き直す（約 40 回）。
チャンク単位にすれば減る」だった。**同じ文書・同じモデルでバックエンドだけを変えて測ったところ、
減らなかった**（`scenario-3.md`）。

| 問い | vector_store（ファイル単位） | adb（チャンク単位） |
|---|---|---|
| 複数の事実をまとめて聞く（順序・プラン・支払・工事枠の 4 点） | **1 回** | **1〜2 回**（実行により変動） |
| 1 つの値と出典を聞く | **1 回** | **1 回** |

- 各条件 **1 回ずつ**の実測なので、「増える／減る」を統計として言える強さは無い。
  それでも「減った」と書ける材料は無いので、**減らなかったとそのまま記録する**。
  計測は 2 度行い、1 度目は「複数の事実」で adb が **2 回**（vector_store は 1 回）＝
  むしろ多かった。残っている証跡（`scenario-3.md`）は 2 度目のもので、両問い 1 対 1 である。
- 起票時の約 40 回は、この検証用の小さな仕様書（8 チャンク・3 シート）では再現しなかった。
  実案件は API 8 本で仕様書も大きいため文書の規模が効いている可能性はあるが、
  **それはこの検証では確かめていない**（数字を作らない）。
- 派生の観測: 検証の途中、**答えが文書に無い問い**（「受付番号 ORD-8801 で使うプランコードは？」
  ——文書に受付番号とプランの対応は無い）を built-in の `file_search` に投げたところ、
  同一応答内で **7 回以上**検索を繰り返し、かつ**本文を 1 文字も返さなかった**。
  約 40 回はこの形（答えの無いものを探し続ける）に近いかもしれないが、
  **対照実験ではない**ので原因の証拠としては扱わない。

**結論**: adb バックエンドを足す価値は「**根拠がセルまで辿れること**」であって、
「検索回数が減ること」ではない。ADR-0025 の根拠から後者は落とした。

## 5. チャンク単位の出典が実際に返ること

`agent_rag_backend="adb"` のエージェント実行で、ツール結果と `citations` の両方に
チャンク単位の出典が載った。**5 / 5 件がシート名とセル範囲を持つ**。

```
"source": {"chunk_id": "…-2", "chunk_no": 2, "file": "…受付フロー仕様書.xlsx",
           "version": "1.0", "sheet": "コード", "cells": "A1:C4", "kind": "spec",
           "current_version": "Y"}
```

モデルの最終回答にも出典がそのまま出た（「シート名: **コード** / セル範囲: **A1:C4**」）。
従来の built-in 経路（シナリオ4）は同じ文書でも `{file_id, filename, score}` までで
`source.cells` を持たない —— ADR-0020 が示した能力差を、エージェント経路でも選べるようになった。
