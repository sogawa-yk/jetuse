## 実環境で見つかった経緯(なぜこのタスクが必要になったか)

TOOL-01 の `validate_parameters` は `ALLOWED_PARAM_TYPES = ("string","number","integer","boolean")`
だけを受理していた。実案件のデモで業務 API を登録しようとしたところ、**8 本のうち 6 本が
登録すらできなかった**。

| 相手の API | 必要な形 | TOOL-01 時点 |
|---|---|---|
| 受付可否 | スカラー 1 個 | 登録できる |
| 注文コンテキスト初期化 | スカラー 2 個 | 登録できる |
| 契約者情報設定 | オブジェクト 1 段 | **不可** |
| お届け予定日取得 | オブジェクトの配列 + スカラー | **不可** |
| 受取方法設定 | オブジェクト 1 段 + スカラー | **不可** |
| 商品設定 | オブジェクトの配列 | **不可** |
| サービス情報設定 | **配列の中に配列**(2 段) | **不可** |
| 分割払い情報設定 | オブジェクトの配列 + スカラー | **不可** |

実測の応答(推測ではない):

```
入れ子オブジェクト → 400 「引数 <名> の type は string/number/integer/boolean のいずれかです」
配列              → 400 同上
平坦なスカラーのみ → 200 登録できる
```

このデモの趣旨は「**SoR の API 仕様が複雑すぎるので、AI に仕様書を読ませて正しく呼べるかを
確かめる**」ことである。JetUse が複雑なボディを表現できないと、**複雑な API ほど渡せない**という
逆転が起きる。測定したい能力の手前で、機構の都合が上限を作っていた
(ADR-0023 の「仕掛けの制約で失敗すると測定値が意味を失う」と同じ構図)。

## 何ができるようになったか

```
POST /api/agent/http-tools
  parameters: { "type": "object", "properties": {
      "order_id": {"type": "string"},
      "items": {"type": "array", "items": {          # ← オブジェクトの配列
        "type": "object", "properties": {
          "sku": {"type": "string"}, "qty": {"type": "integer"},
          "options": {"type": "array", "items": {    # ← 配列の中の配列(2 段)
            "type": "object", "properties": {"code": {"type": "string"}},
            "required": ["code"]}}},
        "required": ["sku", "qty"]}}},
    "required": ["order_id", "items"] }
```

**ただし「検証しきれる形しか通さない」方針は変えていない。** TOOL-01 の設計意図は正しく、
未対応の JSON Schema キーワードを素通しすると「モデルには制約に見えるが、実行前検証は何も
していない」状態になり、そちらの方が危険である。したがって受理するのは**実行時に同じ強さで
検証できる形**だけとした。

- `object` は `properties` を持つこと(自由形式は受理しない)。root だけ従来どおり省略可。
- `array` は `items`(単一スキーマ)を持つこと。タプル形式の `items` は受理しない。
- 未対応キーワード(`enum` / `pattern` / `oneOf` / `$ref` 等)は**各階層で落とす**。
- 実行前検証も再帰にし、**未知キーの拒否・型検査・`required` を各階層で**効かせる。
  配列は要素ごとに `items` で検査する。
- 上限(超過は**黙って切り詰めない**): 深さ 6 段 / 全体 100 ノード / 各階層 20 引数
  (以上は登録時に 400)/ 配列の要素 100 件(実行時にツール実行の失敗)。
- **GET には入れ子を宣言できない**(登録時に 400)。GET にはボディが無く、入れ子をクエリ文字列へ
  載せる標準の書き方が無いため。JetUse が勝手な符号化を決めると「送ったつもりの形と相手が読む形が
  違う」という、検証をすり抜ける壊れ方になる。

## 設計上の判断(なぜこの形か)

### 1. 宣言側と実行側の「強さ」を一致させる

本タスクの核はここにある。宣言(`http_tools.validate_parameters`)だけを再帰にして実行前検証
(`tools._validate_args`)を平坦なままにすると、**内側は何を入れても通る**——TOOL-01 が避けた
「制約に見えて素通し」が、階層の内側で再発する。両方を同時に再帰にし、未知キー・型・`required` を
各階層で同じ関数群が見るようにした。

### 2. 上限は「深さ」だけでなく「ノード数」で抑える

深さだけを制限しても、各階層の引数上限(20)の掛け算で 20^6 まで広がる。実際の広がりを抑えるのは
ノード数の方である。逆にノード数だけだと、細長い入れ子が無制限に深くなる(再帰の深さがそのまま
実行前検証の再帰の深さになる)。両方を置いた。値の根拠と、判断を仰ぐ論点は
**ADR-0024 §3**(この節が人間ゲート)。

### 3. 上限超過は切り詰めない

配列の要素数超過を切り詰めると、**相手には 200 で届いたのに中身だけ欠ける**。発注明細で言えば
「頼んだつもりの行が消えた発注」が成立してしまう。TOOL-01 が応答サイズ上限で採った
「上限超過は黙って切り詰めず失敗にする」と同じ扱いに揃えた。

### 4. GET は断る(符号化を発明しない)

入れ子をクエリ文字列へ載せる標準は無い。`a[0].b=` / `a=<JSON>` / `a=1&a=2` のどれを選んでも
相手の実装次第で、外れれば「JetUse は送ったつもり、相手は読めていない」になる。
検証をすり抜ける壊れ方なので、**宣言の時点で断る**方に倒した(実行時にも `str(dict)` を送らない)。

### 5. 改ざんされたスキーマで実行しない(review-1 の VAL-001)

`parameters` は CLOB なので、DB を直接書き換えられれば未知の `type` や `properties` の無い
`object` も入りうる。素朴に書くとそこが**素通り**する(スカラ検査のどの条件にも一致せず、
未検証の値が相手の業務 API へ飛ぶ)。実行時も「検証できない宣言は通さない」に倒した。
