# AGT-05 検証レポート — 文書検索をツール往復（ホップ）の予算から外す

日付: 2026-08-02 / 対象: `packages/api/jetuse_core/chat.py`（エージェントループ）・`settings.py` /
決定: **ADR-0026**（本タスクの決定。上限値と「同じ検索の繰り返し」は2026-08-02 人間ゲートで承認済み）・

証跡: `runs/2026-08-02T1942_AGT-05/e2e/`

> ファイル名について: `docs/verification/AGT-05.md` は**別の AGT-05**（2026-06-11 の
> 「長期メモリ統合」）が既に使っている。チケット ID が再利用されているため、

## 1. 何が起きていたか（実案件の実測。推測ではない）

チャンク単位の出典（`agent_rag_backend=adb`）を選ぶと `rag_search` は **function tool** になり、
**1 回の検索が 1 ホップを消費**していた。実案件のデモ（API 8 本の受付フロー・仕様書 8 冊・
ホップ上限は既定 24）を 3 回実行した結果:

| 実行 | 文書検索 / 全ツール呼び出し | 業務 API 成功 | 自己修正 | 打ち切り |
|---|---|---|---|---|
| 1 | **20 / 24** | 0 | 0 | `max_tool_hops` |
| 2 | **22 / 24** | 1 | 0 | `max_tool_hops` |
| 3 | **19 / 24** | 2 | 1 | `max_tool_hops` |

**3 回とも上限で打ち切り。予算 24 のうち 19〜22（約 8 割）が検索**で、業務 API に回せたのは
4〜5 回分だけだった。エージェント自体の振る舞いに誤りは無い（先頭 2 本を正しい順序で呼び、
422 から自己修正し、409 の順序違反から前段へ戻っている）。**足りないのは予算の配分**である。

従来の `vector_store` 経路（`file_search` built-in）は OCI 側が 1 応答の中で検索するので
**ホップを消費しない**。同じ「文書を調べる」操作が、出典を細かくした途端に業務の予算を食う
—— 能力の対価ではなく、実装形態が予算に漏れていただけの**不整合**だった。

### ADR-0025 の前提の誤り（記録として残す）

ADR-0025 §1 は既定値 24 を「1 ステップ = 検索 1 + API 1」で置いた。実測は **1 API あたり
検索 3〜5 回**（前提の 3〜5 倍）。§2 は「function tool はホップを消費する」を副作用として
認識していたが、**影響の大きさを見誤っていた**。AGT-04 の E2E が API 6 本・仕様書 1 冊
（8 チャンク）の縮小版で、検索が 1 問あたり 1〜2 回にとどまっていたためである。
実案件では 1 本の API を呼ぶ前に順序・コード値・制約を**別々の本から**引き直すので、
検索回数は API の本数ではなく**引くべき事実の数**に比例する。詳細は ADR-0025 §6。

## 2. 直し方（何を変えたか）

**数える対象を変えた。値は変えていない**（ホップ上限の既定 24 / 天井 48 は据え置き。AGT-05 の非ゴール）。

| | 変更前 | 変更後 |
|---|---|---|
| ホップを消費するもの | ツールを渡した往復すべて | **業務の操作**（外部HTTPツール・MCP・組込ツール）を含む往復だけ |
| adb 経路の `rag_search` | 1 回 = 1 ホップ | **別枠**（`AGENT_MAX_DOC_SEARCHES`） |
| `vector_store` 経路（built-in） | 消費しない | **消費しない**（挙動不変） |
| 承認往復の累計上限 `max(16, ホップ上限)` | 検索も数える | **検索は数えない** |
| 検索の上限に達したとき | （上限が無かった） | `rag_search` だけ外して**手続きは続ける**。`limit_reached{reason=max_doc_searches}` で通知 |

- **切り詰めない**: 上限を跨いだ回のバッチは全件実行して結果を返す（出した `function_call` に
  結果を返さないと Responses の入力契約が壊れ、「調べたのに結果が来ない」状態を作る）。
  そのぶん実際の検索回数は上限をわずかに超えうる。
- **上限後に呼ばれた検索は実行せず理由を返す**（ツール一覧から外してもモデルが名前を出す
  ことはある。実行すると上限が空振りする）。その往復は業務の操作と同じ扱いでホップを消費する
  ＝ 必ず止まる。
- **承認往復では送り返された `tool_results` から検索回数を引き継ぐ**（0 から数え直すと、
  累計上限からも外した検索に歯止めが無くなる）。あわせて要求ボディの `tool_results` の
  件数枠を「ホップ天井 + 検索天井」まで広げた（検索を別枠にした以上、ここが 48 のままだと
  検索を挟む承認往復が予算判定に届く前に 422 で詰まる）。
- **上限値は 2026-08-02 の人間ゲートで承認済み**（既定 40 / 天井 80）。ADR-0026 §2 は Accepted。
  承認前は「新しい policy の数値を勝手に決めない」ため、承認済みのホップ上限の数値（24 / 48）を
  暫定として流用していた。承認に伴い `settings.py` の 2 行を差し替えた。
- **1(b) が本題の証明**である。1(a) は検索 7 + 業務 8 = 15 で、旧来の数え方でも既定 24 には
  収まった（**この題材は実案件より軽い**。仕様書 3 冊 vs 8 冊）。そこで同じ要求を
  **予算 10 ホップ**に絞って流したところ、検索 8 回を挟みながら 8 本すべてに到達した ——
  旧来なら 16 ホップ必要で、入口の数本で力尽きていた数である。
- **シナリオ2 で検索の呼び出しは 4 回、実際に走ったのは 3 回**（上限 3）で、4 回目は
  **実行されず理由が返った**（「文書検索の回数が上限(3 回)に達したため実行できません」）。
  上限が空振りしないこと（ADR-0026 §既知の限界）が実環境で確認できた形である。
  一方 **「上限を跨いだ*同一バッチ*を切り詰めない」（ADR-0026 §3）はこの実行では起きていない**
  —— モデルが 1 往復に複数の検索を出さなかったため。こちらはユニットテストで固定している
  （`SKIPPED.md` §4）。
- **呼び出し順序は判定条件に入れていない**（記録はする）。tasks/AGT-05.md のシナリオ1 が
  求めるのは「打ち切られずに**最後まで到達**」であり、順序は要求していない。実際、
  同じ要求を 5 回流すと順序は run ごとに揺れた（`set_billing` や `add_equipment` が
  `set_service_plan` の前に来た実行がある）。**AGT-05 が変えたのは予算の数え方**であって、
  呼ぶ順の作り込みは AGT-04 の主題なので、揺れる指標を完了ゲートに入れない
  —— **判定条件を後から緩めたのは事実なので明記する**（最初はチケットより厳しく
  「順序どおり各 1 回」を条件にしていた）。最終実行では (a)(b) とも順序も仕様書どおりだった。
- シナリオ3 の**引用イベントは 0 件**だったので、「引用がファイル単位のままか」は
  **この実行では確認できていない**（`all([])` が真になる空虚な PASS を作らないよう、
  0 件のときは判定から外した）。この経路の引用形式は AGT-04 のシナリオ4 で確認済み。

## 4. 人間ゲートで決まったこと（2026-08-02）

ループは値を決めず ADR に書いて止め、承認後に実装へ反映した。

1. **文書検索の上限値**（ADR-0026 §2）→ **既定 40 / 天井 80 で確定**。
   根拠は実測「1 API あたり 3〜5 回 × 8 本 = 24〜40」の**上端**。
   上限に達しても手続きは死なないので、余らせるより届かせる側に倒した。
   承認前は新しい数値を入れず、承認済みの 24 / 48 を流用して動かしていた。
   承認に伴い `settings.py` の 2 行を差し替えた。
   代償: 1 ターンの往復数の上界が `ホップ上限 + 検索上限 + 1` に上がる
   （コストは往復数に対して概ね二次）。
2. **同じ検索の繰り返しの扱い**（ADR-0026 §4）→ **案 B（検知して知らせる）で確定・実装済み**。
   表記ゆれ（前後の空白・大小・連続空白）だけの違いは同じ検索とみなし、2 回目以降に
   `notice` と `repeated_search` イベントを出す。**結果はそのまま返す**。
   引数を解析できないものは反復判定の対象にしない（判定できないものを「同じ」と決めつけない）。
   案 C（抑止）は却下 — モデルが「調べた」と思ったまま結果を得られず、記憶で埋めてしまう。

## 5. 残る限界

- ホップの予算はこれまでどおり **1 要求のうち**の往復数で、承認モードでは要求ごとに数え直す
  （ADR-0025 §1 の既知の限界）。検索の予算はクライアントが送り返した分だけ引き継げる。
- 検索を別枠にしたので、**1 ターンの往復数の上界は上がった**（ホップ上限 + 検索上限 + 1）。
  「止まらないための保険」であって常用の想定ではないが、上限値を決めるときの前提になる。
- 既定値 40 が実案件に足りるかは**まだ測っていない**（顧客資産を検証環境に持ち込まないため）。
  承認後に実案件で測る。実施しなかった範囲は `runs/2026-08-02T1942_AGT-05/e2e/SKIPPED.md`。
