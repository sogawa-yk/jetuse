# PREP-03 検証レポート — スキャン PDF・画像を取り込み経路へ結線する（OCR）

**結論**: スキャン PDF（テキスト層なし・日本語）と画像を取り込むと、中身が検索でヒットし、
引用に**ページ番号が構造化された値**（`source.sheet = "p.2"`）で載る。テキスト層のある PDF は
**OCR を 1 度も呼ばない**（実測: 呼び出し回数 0）。既定エンジンは **Document Understanding**、
VLM は利用者の明示指定のみ（自動では切り替えない）。

**この結論の範囲**: 検証はプロセス内 ASGI からローカルの `config_file` 認証で行った（相手の
OCI Document Understanding / Generative AI / ADB はすべて実物）。**配備先（Resource Principal）での
OCR 認可（動的グループへの `use ai-service-document-family`）は未検証**で、IAM は本タスクの
禁止事項につき触っていない（§10-1・人間ゲート）。また**生成回答が識別子を忠実に写すことは保証しない**
（§7。実行ごとに揺れる）。

dev コンパートメント・ap-osaka-1。証跡は `runs/2026-08-01T1033_PREP-03/e2e/`。

## 1. 何を結線したか（OCR 実装は作り直していない）

OCR 本体（`jetuse_core/docunderstand.py`。ENH-07 / 07b / 07g）は既にあり、`POST /api/ocr` から
だけ使えて**取り込み経路と繋がっていなかった**。足したのは判断と配線だけ:

| 追加 | 中身 |
|---|---|
| `jetuse_core/extract_scan.py`（新規） | いつ OCR を通すか / どのページを出すか / ページ番号つきの本文へ並べ直す |
| `rag.ALLOWED_EXTENSIONS` | `.png` / `.jpg` / `.jpeg` を追加（画面側 `uploadFormats.ts` も同時に更新） |
| `rag.prepare_upload` | 画像・テキスト層の無い PDF は OCR したテキストをマネージド Vector Store へ渡す |
| `rag_adb._segments` | PDF / 画像を `extract_scan` 経由にし、出典を `p.N` にする（PDF は元からこの語彙） |
| `rag_opensearch._extract_text` | 同上（画像を UTF-8 デコードして文字化け本文を索引に入れない） |
| ルート（`/api/rag/files` / `/api/extract`） | `ocr_engine` の明示指定・上限超過 422・サービス障害 503 |

`docunderstand` への変更は**加算のみ**: 返り値に `pages`（ページごとの行）を足し、上限超過を
`OcrLimitError`（`OcrError` の派生）に分けた。ページごとの行が無いと「何ページ目の本文か」が
失われ、出典にページ番号を付けられない。既存キー・既存の呼び出し側の挙動は変えていない。

## 2. OCR を通すかどうかの判定根拠（推測しない）

**ページ単位で、`pypdf` の `extract_text()` が空白以外を返すか**だけで決める。
ファイル名・生成ソフト・埋め込み画像の有無といった推測材料は使わない。

- テキスト層のあるページ → そのまま使う（**OCR を呼ばない = 課金しない**）
- テキスト層の無いページ → **そのページだけ**を 1 本のサブ PDF にまとめて OCR へ出す
- 画像（png/jpg/jpeg）→ 常に OCR（1 ページ扱い）

混在 PDF（一部だけスキャン）で読める分を課金しないのはこの設計による。
テストで固定: `packages/api/tests/test_extract_scan.py::test_pdf_with_a_text_layer_never_calls_ocr`
/ `test_only_pages_without_a_text_layer_are_sent_to_ocr`。

**実測（対照シナリオ）**: 同じ内容のテキスト層つき PDF を抽出・取り込みの両方に通し、
`docunderstand.ocr` / `ocr_vlm` を数えるラッパで包んで測ったところ、**どちらも 0 回**
（`e2e/scenario-3.md`）。それでも本文は従来どおり検索で引けている。

## 3. エンジンの既定は Document Understanding（判断根拠）

| 観点 | Document Understanding | VLM（ビジョン LLM） |
|---|---|---|
| 日本語テキスト | 高精度（SPIKE-E4: char recall 100% / mean conf 0.994。本 E2E でも 0.991 / 0.974） | 読めるが**厳密 OCR ではない**（生成なので言い換え・欠落がありうる） |
| 日本語の表 | **英語のみ**（全リージョン。SPIKE-E4） | 読める |
| 呼び出し回数 | 5 ページ/回（超過はサーバ側で分割。ENH-07b） | **1 ページ = 1 LLM 呼び出し** |
| 実測の所要 | 2 ページ 3.4 秒 / 1 画像 1.9 秒 | 1 画像 11.2 秒 |

**採用: DU を既定**。理由は 3 つ:

1. このタスクの目的は「本文が検索に出ること」であり、**表構造の復元は明示的な非ゴール**。
   VLM の唯一の優位点（日本語の表）は、いま買う価値が無い。
2. 取り込みは**全ページを必ず読む**処理なので、ページ単価がそのままコストになる。
   VLM はページごとに LLM を呼ぶため、ページ数に比例して高くつく（実測でも 6 倍の時間）。
3. 索引に入れる本文は**原文に忠実**であるべきで、生成モデルの言い換えを混ぜたくない。

**切り替えは利用者の明示指定のみ**（`ocr_engine=vlm`）。自動判定にはしない —
「表があるか」「日本語の表か」を OCR **前に**知る手段が無く、判定材料をでっち上げることになる
（推測で切り替えない、というタスクの要求そのもの）。誤った名前（`vlmm` 等）は**黙って既定へ
落とさず 422**（「VLM で読んだ」と誤解したまま結果を受け取るのを防ぐ）。
VLM 経路が実機で通ることは付録シナリオで確認済み（`e2e/scenario-4.md`）。

表の抽出（`tables=True`）は**要求していない**。本文検索が目的で、DU の表機能はページ単価が
別に掛かる。

## 4. 出典の位置情報は既存キー `sheet` に載せる（属性キーを増やさない）

`rag_metadata.ATTRIBUTE_KEYS` は 8 個（上限 16）。**`page` は足さなかった**:

- `rag_adb` は PDF の出典に**元から `p.N` を `sheet_name` 列へ入れている**（RAGM-02）。
  `page` を足すと同じ位置情報が 2 通りになり、絞り込みをどちらで書くかが分かれる。
- 新キーは ADB 側の列追加（マイグレーション）と `FILTER_COLUMNS` の拡張も伴う。
  得られるものは「`p.` という接頭辞が要らなくなる」だけで、割に合わない。

粒度はバックエンドで違う（ADR-0020 の決定内容そのもの。隠さない）:

| バックエンド | スキャン PDF・画像の出典 |
|---|---|
| `adb` | **チャンク単位**。`sheet="p.2"` + 行範囲 `L1:L9` |
| `vector_store`（マネージド） | **ファイル単位**。`sheet="p.1-p.3"`（そのファイル全体の範囲） |

**実測**: 2 ページのスキャン PDF で、2 ページ目にしか無い語を問うと、引用は
`sheet="p.2"` で返った（`e2e/scenario-1.md`）。画像は `p.1`（`e2e/scenario-2.md`）。

## 5. 上限（切り詰めずに 422）

| 上限 | 値 | detail の `limit=` |
|---|---|---|
| OCR に出すページ数 | 100（`docunderstand.MAX_TOTAL_PAGES`） | `ocr_pages` |
| 1 画像のバイト数 | 8MB（DU の inline 上限。画面の案内も 8MB に揃えた） | `ocr_bytes` |
| 抽出後の総文字数 | 200 万字（`rag_adb.MAX_EXTRACT_CHARS` と同値） | `extract_chars` |
| `docunderstand` 側の上限（総バイト・総ページ） | 60MB / 100 ページ | `ocr_input` |
| アップロード全体 | 20MB（`rag.MAX_BYTES`。従来どおり 413） | — |

上限超過は**切り詰めない**（PREP-01 / RAGM-01 と同じ規律。黙って一部だけ取り込むと
「取り込めたのに根拠が出ない」と区別が付かない）。実測: 上限を 1 ページに落として 2 ページの
スキャン PDF を投げると 422 で
`OCR が要るページ数が上限を超えました(2 > 1 ページ)。ファイルを分割してください (limit=ocr_pages)`。

画像は **OCR へ送る前にこちらでデコードして確かめる**（PNG / JPEG の先頭バイト + 全体の
デコード）。壊れた画像を OCI へ投げると 400 が返るが、400 は compartment 指定ミス等でも返るため、
それを「入力が悪い」と断定できない（＝利用者の壊れたファイルがサービス障害として 503 に見える）。
判る分はこちらで判ってから送る。

**OCR の要否判定と本文の変換は分けてある**。判定（`needs_ocr`）はページを 1 枚ずつ見て
テキスト層の無いページを 1 つ見つけた時点で打ち切り、本文を保持しない。ここに文字数上限を
掛けると、テキスト層が揃った巨大な PDF が急に 422 になり、**従来の素通しを壊す**。

ページ数・文字数の上限は**読みながら**見る（全ページを展開しきってから数えない）。空ページだらけの
小さな PDF で「拒否するために全ページ読む」時間とメモリを使わないため。

**本文が 1 文字も取れない入力（白紙・判読できない紙面）は 422**。抽出口 `POST /api/extract` と
取り込み口の**両方**で同じ扱いにする（片方だけ 200 / `chunk_count=0` を返すと、同じ入力に対して
入口ごとに挙動が違う）。一部のページでも本文があれば取り込む（読めたページを白紙 1 枚のために捨てない）。

**OCR サービス側の失敗（IAM 未整備・障害）は 503**。利用者の入力の問題ではないので 422 にしない。
IAM 未整備（`use ai-service-document-family` 未付与）はここに出る。

## 6. 二重 OCR をしない（課金の話）

1 回のアップロードは最大 3 経路（マネージド変換 / ADB チャンク化 / OpenSearch）が同じ本文を
読む。素朴に書くと同じスキャン文書を 3 回 OCR に出す＝ 3 倍課金される。
`extract_scan` は内容ハッシュ + エンジン + 形式で直近の結果を覚え、**1 リクエスト内では
1 回に抑える**。
同じ文書の**同時要求も 1 本に束ねる**（single-flight。覚えるだけだと、キャッシュに入る前に来た
2 本目が同じ OCR を走らせる）。結果をキャッシュへ入れてから待ち手を起こす順序と、先行者が失敗した
場合に待ち手が計算役を引き継ぐことを単体テストで固定した。
実測: 2 ページのスキャン PDF のアップロードで OCR 呼び出しは **1 回**（`e2e/scenario-1.md`）。

**保証の範囲はプロセス内まで**。worker / コンテナが複数あると、同じ文書が同時に別プロセスへ
振り分けられた場合は OCR がその数だけ走る（分散ロックは入れていない）。防いでいるのは
「1 リクエストの中で 3 経路が同じ文書を読む」重複＝ 3 倍課金であり、そこがこの機構の目的。
配備全体での重複排除が要件になったら ADB を使った分散ロックを別途検討する（→ 残課題）。

## 7. 実機で分かったこと（Tips へも転記）

**DU の日本語 OCR は英数字の連なりに空白を挟むことがある。**

```
原本: 交換部品コード: BRG-7781      → OCR: 交換部品コード: BRG - 778 1
原本: ロット番号: LOT-2026-0518     → OCR: ロット番号: LOT - 2026 - 0518
原本: 冷却ポンプ P-204              → OCR: 冷却ポンプ P - 20 4
```

文字自体は落ちていない（mean confidence 0.99）が、**チャンク本文も空白入りのまま保存される**
（`BRG - 778 1`）。原文そのままではなく、**空白を除けば原文と一致する**という状態である。
日本語の語によるベクタ検索は当たる（実測）。

**ただし生成回答の識別子の忠実性は保証されない（実行ごとに揺れる）**: 同じ入力・同じ手順で
2 回測ったところ、「交換部品コードは?」への回答は 1 回目が `BRG-778`（末尾の `1` が欠落）、
2 回目が `BRG-7781`（一致）だった。空白で切れた `BRG - 778 1` を生成側がどう読むかの揺れである。
つまり本タスクが実証したのは「スキャン文書の本文が検索でヒットし、出典にページ番号が載る」ことで
あって、「生成回答が識別子まで忠実に写す」ことではない。**型番の完全一致検索**（`LIKE '%BRG-7781%'`）
も当たらない。E2E の判定は空白を無視した比較で行い、生の OCR 出力と当該回答を証跡に残した
（出力を書き換えて癖を隠さない）。→ 残課題（§10-3）。

## 10. 残課題

1. **配備先（Resource Principal）での OCR 認可**。動的グループに
   `use ai-service-document-family` が要る。ローカルの `config_file` 認証では通ったが、
   配備先では未確認。IAM は本タスクの禁止事項なので触っていない（人間ゲート）。
   承認・適用後に、配備済み API へスキャン PDF と画像の 2 シナリオを再実施すること。
2. **`select_ai` バックエンドはスキャン PDF・画像を索引化できない**（DB 側が原本を読む方式で
   アプリの OCR を通らない）。バッジが `pending` のままになる。扱いを決めるには実測が要る
   （PREP-01 → PREP-02 で「実測なしに恒久 `error` にした」のを撤回した経緯があるため、
   同じ轍を踏まない）。
3. **英数字トークンの空白と、生成回答の識別子の忠実性**（§7）。型番の完全一致検索・
   識別子を含む回答が要件になったら、前処理側の正規化（比較用の別値を持つ）か
   生成側の逐語引用のどちらで解くかを決める必要がある。**このタスクでは実装していない**
   （OCR 出力を書き換えると「原文に何が書いてあったか」が失われるため、独立した判断が要る）。
4. **`opensearch` 経路は実機未確認**（この環境では無効）。単体テストのみ。
5. **OCR の重複排除はプロセス内まで**（§6）。複数 worker / コンテナ構成で同じ文書が同時に
   来た場合の重複は防いでいない。必要になったら分散ロック（ADB）を検討する。
