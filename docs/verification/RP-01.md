# RP-01 検証レポート: 開発環境の DB 内資格情報をリソースプリンシパルへ統一

- 日付: 2026-07-29
- 決定の正本: [ADR-0021](../decisions/ADR-0021-dev-resource-principal.md)（Accepted）
- 対象: 共有 loop ADB（`jetuse-loop-adb` / Oracle AI Database 26ai 23.26.3.1.0 / ap-osaka-1 /
  コンパートメント `jetuse:dev`）。**ADB は増やしていない**。検証用スキーマ（run 固有名 `JETUSE_RP01D389`）で隔離し、
  検証後に削除した。
- 証跡: `runs/2026-07-29T1605_RP-01/e2e/`（`scenario-1..4.md` / `guard.md` / `teardown.md` /
  `post-teardown-state.md` / `terraform-validate.log` / `SKIPPED.md` / 実行に使った `driver.py`）。
  ログ中の OCID・ネームスペース・リージョンは `spikes/spike_m1/redact_evidence.py` で
  伏字化してある（規約: 実値をコミットしない）。原本の `*.log` は `.gitignore` 対象。

## 何を変えたか

`ops/setup-select-ai.py` / `ops/setup-dev-schema.py` から **`~/.oci/config` の手書きパース（4 箇所）と
`DBMS_CLOUD.CREATE_CREDENTIAL` 呼び出しを削除**し、`DBMS_CLOUD_ADMIN.ENABLE_RESOURCE_PRINCIPAL`
に置き換えた。バグを直したのではなく、**バグのあったコードを無くした**。

```console
$ grep -rn '\.oci/config\|CREATE_CREDENTIAL' ops/
（該当なし）
```

あわせて、DB 内資格情報の既定を `OCI$RESOURCE_PRINCIPAL` に寄せた
（`settings.select_ai_credential` の既定値 / `infra/terraform/environments/app` の env 注入 /
`.env.example`）。ローカル Python プロセスの OCI 認証（`AUTH_MODE`）は変更していない。

両スクリプトの共通部は `ops/_adb.py` に集約した。ここに **DDL 前の fail-closed ゲート
`assert_target()`** を置いてある（下記 E2E の項）。このため ops スクリプトの実行には
`.env` の `ADB_OCID` と `ADB_COMPARTMENT_OCID`（無ければ `COMPARTMENT_OCID`）、および
OCI API への到達性が要る（未設定・不一致ならスキーマを 1 つも作らずに中止する）。
ADB が階層の子コンパートメント（例 `jetuse:dev`）にある環境は `ADB_COMPARTMENT_OCID` を
`.env` に置く。雛形は `.env.example`。

## 実機で確認した前提（read-only）

| 確認項目 | 結果 |
|---|---|
| `ENABLE_RESOURCE_PRINCIPAL(username => X)` の実体 | X のスキーマに資格情報を作るのではなく、**ADMIN 所有の `OCI$RESOURCE_PRINCIPAL` へ EXECUTE を付与**する。よって `DBA_CREDENTIALS` に X の行は出ず、`DBA_TAB_PRIVS`（grantee=X / table_name=`OCI$RESOURCE_PRINCIPAL`）で確認する |
| 再実行 | エラーにならない（**PL/SQL 側で冪等**）。スクリプト側に「既に有効なら飛ばす」分岐は不要 |
| IAM | 変更していない。動的グループ `jetuse-internal-dg` とポリシーは既存のまま通った（ADR-0021「実機で確認した事実」どおり） |

> ハマりどころ: 切り分けに使う `DBMS_CLOUD.SEND_REQUEST` の `/n/<ns>/b/`（ListBuckets）は
> **`?compartmentId=<OCID>` が必須**で、付け忘れると認証と無関係に HTTP 400 になる。さらに
> `.env` の `COMPARTMENT_OCID` は親の `jetuse` を指しており、リソースプリンシパルのポリシーは
> `jetuse:dev` に閉じているため、親を指定すると正しい設定でも ORA-20404 になる。
> 切り分けでは「権限があるはずのコンパートメント」を明示すること（`docs/tips.md` に追記済み）。

## E2E シナリオと実結果

実行は `runs/2026-07-29T1605_RP-01/e2e/driver.py`（**1→guard→2→3→4→teardown を通しで 1 回**。
否定テストを索引・バケット作成の前に置くことで「止まらなければ消えていたはずのもの」を絞って観測する）。
接続とセットアップは成果物 `ops/_adb.py` をそのまま使う＝検証が本番経路を通る。
DDL・破壊操作の前に fail-closed の三重ゲートを通す:

1. `_adb.assert_target()` — **同一性と認可**の 2 つ。
   - 同一性: その SQL 接続が `.env` の `ADB_OCID` と同一 ADB か。ADB Serverless の
     `DB_NAME = <インスタンス固有トークン>_<db_name>` を使い、トークンが当該 ADB の接続文字列に
     現れることまで照合する（表示名一致では同名の別 ADB を弾けない）。
   - 認可: その ADB が `.env` の `ADB_COMPARTMENT_OCID`（無ければ `COMPARTMENT_OCID`）
     **そのもの**にあるか（OCID の完全一致）。名前はテナンシをまたいで一意でないので根拠にせず、
     「承認済みの配下ならどこでも」も許さない（親を承認済みにしている環境では兄弟・子孫まで
     通ってしまう）。`ADB_OCID`・ウォレット・OCI プロファイルが揃って別環境を指していても止まる。
2. ドライバ側 `assert_loop_adb()` — 承認済みの根（`.env` の `COMPARTMENT_OCID`）の直下から
   `dev` の OCID を引き、ADB のコンパートメントと完全一致することを見る。確認できた OCID を
   `ADB_COMPARTMENT_OCID` として ops サブプロセスへ渡すので、1 と 2 は同じ値で照合する。
3. ドライバ側 `verify_owned()` — 触ろうとしているスキーマが**この run が作ったもの**か。
   根拠は `ops/setup-dev-schema.py --receipt <path>` が **`CREATE USER` と同じ PL/SQL ブロックで
   取得して**書く作成証跡
   （`DBA_USERS.USER_ID` / 作成時刻 / この実行が作ったかの別）。`USER_ID` は DROP して同名で
   作り直すと必ず変わるので、秒精度の作成時刻では区別できない「同じ秒での作り直し」も検出できる。
   ドライバは**いま在るユーザーを推測で取り込まず**、この証跡だけを根拠に台帳化する。
   証跡は CREATE 直後にあるので、後続（権限付与・リソースプリンシパル有効化・マイグレーション）が
   失敗しても、作ったものが孤児にならずに片付けられる。
   台帳 `created-resources.json` にユーザーの作成時刻と、スキーマ内に置いた
   **この run 固有の乱数マーカー**（`RP01_RUN_MARKER` 表）を記録し、**破壊操作の前に**
   ADMIN 接続で照合する。一致しなければスキーマへ接続すらせずに中止する。照合は
   開始時だけでなく **`DROP USER` の直前にも両ユーザー分やり直す**（索引やバケットの削除中に
   同名ユーザーが作り直される TOCTOU を塞ぐ）。1 件でも合わなければ 1 件も消さない。

**検証が作る資源の名前はすべて run 固有**（`rp01<乱数4>` → `JETUSE_RP01XXXX` /
`jetuse-spike-rp01xxxx-rag` など）。固定名だと「事前に無い」と確認してから作るまでの間に
同名を作られたとき、他人のものを自分の所有物として台帳へ取り込みうる（TOCTOU）。一意名なら
衝突自体が起こらず、それでも既存なら中止する。作成の競合（409）や結果不確定は**台帳へ入れない**
＝自動削除の対象にしない。

所有証跡は**作成直後**に台帳へ書く（ユーザーの識別値を先に永続化し、マーカーは INSERT 成功後に
追記。CREATE TABLE の暗黙コミットで順序が入れ替わらないようにする）。バケットは名前ではなく
etag と作成時刻で同一性を見る。削除できたものは台帳から落とす。
ゲート 3 が実際に効くことは否定テスト（`guard.md`）で確認している。

## 単体テスト / lint

```console
$ .venv/bin/pytest packages/api/tests
381 passed
$ .venv/bin/ruff check packages/api ops spikes
All checks passed!
```

実環境 E2E は「正しい接続先で成功する」経路しか通らないので、**通ってはいけない経路**は
`packages/api/tests/test_ops_adb.py`（38 件）で押さえた: `ADB_OCID` 未設定 / トークン不一致 /
`DB_NAME` が `<token>_<db_name>` 形式でない / **承認済みコンパートメントと一致しない**
（同名の `jetuse/dev` 階層を持つ別テナンシも、承認済みの**子**コンパートメントも拒否。
`ADB_COMPARTMENT_OCID` での上書きも承認済みの根の配下でなければ拒否）/
`COMPARTMENT_OCID` 未設定 → いずれも DDL を実行せず `SystemExit`。接続後の `call_timeout` は 0 以下を拒否（無期限待ちを作らない）。
`settings.select_ai_credential` の既定が `OCI$RESOURCE_PRINCIPAL` で、env で旧名へ戻せることも固定。
`ENABLE_RESOURCE_PRINCIPAL` 後に EXECUTE が無ければ中止（付与の確認は `OWNER='ADMIN'` に限定し、
別スキーマの同名オブジェクトへの grant を誤認しない）。既存ユーザーのパスワード無指定では
`ALTER USER` を出さない。ORA-28007 は実ログインで裏取りし、入れなければ中止。
`IDENTIFIED BY "..."` へ埋めるパスワードは引用符・空白・改行を拒否し、拒否時は DDL を 1 本も出さない。

`pytest` をリポジトリ直下から流すと `pydantic-settings` が `.env`（実値入り）を拾うため、
`SPEECH_BUCKET` / `OIDC_*` を設定済みの開発機で 2 件が落ちていた。既存の同種テストと同じ作法
（`delenv` ではなく空文字を `setenv`）に揃えて解消した。
