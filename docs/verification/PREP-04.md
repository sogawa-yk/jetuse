# PREP-04 検証レポート — 1 セルが上限を超える xlsx（セル内分割）

対象: `packages/api/jetuse_core/extract_xlsx.py`
実施日: 2026-08-02 / 実環境: 共有 loop ADB（run 固有スキーマ）+ OCI Generative AI（大阪）
証跡: `runs/2026-08-02T0934_PREP-04/e2e/`

## 1. 何が起きていたか（実データで見つかった）

仕様書 8 冊を JetUse へ取り込んだところ、**2 冊が丸ごと取り込めなかった**
（`422 limit=chunk_chars`）。原因は PREP-01 の分割設計の穴である。

| 事実 | 値 |
|---|---|
| 失敗したファイル | 2 冊（いずれも「サンプル」シート） |
| 超過していた行 | 13,728 文字 / 13,288 文字 |
| その行の非空セル数 | **1 個**（`A53` に 13,728 文字。API のリクエスト例が丸ごと 1 セル） |

PREP-01 は「上限を超えたら**行境界で分割**する（分割は切り詰めではない）」と設計したが、
**1 行そのものが上限を超える**場合は分ける場所が無く、ファイル全体を拒否していた。
しかもその行の非空セルは 1 個なので、**セル境界でも割れない**。

影響が「一部が欠ける」ではなく「**そのファイルが入らない**」だったのが重い。
利用者から見ると 8 冊上げたのに 6 冊しか検索対象になっていない。

## 2. なぜ架空データで出なかったのか

PREP-01 の検証ブック（`spikes/prep01/fixtures.py`）を「**表らしい表**」として作っていた。
複数シート・空シート・結合セル・数式セル・広い空白領域と、扱いにくい要素は入れてあったが、
**1 マスに巨大テキスト**という形が無かった。セルの値はどれも見出しや短い説明で、
1 行が上限（2,000 文字）に届くことがない。

実務の仕様書では「API のリクエスト例やレスポンス例を 1 セルに貼る」のは普通の書き方であり、
**表として整っていないセル**こそが前処理の難所だった。上限の分割ロジックは
「行数が多い塊」だけを想定していて、「セルが太い」ケースを想定していなかった。

→ 今回の架空ブック（`spikes/prep04/fixtures.py`）は**この形**を固定した:
`サンプル` シートの `A53` に 13,081 文字（JSON のリクエスト例と説明が交互）、その行の非空セルは 1 個。

## 3. 採った対処（2026-08-02 人間ゲートで承認済み）

**セルの中で分割する。** 上限の引き上げも、長いセルの読み飛ばしも採らない。

| 案 | 採否 | 理由 |
|---|---|---|
| 上限を引き上げる | **不採用** | もっと長いセルが出れば同じ問題。検索単位が粗くなり根拠の絞り込みが効かなくなる |
| 長いセルを読み飛ばす | **不採用** | **黙って中身が欠ける**。「取り込めている」のに入っていない状態を作る |
| **セルの中で分割する** | **採用** | 元の設計意図は「黙って切り捨てない」。分割は切り捨てではない（中身は全部残る） |

分割の順序は 3 段階になった。**分ける場所が無いなら作る**。

1. **行境界**（PREP-01 のまま）— 塊が収まらない → 行で割る。`cells` は行範囲。
2. **セル境界**（新規）— 1 行だけで超える → 連続する列の並びで割る。`cells` は列範囲。
3. **セルの中**（新規）— 1 セルだけで超える → セルの中で割る。**`cells` は元のセルのまま**。

切る位置は**意味の切れ目を優先**する（改行 → 区切り文字 `。、，；！？.,;`・空白 →
最後の手段として文字数）。実データは JSON のリクエスト例だったので改行が効く。
**構造の解析はしない**（JSON として妥当な位置で切ることは目指さない = 非ゴール）。

## 4. 出典の精度は落ちない

セル内で割った断片は、どれも**元のセルと同じ `sheet` / `cells`** を持つ（例: 7 断片すべてが
`A53`）。どの断片が引かれても「`サンプル` シートの `A53` が根拠」であり、これは
**分割前に返せたはずの出典とまったく同じ粒度**である（分割前はそもそも取り込めなかった）。
`chunk_id` は既存の採番規則（`<file_id>-<n>`）でそのまま一意になる。

## 5. 黙って分割しない

分割は「切り捨てではない」が、**起きたことは見えるべき**である。API 契約は変えずに 2 つ:

- セル内で割った断片だけが `part`（`"2/7"`）を持つ。`POST /api/extract` の応答にそのまま出る。
  **既存の鍵は増減しない**ので、`part` を見ない既存クライアントは無変更で動く。
- サーバー側に WARNING ログ（`sheet` / `cells` / 文字数 / 断片数。**本文は出さない**）。

`part` は ADB のチャンク表には持たない（列を増やさない。引用の出典は `cells` で足りる）。

## 6. 上限の意味は変えていない

`chunks`（総チャンク 1,000）/ `workbook_bytes`（10MB）/ `uncompressed_bytes`（100MB）/
`scanned_cells`（5,000,000）は**据え置き**で、超過は従来どおり 422（切り詰めない）。
変わったのは `chunk_chars` を**拒否の理由から外した**ことだけである（分割で必ず収まるため）。
セル内分割で断片が増えて総チャンク数を超えれば、従来どおり `limit=chunks` で拒否する。

### 検証データについての気づき（隠さず書く）

最初の架空ブックは「同じ形の JSON を延々と繰り返す」13,000 文字にしていた。取り込みも分割も
出典も正しく動いたが、**どの断片も同じように埋め込まれる**ため、中ほどに置いた一文を狙った
検索が上位に入らなかった（スコアはどれも 0.37 前後で横並び）。これは実装ではなく**検証データ**の
問題である（実物の仕様書は節ごとに内容が違う）。ブックを「話題ごとに内容の違う節が並ぶ」形に
作り直したところ、狙った断片が 0.56 で 1 位になった。**上限や判定を緩めてはいない。**

## 8. 残っていること
