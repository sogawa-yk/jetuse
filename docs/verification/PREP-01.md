# PREP-01 検証レポート: xlsx の前処理（セル位置つき抽出）と取り込み口

実施日: 2026-07-30 / リージョン: ap-osaka-1 / 対象: `adb` と `vector_store` の両バックエンド
仕様の正本: `docs/decisions/ADR-0020-rag-metadata-backend.md` / `specs/09-rag.md` [PREP-01]
実測の前提: `docs/verification/SPIKE-M1.md` ①-a（マネージドの属性はファイル単位）・③（ADB はチャンク単位）
証跡: `runs/2026-07-30T1600_PREP-01/e2e/`（実施しなかった範囲は同ディレクトリの `SKIPPED.md`）

## 結論（先に）

**xlsx を投げると、シート名とセル範囲を持ったチャンクとして取り込める。**
実環境（実 OCI Generative AI + 実 ADB）で確認した。

1. `adb` バックエンドでは、1 ファイルの引用が**チャンクごとに異なる出典**を返す
   （`制約 C5:E6` / `制約 C40:E40` / `改訂履歴 A1:C2` / `API一覧 B12:D14`）。
   「仕様書 v2.0 の『制約』シートの C5:E6 が根拠」まで返せる状態になった。
2. マネージド Vector Store は**ファイル単位**のままである（`sheet="(ブック全体: 3 シート)"` /
   `cells="(ブック全体)"`。N は**本文があったシート数**で、空シートは数えない）。
   **この差は隠していない**。
3. 版フィルタ（`current_version='Y'`）は xlsx 由来のチャンクにも効く。

## 新しく分かったこと（一次情報）

### マネージド Vector Store は xlsx を受け付けない（実測）

素の xlsx を `files.create` → `vector_stores.files.create` に流すと 400 で断られる
（`runs/.../e2e/scenario-2.md` (a)）:

```
BadRequestError: 400 - {'error': {'code': 'unsupported_file',
  'message': "Unsupported file type 'xlsx' found for file-kix-… ", 'type': 'unsupported_file'}}
```

SPIKE-03 の docx（`Unsupported file type 'docx'`）と同じ扱い。つまり **xlsx はアプリ側の
前処理が必須**であり、本タスクの抽出はマネージド経路にとっても前提条件だった。
そこで取り込み時は、抽出したテキストを `<原名>.xlsx.txt` として Files API へ渡す。
台帳の表示名・Object Storage の原本バックアップ・`sha256` は**元の xlsx のまま**にしてある
（利用者に見える名前と、出典のハッシュは原本を指す）。

### 属性はやはりファイル単位（①-a の追試）

同じブックを取り込んだ 2 ファイル（v1.0 / v2.0）の属性はそれぞれ 1 種類だけで、
チャンクがいくつできても増えない。実 API の RAG 応答でも、同一ファイル由来の引用が持つ
(シート, セル範囲) は**常に 1 種類**だった（`scenario-2.md` (c)）。

| | `adb` | `vector_store`（マネージド） |
|---|---|---|
| 出典の粒度 | **チャンク単位**（シート名 + セル範囲） | **ファイル単位**（1 ファイル 1 種類） |
| 実測値の例 | `制約 C5:E6` / `改訂履歴 A1:C2` | `(ブック全体: 3 シート)` / `(ブック全体)` |
| 取り込み形式 | 原本の xlsx をアプリ側で抽出 | 抽出テキスト（`.xlsx.txt`）。素の xlsx は 400 |

**「マネージドでもセル単位で返る」ように見せる細工（1 チャンク = 1 ファイルへの分割等）はしていない。**
差があること自体が ADR-0020 の決定内容であり、その可視化は RAGM-03 の担当。

## 実装（何を足したか）

| 変更 | 内容 |
|---|---|
| `jetuse_core/extract_xlsx.py`（新規） | 抽出の唯一の実体。`openpyxl` を **`read_only=True, data_only=True`** で開き、シートごとに**連続する非空セルの矩形**を 1 チャンクにして `sheet` / `cells`（A1 形式）を付ける。ファイル単位の属性（`file_attributes`）とテキスト化（`render_text`）もここ |
| `jetuse_core/rag.py` | `ALLOWED_EXTENSIONS` に `.xlsx`。`prepare_upload()` が xlsx だけ「抽出テキスト + ファイル単位属性」に変換する。導出した `sheet` / `cells` を**利用者指定で上書きさせない**（422） |
| `jetuse_core/rag_adb.py` | `chunk_units()` が xlsx を `extract_xlsx` へ振り分ける（出典が行番号ではなくセル範囲になる。返る形は同じ `{sheet, cells, text}`） |
| `jetuse_core/rag_opensearch.py` | xlsx をそのまま UTF-8 デコードして文字化け本文を投入しないよう抽出経由に |
| `service/routes/rag.py` | `POST /api/extract`（取り込まずに抽出結果を返す）。xlsx の上限超過・壊れたブックを 422 に正規化 |

### 決めたこと 1: 上限超過は切り詰めずに 422 で拒否する

| 上限 | 値 | 理由 |
|---|---|---|
| `workbook_bytes` | 10 MB | xlsx は zip。展開後（共有文字列 + シート XML）は桁で大きいので、汎用の 20MB より手前で止める |
| `uncompressed_bytes` | 100 MB | 圧縮率で殴られない（zip bomb）。zip の各エントリの合計を**開く前**に見る |
| `scanned_cells` | 5,000,000 | チャンクにならないまま延々と読ませない。**空行・空セルも数える**（`read_only` の反復は欠けた行を空行で埋めるので、非空行だけ数えると「中身が無いのに広いブック」が上限を抜ける） |
| `chunks` | 1,000 | ベクタの同時保持量と取り込み時間の上限 |
| `chunk_chars` | 2,000 | 埋め込み API の切り詰め位置に合わせる（本文と検索表現をずらさない） |

**行もチャンクも逐次処理し、上限は 1 件作るたびに見る。** 塊を丸ごとメモリへ溜めてから数えると、
上限内のファイル（密なシート 1 枚）でも API worker を落とせる（review-2 の blocker 指摘）。
同時に保持するのは「作りかけの 1 チャンク分の行」と確定済みチャンク列だけで、どちらも上限で抑えてある。

detail に `limit=<名前>` を書く（実測: `チャンク数が上限を超えました(> 1)。… (limit=chunks)`）。
**黙って一部だけ取り込まない。** 一部だけ入ると、利用者からは「取り込めたのに根拠が出ない」と
区別が付かない（RAGM-01 で属性の切り詰めを禁じたのと同じ理由）。

なお、上限に収まらない**塊は行境界で分割する**（切り詰めではない。分割後のチャンクは自分の
行範囲を `cells` に持つ）。拒否するのは「1 行だけで上限を超える」場合だけ。

### 決めたこと 2: 表構造の復元はしない

結合セルは左上のセルだけが値を持つ（`read_only` の素の挙動）。ヘッダ推定も列の意味解釈もしない。
まず**位置が取れること**を優先した（タスクの非ゴール）。テキスト化は行ごとにタブ区切り、
塊の左端から埋めるので列はずれない。

### 決めたこと 3: 壊れたブックは 500 ではなく 422

`read_only` の反復は遅延実行なので、シート XML の破損は**行を読んでいる最中**に初めて現れる。
開くときだけを try で囲っても 500 が漏れる。抽出の全区間（開く → 全シートの反復）を
`UnsupportedWorkbook` への変換境界で囲い、zip としては正しいがシート XML が壊れたブックで
テストを固定した。

### 決めたこと 4: `kind` は両バックエンドで同じ値にする

取り込み時に指定した分類（`kind="spec"`）を ADB 側にも渡す。渡さないと、同じファイルが
マネージドでは `spec`、ADB では既定の `doc` になり、**分類での絞り込みがバックエンドを
変えた瞬間に結果を変える**。あわせて `kind` は UTF-8 で 32 バイト以内に限った（ADB の列が `VARCHAR2(32)`・BYTE
セマンティクス想定。片方だけ通る長さを受け付けない）。型は従来どおりスカラーを受けるが、
**ADB 側は文字列列**なので非文字列は文字列化されて入る（`kind=0` → マネージド `0` / ADB `"0"`）。
分類は文字列で揃えるのが前提（残課題に記載）。

### 決めたこと 5: `select_ai` の xlsx は `pending` ではなく `error` — **PREP-02 で撤回**

> **この判断は誤りだった。** 「xlsx は索引に載らない」は実機の裏付けが無い推測で
> （当時 `SKIPPED.md` §2 に「実機確認は未実施」と明記）、PREP-02 の実測では **Select AI は
> xlsx を正常に取り込む**。恒久 `error` は撤回し、他形式と同じ「索引に在れば `indexed` /
> 無ければ `pending`」に戻した。根拠は `docs/verification/PREP-02.md`。以下は当時の記録。

Select AI の索引はバケットの**原本**を DB 側が読むので、アプリ側の抽出を通らない。
xlsx は索引に載らないため、取り込み状況バッジを `pending`（= いつか入る）のままにすると
永久に入らないことに誰も気づけない。`rag.SELECT_AI_EXTENSIONS`（pdf / txt / md）に無い形式は
`error` を返す。実機での挙動確認は未実施（`SKIPPED.md` §2・残課題）。

### 決めたこと 6: キャッシュの無い数式セルは空扱い

`data_only=True` は Excel が保存した**値のキャッシュ**を読む。openpyxl などで生成したブックの
数式セルはキャッシュを持たないので `None` になる。数式そのものは取り込まない（`=SUM(...)` を
本文に混ぜても検索の役に立たない）。単体テストで固定した。

## 残課題

- **`select_ai` バックエンドと xlsx 原本**（要起票）。バッジ上は `error` として正直に出す
  ようにしたが、実機で「索引がどう扱うか」「抽出テキストを別オブジェクトとして投入すべきか」は
  未確認（この環境では Select AI の索引が未作成。作成に数十分と ADMIN セットアップが要る）。
- `opensearch` 経路の xlsx は単体テストのみ（この環境では無効）。
- `kind` に数値・真偽を入れると、マネージドは値のまま・ADB は文字列（`0` / `"0"`）になる。
  既存クライアントを壊さないためスカラーは受け続けているが、分類は文字列で揃える前提。
  型を文字列に寄せるなら公開契約の変更なので別途判断が要る。
- 抽出の粒度（矩形の切り方）は「空行・行の飛びで区切る」だけ。列方向に離れた 2 つの表を
  同じ行範囲に置くと 1 チャンクにまとまる。案件で必要になったら `POST /api/extract` の結果を
  使って呼び出し側で組み直せる（そのための口）。
