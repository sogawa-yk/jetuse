# 実施しなかった範囲と理由（無言スキップしない）

## 実施できたこと

- スケール検証 3 ラウンド（50,000 チャンク・実行計画・再現率）を**投入からやり直して 2 周**: `e2e/scale/`
- E2E シナリオ 1〜7（実 ADB・タスク専用スキーマ `JETUSE_RAGM02`・マイグレーションのクリーン適用込み）:
  `e2e/scenario-*.md` / `e2e/migrate.md`
- 安全ガードの否定シナリオ 6 件（作り直し・同秒作り直し・台帳空・**最終照合前の差し替え**・既存再利用時の変更拒否）: `e2e/guard.md`
  （いずれも `teardown.py --yes` の実削除を実際に試させている。スキーマ名が run 固有でこの run の所有物なので、ガードが壊れていても他タスクへ届かない）
- アップロード経路（`rag.add_file` → `rag_adb.ingest`）の配線は単体テストで固定: `packages/api/tests/test_rag_adb.py`

## 実施しなかったこと

| 範囲 | 理由 |
|---|---|
| **数十万チャンクでの測定** | 50,000 で測った（投入からやり直して 2 周）。10 倍規模は埋め込み API 呼び出し（約 50 万回）と ADB のベクタメモリ消費が別桁になり、共有 loop ADB を並行タスク（RAGM-01）と共有している状況では影響が読めない。50,000 で実行計画の分岐（PRE-FILTER / IN-FILTER / 全件走査）は再現できたため、判断に必要な情報は取れている。数十万規模は未検証と明記した（`docs/verification/RAGM-02.md` ⑥）。 |
| **VPD / Data Redaction がベクタ検索に効くか** | タスクの非ゴール（別タスク）。未実証のまま「行レベル制御ができる」と資料に書かないよう、ADR-0020 の未解決事項のままにした。 |
| **ブラウザ（/rag 画面）からの操作** | 本タスクの area は `api`。バックエンド選択 UI と能力差の表示は RAGM-03 の担当で、`packages/web` には触れていない。HTTP エンドポイント（`POST /api/chat/stream`）と `backends` バッジまでを実環境で確認した（シナリオ 4）。 |
| **配備済み Container Instance からの実行** | ローカル（macOS）→ 大阪リージョンの往復で測っている。`AUTH_MODE=resource_principal` の配備環境での再測定はしていない（レイテンシの絶対値はその分ぶれる。実行計画と再現率は DB 側の性質なので変わらない）。 |
| **DB 内埋め込み（`UTL_TO_EMBEDDING`）を通した取り込み** | `OCI$RESOURCE_PRINCIPAL` では ORA-24247 で通らないことまでは実測した（`docs/verification/RAGM-02.md` ④）。通すには API キーの資格証明を DB に作る必要があり、ADR-0021 が廃止した経路のため、実装にも E2E にも入れていない。 |
| **実績実行計画（`DBMS_XPLAN.DISPLAY_CURSOR`）** | `V$SESSION` の権限が検証スキーマに無い（SPIKE-M1 と同じ制約）。`EXPLAIN PLAN`（推定）で代替した。 |
| **他バックエンド（vector_store / select_ai / opensearch）の同時確認** | 本タスクの禁止事項（既存 3 バックエンドの挙動を変えない）。シナリオ 4 で見たのは `backends` の `adb` 欄のみで、他バックエンドの状態には依存させていない。 |
| **多数同時・多文書の負荷試験** | 同名ファイルの 2 接続同時取り込み（初回競合）は実 ADB で確認した（シナリオ 7）。それ以上の並行度・多文書混在の負荷は測っていない。 |
| **部分マイグレーション中のアップロードの再開（outbox）** | 017 だけ適用済みの状態は `unavailable` として扱うが、失敗の記録先（019）自体が無いので**記録できない**。そのファイルは `pending` のまま残り、再アップロードで取り込まれる。恒久対策（永続 outbox と再開ジョブ）は本タスクの範囲外（残課題）。 |
| **マイグレーション途中停止からの回復（DDL 成功 → 履歴 INSERT 前にプロセス停止）** | Oracle の DDL は暗黙コミットなので、この瞬間に止まると再実行が ORA-00955 になる。**マイグレーションランナー（`jetuse_core/migrate.py`）の設計に由来する既存の性質**で、RAGM-02 の 3 ファイルだけの問題ではない（001〜016 も同じ）。1 ファイル 1 DDL にして影響範囲を最小化したうえで、ランナー側の回復設計はリポジトリ全体の後続課題として残す。 |
| **シナリオ7 の同期点の粒度** | `threading.Barrier` は `ingest()` の入口にあり、そこから DB の版採番までの間に埋め込み API 呼び出しが入る。実測では 2 スレッドの実行区間が重なった（`overlapped=True`）うえで版が 1.0 / 2.0 に分かれ現行版が 1 つになったが、「版採番の critical section が重なった」ことを直接示してはいない（それには製品コードにテスト用フックが要る）。 |
| **取り込み失敗時の自動リトライ** | 未実装。失敗したファイルは `backends.adb` が **`error`** になり、同じファイルを上げ直せば取り込まれる（版が上がる）。恒久的な再試行ジョブは本タスクの範囲外（残課題）。 |
| **`POST /api/rag/files`（実アップロード API）からの取り込み** | この経路は Vector Store と Files API に実リソースを作る既存経路（RAGM-01 の担当領域）で、本タスクの変更は「そこに `rag_adb.ingest` を1か所足した」配線のみ。共有テナンシに検証用 Vector Store を増やさないため、配線は単体テスト（有効時に呼ぶ / 無効時に呼ばない / 取り込み失敗でもアップロードは成功）で固定した。チャット側の実 HTTP 経路（`POST /api/chat/stream`）はシナリオ 4 で実環境を通している。 |
| ~~最終照合と `DROP USER` の間の競合~~ | **解消**。検証用スキーマを **run 固有名**にした（オーケストレータ承認 2026-07-30）ので、同名を作る他主体がおらず窓が構造的に消えた。否定シナリオは実削除（`--yes`）を実際に試させている。 |
| **配備済み Container Instance（`AUTH_MODE=resource_principal`）への実ネットワーク E2E** | シナリオ 4 は**プロセス内の ASGI 統合テスト**（`TestClient`）で、相手の ADB と LLM は実物だが、認証・LB・Resource Principal 経路は通っていない。配備しての確認は RAGM-03 / デプロイ時のゲートに残す（このタスクの area は `api`）。埋め込みも検索も `jetuse_core` の共通経路（`oci_auth` / `embeddings` / `db`）を通るため、認証方式の差はこのタスク固有ではない。 |
