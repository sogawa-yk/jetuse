# 実施できなかった検証と、その理由

## 未実施: 配備済みスタックでの `POST /api/tts`（修正後）

**ゲート**: `/api/tts` を処理するのは **Functions ルーターのコンテナ画像**であり、
修正を反映するには画像の再ビルドと push が要る。本リポジトリの Public 版では、
その画像は **`main` への merge 時に release.yml が生成**する。したがって、
修正が merge される前に配備経路を通すことは、通常のリリース手順の中では成立しない。

**手動で通す場合に必要な操作（未実施・人間の承認が要る）**:
1. 修正版の `jetuse-fn-router` 画像をビルドし、検証用リポジトリ（`jetuse-spike-` プレフィックス）へ push
2. 配備済みスタック `jetuse-pub` の `fn_router_image` をその画像へ変更して apply
3. TTS の E2E を実行
4. 変数を戻して再 apply

2 と 4 は、利用者が「常設でよい」と承認した稼働中の環境を一時的に非リリース画像へ差し替える。
環境を変更する判断は人間のものなので、承認なしには行っていない。

## 代わりに実施したこと

`real-service-before-after.md` のとおり、**モックを使わず実 OCI Speech に対して**
修正前後の同一シナリオを実行し、修正前は 500 で失敗・修正後は Phoenix へ
フォールバックして MP3 を返すことを確認した。ただしこれは **ライブラリ層の確認**であり、
API Gateway → Functions の経路そのものは通していない。

## 完了主張の範囲

**「実環境で確認済み」とは主張しない。** 実サービスに対する前後比較と単体テストまでが
現時点の裏付けである。配備経路の確認は merge 後（release.yml が画像を作った後）に、
スタックを更新して実施する必要がある。
