# 実施できなかった範囲と理由（無言スキップ禁止）

## 1. 大規模データでのベクタ索引利用・再現率（③）

- **何を**: 数万〜数十万チャンク規模で「メタデータ WHERE + HNSW/IVF 索引」がどう組み合わさるか
  （プレフィルタか、索引探索後のフィルタか）、および TARGET ACCURACY に対する実再現率。
- **なぜ実施しない**: 本タスクの検証データは架空 10 チャンク。10 行ではオプティマイザが
  索引を使わず全件走査＋厳密検索を選ぶ（実行計画 `TABLE ACCESS STORAGE FULL` で確認済み）。
  規模を作るには顧客データか大量のダミー生成が必要で、いずれも本タスクの範囲外。
- **影響**: `docs/comparison/rag-metadata-backends.md` のレイテンシ表は
  「小規模での数字であり大規模の傾きを示さない」と明記した。ADR-0019 でも
  ③ 採用前のスケール検証を未解決事項として残した。

## 2. Chicago（us-chicago-1）での再確認

- **何を**: ①②③ の可否・レイテンシの Chicago 差分。
- **なぜ実施しない**: `tasks/SPIKE-M1.md` の非ゴールに明記（後続タスク）。
  ユーザー指示でも「Chicago 差分の確認は対象外」。

## 3. ③ の VPD / 業務表 JOIN の実証

- **何を**: 「在庫表と JOIN したベクタ検索」「VPD による行レベル制御がベクタ検索にも効く」の実機実証。
- **なぜ実施しない**: 架空チャンクのみを用意し業務表を作らなかったため。
  SQL である以上書けることは自明だが、**実行結果は無い**。
- **影響**: 比較ドキュメントと ADR では「SQL なので JOIN できる」という一般論以上の
  主張をしていない（実測値として提示していない）。

## 4. JetUse 本体（rag.py / chat.py）に属性を通す E2E

- **何を**: `/api/chat` の実応答に構造化された出典が載ることの確認。
- **なぜ実施しない**: `tasks/SPIKE-M1.md` の非ゴール「JetUse 本体の実装を変更しない」。
  実装は ADR-0019 承認後の別タスク。
- **影響**: 本スパイクは OCI / ADB の生 API・生 SQL の水準で確定させ、
  アプリ層への反映は ADR の実装タスクへ送った。

## 5. ① の大規模データ・チャンク分割戦略の最適化

- **何を**: 1 チャンク = 1 ファイルにしたときのファイル数上限・取り込みスループット・コスト。
- **なぜ実施しない**: ADR-0019 が ① を短期採用として提案しており、その運用設計は
  実装タスク側の検討事項。本スパイクは「属性がファイル単位である」ことの確定までを担った。

## 6. デプロイ（Container Instance）を伴う E2E

- **何を**: `loop-config.yml` の `areas.api.deploy_cmd`（ADB 起動 + マイグレーション）以降の
  アプリ配備と、配備済みエンドポイントからの計測。
- **なぜ実施しない**: 本タスクはアプリコードを一切変更しない検証タスクで、
  配備すべき差分が無い。ADB は起動して実スキーマを作り、実 SQL / 実 API を叩いている
  （＝実環境実行そのものは満たしている）。レイテンシはローカル macOS → ap-osaka-1 の
  往復であり、配備済み CI からの数字ではない旨をレポートに明記した。
