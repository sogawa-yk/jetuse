+### [PREP-04] 1 セルが上限を超える xlsx（セル内分割）2026-08-02追記

+
+1. **行境界**（[PREP-01]）: 塊が収まらない → 行で割る。`cells` はその行範囲。
+2. **セル境界**（新規）: 1 行だけで超える → その行を連続する列の並びに割る。`cells` はその列範囲。
+3. **セルの中**（新規）: 1 セルだけで超える → セルの中で割る。**どの断片も `cells` は元のセル**
+   （例: 7 断片すべてが `A53`）。どの断片も「そのセルが根拠」なので出典の精度は落ちない。

# シナリオ4（回帰）— 上限の意味は変えていない

セル内分割で**収まらなくなる上限**（総チャンク数・ブックのバイト数）は据え置きで、
超過は従来どおり **422**（切り詰めない）。一時的に上限を下げて同じ架空ブックを投げた。

```
chunks: HTTP 422 / detail = チャンク数が上限を超えました(> 3)。シートを分けるかファイルを分割してください (limit=chunks)
workbook_bytes: HTTP 422 / detail = ブックのバイト数が上限を超えました(6998 > 100 バイト) (limit=workbook_bytes)
```

- どちらも 422 で、**どの上限に当たったか**が detail に出る: **True**

判定: **PASS**

> セル内分割は「1 チャンクの文字数」だけを拒否理由から外した（分割で必ず収まるため）。
> 断片が増えて総チャンク数の上限を超えれば、従来どおり `limit=chunks` で拒否する。

# 実環境 E2E で実施しなかった範囲と理由（無言スキップ禁止）

## 1. 顧客の実ファイルでの確認 — **実施しない（禁止事項）**

不具合を見つけた実ファイル（仕様書 8 冊）は持ち込まない。代わりに**実データと同じ形**
（1 セルに 13,000 文字級・その行の非空セルは 1 個・中身は API のリクエスト例）の
**架空ブック**を `spikes/prep04/fixtures.py` に固定して検証した。
実データの数値（13,728 / 13,288 文字・`A53`）は形の再現にだけ使い、中身は再現していない。

## 2. マネージド `vector_store` 側の粒度の再測定 — **実施しない（本タスクで変えていない）**

取り込み自体は実環境で通っている（シナリオ1 の `backends` が `vector_store: indexed`。
巨大セルのブックが 422 にならずマネージド側にも入った）。ただし属性が**ファイル単位**で
あることは PREP-01 が実測済み（`docs/verification/PREP-01.md`）で、本タスクは
`file_attributes()` を変更していない。断片ごとの `part` もマネージド属性には載せていない。

## 3. `select_ai` / `opensearch` バックエンド — **未確認（この環境では対象外）**

- `select_ai`: バケットの原本を DB 側が読む経路で、アプリのチャンク化を通らない
  （PREP-02 で実測済み）。取り込み状態は `pending` のまま（DB 側パイプラインの非同期処理）。
- `opensearch`: この環境では無効（`backends.opensearch = disabled`）。単体テストのみ。

## 4. `scanned_cells` / `uncompressed_bytes` の上限超過 — **単体テストで固定**

実環境では `chunks` と `workbook_bytes` の 2 つを 422 で確認した（シナリオ4）。
残る 2 つは同じ経路（`extract()` 冒頭・`_Budget`）で、本タスクの差分が触っていない。
`packages/api/tests/test_extract_xlsx.py` が全上限を固定している。

## 5. SPA（画面）からの取り込み — **実施しない（api area のタスク）**

変更は `packages/api` に閉じており、画面側の変更は無い。
